# MediaFlow Frontend — 前端工程与创作工作台规范

本文件适用于 `frontend/` 下的所有前端源码、脚本、测试、样式和构建配置，并与仓库根目录 `AGENTS.md` 共同生效。实现前先检查仓库现状与 `docs/README.md` 中的设计基线，不得假设尚未实现的后端接口已经可用。

## 1. 技术栈与基本原则

- 使用 **React + TypeScript + Vite** 构建前端应用，优先使用函数组件与 Hooks。
- 使用 **Arco Design（React）** 提供表单、表格、弹窗、通知、导航等标准业务组件；使用 **Tailwind CSS** 负责布局、间距、响应式及定制页面样式。
- 使用 **React Flow** 构建工作流 DAG 编辑与可视化界面；视频时间轴编辑器须独立设计，不得直接以 DAG 画布代替。
- 使用 **TanStack Query** 管理服务端数据请求、缓存、失效和刷新；仅在确有跨组件客户端状态需求时使用 **Zustand**。
- 不得擅自改用 Next.js、Vue、其他 UI 框架或引入第二套大型组件库；新增重要依赖须说明用途、替代方案与维护成本。
- 优先采用清晰、可维护的方案，不为抽象而抽象，不在一次任务中实现未授权的后续业务功能。

## 2. 应用架构与模块边界

- 按业务领域/功能模块组织代码，例如 `workspace`、`project`、`script`、`storyboard`、`asset`、`workflow`、`task`、`model`、`settings`，而非把全部代码堆在全局 `components/` 和 `services/` 中。
- 页面与路由负责组织视图和交互；业务状态及用例协调放在相应模块；通用组件仅承载可复用的展示或交互能力。
- 推荐区分页面、功能组件、API Client、数据查询 Hooks、类型、校验 Schema 和纯工具函数；避免组件直接拼接 URL 或散落处理后端错误。
- 不把数据库表结构、sqlc 生成类型、Lease 等后端实现细节直接视为前端领域模型；仅使用明确的 HTTP API 契约。
- 共享代码必须具有真实复用场景，避免创建过度通用的组件、状态容器或框架层。
- 仅在必要时建立跨模块依赖，防止循环依赖；路径别名、命名和导出规则应保持一致。

## 3. RESTful API 与类型契约

- 对外业务接口使用后端确定的 **RESTful API**，统一通过 `/api/v1` 访问，默认交换 JSON。
- 前端不得直接调用 `/internal/v1` Worker 通信接口，也不得直接访问 PostgreSQL、Redis 或执行内部调度操作。
- 使用 **OpenAPI 3.1** 作为前后端接口契约。接口文档存在时，优先据此生成或维护类型化 API Client；不得凭设计文档编造请求字段、响应字段和可用接口。
- API 请求集中封装，统一处理 API Base URL、认证信息、请求取消、超时、错误响应和必要的追踪标识；不在 UI 组件中直接散落 `fetch` 调用。
- 遵循 HTTP 方法与状态码语义：GET 为安全读取；创建使用 POST；更新按契约使用 PUT/PATCH；正确处理 201、202、204、400、401、403、404、409、422、429、5xx 等响应。
- 解析后端错误时兼容约定的 **RFC 9457 Problem Details** 及业务错误码；界面展示用户可理解的错误信息，日志不得泄露凭据或敏感响应内容。
- 服务端状态使用 TanStack Query 管理，合理设置 Query Key、失效策略、轮询和取消；不要把服务端数据无必要地复制到 Zustand。
- 对工作流创建、运行提交、任务重试等可能重复触发副作用的操作，遵守后端幂等约定；按钮禁用不等于请求幂等。
- 分页、筛选和排序遵循 API 契约；高频状态查询应控制轮询间隔与并发，不得无限制请求。
- 后端接口尚未实现时，明确标记 Mock/占位数据，并与真实 API Client 分离；不得将演示数据伪装为生产数据。

## 4. UI 体系与样式规范

- **Arco Design 负责标准业务组件，Tailwind CSS 负责布局和局部视觉样式**；避免大量覆盖 Arco 内部 DOM 类名或私有样式。
- 统一主题色、字号、间距、圆角、阴影、状态色和暗色模式策略，优先使用可维护的主题 Token，不在各页面重复硬编码视觉规则。
- 检查 Arco 样式与 Tailwind Preflight/基础重置之间的冲突；根据实际 Tailwind 版本配置样式层与导入顺序，不直接照搬其他版本的配置片段。
- 界面必须提供加载、空状态、错误、无权限、无数据和长任务进行中状态；异步操作应有明确反馈。
- 保持键盘可操作性、合理焦点管理、可读标签、对比度和必要的 ARIA 语义；不可仅以颜色表达任务状态。
- 兼顾不同屏幕尺寸，但复杂创作工作台可以定义合理的最小工作区宽度，并提供窄屏降级方案。
- 图标、日期时间、数值单位及国际化文本使用统一方案；不可在组件中散落不一致的格式化逻辑。

## 5. 创作工作台与媒体处理交互

- 工作流编辑器基于 React Flow，前端主要负责节点编辑、连接交互、布局和可视化；**DAG 合法性、节点执行资格和状态转换以后端为准**。
- 区分 WorkflowDefinition/WorkflowVersion 与 WorkflowRun，编辑草稿、发布版本、运行实例和运行历史必须有明确 UI 边界；已发布版本不可被前端隐式修改。
- 工作流节点、连线、表单应遵循后端实际节点类型和 Schema；不得凭前端校验替代服务端校验。
- 任务监控需明确区分排队、运行、重试、成功、失败、取消等状态，采用后端状态及时间戳，不从页面计时器推断任务真实完成情况。
- 视频、图片、音频的大文件通过约定的对象存储访问方式及签名 URL/上传流程处理；不得默认将媒体二进制编码进 JSON。
- 大素材列表、DAG 画布与运行日志需考虑虚拟化、分页、懒加载和渲染性能；高频进度更新避免触发整个工作台重复渲染。
- 上传、生成、渲染等长耗时操作应展示可恢复的进度或状态，并明确「请求已接受」与「任务已完成」的区别。
- 浏览器视频预览只是交互能力，正式合成结果以服务端媒体处理流水线及已确认资产为准。

## 6. TypeScript 与代码质量

- 开启 TypeScript 严格检查；避免 `any`、非空断言滥用和 `@ts-ignore`。外部不可信数据必须按契约解析/校验，类型断言不等于运行时校验。
- 组件 Props、API 数据、业务状态与 UI 状态分别定义类型；保持状态单一来源，避免重复派生数据。
- 正确清理订阅、事件监听、计时器和异步副作用；处理组件卸载后的请求取消及竞态。
- 表单校验同时考虑前端体验和服务端结果；敏感操作的最终权限与业务判断由后端执行。
- 不在前端源码、环境变量公开前缀或构建产物中存放服务端密钥、AI Provider 密钥及数据库凭据。
- 前端认证凭据的存储与传输方式必须遵循项目安全设计；避免把高敏感长期凭据放入可被任意脚本读取的位置。
- 禁止未经审核直接渲染不可信 HTML；对上传文件名、用户生成内容和富文本保持 XSS 防护。
- 使用项目统一的 ESLint、Prettier（若已配置）及 TypeScript 规则；不可为了通过检查而批量关闭安全或类型规则。

## 7. 测试与验证

- 单元/组件测试优先使用 **Vitest + React Testing Library**，测试用户可见行为而非组件内部实现。
- 对关键路径增加端到端测试，优先考虑 **Playwright**；是否引入需结合仓库现有测试栈和当前任务范围。
- API 交互测试覆盖加载、空结果、认证失败、权限拒绝、业务冲突、网络超时、请求取消和重复提交。
- DAG 编辑器至少验证节点创建/连线、非法连接提示、版本只读、草稿保存及服务端校验失败的处理。
- 媒体交互测试覆盖上传失败、处理中状态、超大素材和结果不可用等边界。
- 使用 Mock Service Worker 等工具模拟 API 时，保持 Mock 与实际接口契约一致，并避免依赖 Mock 证明后端事务正确性。
- 按仓库实际脚本执行类型检查、Lint、测试与生产构建；环境或依赖不可用时如实说明，不能把跳过视为通过。

## 8. 当前阶段开发顺序

1. 检查 `frontend/` 现状、根目录 `AGENTS.md` 和设计文档，确认现有依赖与路由方案。
2. 建立 React + TypeScript + Vite 基础工程，接入 Arco Design 和 Tailwind CSS，验证样式兼容。
3. 配置应用路由、基础布局、错误边界、环境配置和 RESTful API Client。
4. 接入 TanStack Query，确定 OpenAPI 契约与通用错误处理方案。
5. 建立工作空间、项目与资产等基础页面及可复用 UI 组件。
6. 分阶段实现 Workflow DAG 编辑器、任务监控、媒体预览与创作工作台。
7. 根据真实业务需求增加 E2E、性能与无障碍验证。

不得因为列出开发顺序就自行实施未授权的后续步骤。
