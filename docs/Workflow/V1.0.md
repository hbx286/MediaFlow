> **约定**：文中的 SQL 和 Go 片段是协议/算法示意，除特别标注外不是完整生产实现。实际迁移以 Database 文档及验证过的数据库 migration 为准。本文不重新定义 PRD 的用户业务，也不重述 SAD 的系统分层。

## 1. 设计范围、假设与边界

**引擎负责**：编译和校验已发布 DAG、启动运行实例、初始化/展开 NodeRun、绑定输入、求值依赖、处理分支与汇合、确认节点结果、失败传播、工作流聚合状态、暂停/取消和恢复推进。

**不负责**：Worker 选址、并发配额、CPU/GPU 分配、供应商限流、模型调用、文件渲染、对象存储上传。这些由 Scheduler、Task Execution、Model/Media Handler、Asset Service 承担。

跨模块边界：

```
Workflow Definition ──发布不可变版本──> Workflow Engine
                                            │ CreateReadyTask / CancelTask
                                            ▼
                                      Task Execution
                                            │ TaskTerminal event（可重复）
                                            ▼
                                    Workflow Progression
                                            │ Outbox: TaskReady
                                            ▼
                                         Scheduler ─── Worker Runtime
```

权威状态：`workflow_runs`、`node_runs`、`node_dependency_satisfactions`、`tasks`、`task_attempts`、`outbox_events`。消息通知允许重复、延迟、乱序；任何状态推进都必须从持久化状态重新检查。

**基础不变量**：已发布 WorkflowVersion 不可修改；Run 固定版本与输入快照；NodeRun 终态不回退；依赖满足记录幂等；所有 NodeRun 状态只能由引擎侧命令修改；Task 与 Attempt 区分；有效 TaskResult 只能被当前租约确认一次；Run 不能因“任务全部结束”就跳过必要输出校验。

## 2. 术语与责任映射

| 名称 | 意义 | 状态拥有者 |
|---|---|---|
| WorkflowDefinition | 可编辑的流程定义 | Definition |
| WorkflowVersion | 发布后的不可变 DAG/策略快照 | Definition |
| WorkflowRun | 一个版本在固定输入上的执行实例 | Workflow Execution |
| NodeRun | 单次运行中某节点的实例；动态展开用 expansion_key 区分 | Workflow Execution |
| DependencySatisfaction | 某条实际依赖已满足的去重事实 | Workflow Execution |
| Task | 可以调度的独立执行单元 | Task Execution |
| TaskAttempt | Task 的一次具体执行尝试 | Task Execution |
| Artifact / AssetVersion | 节点输出内容的引用与正式资产版本 | Asset Management |
| WorkflowProgression | 跨 NodeRun/Task 聚合的事务协调器 | Application Service |

**映射**：一个 NodeRun 可对应 0..N 个 Task（例如纯条件节点 0 个、批处理节点多个）；任务成功与节点成功不是同义词。

## 3. WorkflowVersion DSL：最小可实施契约

发布数据建议按 schema version 验证（字段命名供后续 JSON Schema 固化）：

```json
{
  "schema_version": "1.0",
  "workflow_id": "wf-demo",
  "nodes": [
    {"id":"script", "kind":"task", "handler":"text.generate", "inputs":{"topic":{"from":"$input.topic"}}, "outputs":{"script":"application/json"}, "retry":{"max_attempts":3}, "on_error":"fail_run"},
    {"id":"storyboard", "kind":"task", "handler":"storyboard.generate", "inputs":{"script":{"from":"script.script"}}, "outputs":{"scenes":"application/json"}},
    {"id":"scene_map", "kind":"map", "collection":{"from":"storyboard.scenes"}, "item_key":"scene_id", "max_items":100, "child_template":"scene_generate"},
    {"id":"render", "kind":"task", "handler":"media.render", "inputs":{"assets":{"from":"scene_map.results"}}, "outputs":{"video":"asset-ref"}},
    {"id":"output", "kind":"output", "inputs":{"video":{"from":"render.video"}}}
  ],
  "edges": [
    {"id":"e1","from":"script","to":"storyboard","mode":"required"},
    {"id":"e2","from":"storyboard","to":"scene_map","mode":"required"},
    {"id":"e3","from":"scene_map","to":"render","mode":"all_success"},
    {"id":"e4","from":"render","to":"output","mode":"required"}
  ],
  "required_outputs":["output.video"]
}
```

`scene_generate` 是在发布版本中单独定义的子流程/模板引用，生产版本必须固定其内容或不可变版本标识；示例刻意未省略这项要求。实际 JSON 解析器不得将未识别字段默默当成受支持的行为。

### 3.1 节点种类与完成条件

| kind | 运行行为 | 何时完成 |
|---|---|---|
| `input` | 解析运行输入 | 校验并产生输出快照后 SUCCEEDED |
| `task` | 创建 1..N Task | 所有必需 Task 有效结果被确认并聚合输出 |
| `condition` | 对确定的输入做纯条件判定 | 输出分支选择决策及其版本 |
| `map` | 读取稳定集合、按稳定键展开 | 所有要求的子节点满足其汇合策略 |
| `join` | 组合多个分支输出 | Join 策略为真且输出契约满足 |
| `approval` | 人工决定 | 授权用户审批事件被确认 |
| `output` | 校验要求的输出 | 引用可用且符合 schema |
| `subworkflow` | 调用固定 WorkflowVersion | 子运行达到预定的可接受终态并映射输出 |

### 3.2 发布前校验

1. ID 唯一；边的源/目标存在；所有 required output 可达。
2. 静态 DAG 无环：Kahn 拓扑排序，复杂度 `O(V+E)`；动态子流程按各自发布版本检验且禁止递归环调用。
3. 输入输出端口 schema 兼容；输出引用不能访问未授权节点数据。
4. `condition` 必须定义互斥且可确定的分支规则，提供默认/不匹配行为。
5. `join` 明确选取 `all_success`、`all_done`、`any_success`、`quorum(k)` 之一；不能隐式推断。
6. `map` 明确 `item_key`、最大数量、集合去重策略、空集合语义及模板版本。
7. 每种节点配置 `retry`、`timeout`、`error_policy` 必须可解析并校验边界；人工审批不使用普通 Worker 重试。
8. 对存在副作用节点标注 `reusable=false` 或明确专有重用策略。

## 4. 四层状态机——规范矩阵

以下“终态”只允许通过创建**新运行或新修订**重做，不允许原地复活。新增状态必须同时升级 Go 枚举、数据库 CHECK、事件版本和测试。

### 4.1 WorkflowRun 状态

| From | To | 命令/条件 | 操作权限 |
|---|---|---|---|
| CREATED | RUNNING | 初始化成功、StartRun | 引擎 |
| CREATED | CANCELING | CancelRun | 授权用户/系统 |
| RUNNING | WAITING | 所有可继续执行路径均等待人工/外部事件，且无 RUNNING/READY 必需工作 | 引擎 |
| WAITING | RUNNING | 必要事件到达后具备可执行节点 | 引擎 |
| RUNNING / WAITING | PAUSED | PauseRun 到达安全暂停点；未完成执行可按策略结束 | 引擎 |
| PAUSED | RUNNING / WAITING | ResumeRun 并重新评估可运行条件 | 引擎 |
| RUNNING / WAITING / PAUSED | CANCELING | RequestCancel | 授权用户/系统 |
| CANCELING | CANCELED | 必要取消协调完成；迟到结果已隔离 | 引擎 |
| RUNNING / WAITING | SUCCEEDED | 全部必要路径结束且 required outputs 验证通过 | 引擎 |
| RUNNING / WAITING | FAILED | 不可恢复的必要节点失败或不可满足的输出 | 引擎 |
| CREATED | FAILED | 初始化不可恢复错误（允许时） | 引擎 |

`PAUSED` 是运行级暂停状态（单状态模型），其语义是**禁止激活/分发新的工作**；已经领取的 Task 可能运行到安全边界。进入 PAUSED 前的收敛规则应由 Pause Coordinator 决定，不能仅靠修改 run.status。必要时下一版本引入 `PAUSING`，但当前使用“请求标志 + 收敛后 PAUSED”策略；实现中单独保存 `pause_requested_at`，数据库需追加该字段。

### 4.2 NodeRun 状态

| From | To | 条件 |
|---|---|---|
| PENDING | READY | 必需依赖满足、Run 可执行、条件/Join 判断成功 |
| PENDING | SKIPPED | 分支明确未选择或容许性跳过 |
| PENDING | BLOCKED | 不可满足的必需前置结果 |
| PENDING / READY | CANCELED | 运行取消且节点无有效任务 |
| READY | RUNNING | 开始执行或创建被接受的 Task |
| READY | WAITING | 审批/外部事件节点等待 |
| RUNNING | WAITING | 等待人工/外部完成事件的节点（需具备类型许可） |
| WAITING | RUNNING | 接收到合法审批/回调、需继续任务 |
| READY / RUNNING / WAITING | SUCCEEDED | 输出契约满足、所需 Task/审批完成 |
| RUNNING / WAITING / READY | FAILED | 不可恢复的节点错误 |
| RUNNING / WAITING / READY | CANCELED | 取消生效且协调完成 |
| READY | SKIPPED | 条件判定尚未产生副作用且选择不执行 |

`SKIPPED`、`BLOCKED`、`SUCCEEDED`、`FAILED`、`CANCELED` 为 NodeRun 终态。禁止 `BLOCKED -> READY`：恢复需创建新的修订运行。实现可将 `BLOCKED` 作为节点失败类最终状态；它本身不代表工作流一定 FAILED，仍取决于下游策略与 required outputs。

### 4.3 Task 状态（与 DDD/Database 保持一致）

| From | To | 执行方 |
|---|---|---|
| PENDING | READY / CANCELED | 进度协调器 |
| READY | QUEUED / CANCELED | Scheduler / Cancel |
| QUEUED | RUNNING / READY / CANCELED | Claim / Recovery / Cancel |
| RUNNING | SUCCEEDED / RETRY_WAIT / FAILED / CANCELED | Completion / Recovery / Cancel |
| RETRY_WAIT | READY / FAILED / CANCELED | Retry Timer / Cancel |

Task `SUCCEEDED`、`FAILED`、`CANCELED` 为终态；超时由 Attempt 表达，再按重试策略转移 Task。任务已经 RUNNING 但需要取消时必须先使旧租约失效，再在 Task 终态落库，不能先凭用户操作假装外部调用已停止。

### 4.4 TaskAttempt 状态

| From | To | 语义 |
|---|---|---|
| CREATED | RUNNING | Worker 确认开始处理 |
| CREATED / RUNNING | SUCCEEDED | 结果清单被服务端有效提交 |
| CREATED / RUNNING | FAILED | 确认错误且本次尝试结束 |
| CREATED / RUNNING | TIMED_OUT | 执行超时策略触发 |
| CREATED / RUNNING | ABANDONED | 租约失效/会话退出且完成权限被撤销 |

终态 Attempt 不可变。`SUCCEEDED` 与 Task `SUCCEEDED` 的原子确认必须在同一受控事务中完成。

## 5. DAG 依赖语义（必须可复算）

### 5.1 依赖的三值结果

每条实际边解析为：`SATISFIED`（满足）、`RESOLVED_NOT_SELECTED`（条件不选择）、`IMPOSSIBLE`（必要数据不可得到）；未结束则为 `UNRESOLVED`。不可把所有前置终态都当作成功，也不能把条件未选中当作永久 Pending。

**关键区别**：`node_dependency_satisfactions` 现有表仅表达 SATISFIED；**需要扩展独立依赖决议存储**以持久化未选中/失败结果，例如增加 `outcome` 列的 `node_dependency_resolutions`，以 `(target_node_run_id, dependency_key)` 唯一。原表可以迁移到该结构，不能对同一边同时维护两份互相矛盾的事实来源。Database v1.0 对此属于需要实施前同步修订的条目。

### 5.2 Join 语义

| 策略 | 可成功条件 | 可以判定失败的条件 |
|---|---|---|
| all_success | 所有被选中的必需依赖均 SATISFIED；未选中按节点声明处理 | 任一必需依赖 IMPOSSIBLE |
| all_done | 全部适用依赖已经终结；容忍失败值必须在输出类型中体现 | 某必需输入无法表达失败占位 |
| any_success | 至少一个成功依赖 | 所有可能依赖终结且均不成功 |
| quorum(k) | 成功计数 >= k | 成功计数 + 未决计数 < k |

针对 `any_success` 和 `quorum`：一旦达到成功条件，剩余尚未结束的前置节点可能继续执行，但不能在结果已最终确认后重新改写已冻结的 Join 输出。需要指定确定性赢家选择（例如按 dependency_key 排序）并明确是否等待已就绪竞争者；**默认**选择首次事务提交达到阈值时冻结的依赖集合，审计保存被选项，不能承诺跨并发执行完全相同赢家。

### 5.3 幂等依赖决议

`(target_node_run_id, dependency_key)` 唯一，只有首次成功插入决议的事务才可改变剩余依赖视图；如果同一 key 携带不同结果，标记为冲突并报警，不能静默覆盖。剩余计数属于可重建投影，定期基于决议表核对。

### 5.4 死路检测

如果所有可达生产者已达终态且某必需输出仍无法满足：沿依赖传递 `IMPOSSIBLE`，将受影响节点 BLOCKED；当确定 required output 不可能实现时 Run FAILED。不能让 Run 永久停留 RUNNING 而没有可执行节点。

## 6. 编译与运行实例化

发布时：`ValidateSchema -> CheckPorts -> CheckPolicy -> CycleDetection -> CompileGraph -> Hash -> PublishImmutableVersion`。

启动事务：

1. 校验 `WorkflowVersion` 已发布、租户权限与输入 schema。
2. 在固定工作流定义和输入快照下创建 `WorkflowRun(CREATED)`。
3. 实例化静态根节点及必要 NodeRun（也可按需实例化后继，但须保证 deterministic reconstruction）。
4. 校验根节点就绪并将其 READY；运行转 RUNNING。
5. 为可执行根节点创建 Task，并写 Outbox，提交。

动态展开事务：先固定 `collection_ref + fingerprint + child_template_version`，校验 `item_key` 唯一、类型正确、元素数不超阈值；按稳定 expansion_key 逐个 `INSERT ... ON CONFLICT`；生成映射和汇合关系；最后原子标记展开完成。高规模展开使用批量事务 + `expansion_progress` 持久化游标；**在汇合前必须验证全部元素实例化完成**。不能把 map 读取结果依赖于可变的当前分镜列表。

## 7. 输入绑定、节点输出与缓存

- NodeRun 第一次激活时将输入引用解析为固定输入快照；记录 `source AssetVersionID` 而不是当前资产的可变指针。
- 输出验证分为结构校验（schema）、授权校验、内容可用性校验；任务 Handler 不可直接更改 NodeRun 状态。
- 大文件只通过对象引用；数据库避免写大块二进制。
- 结果重用键应包含：节点定义版本、输入指纹、模型/处理器配置版本及租户作用域；随机生成或外部副作用节点默认不缓存。
- 成功输出发布为不可变结果引用；用户修改创作输入时创建新的运行修订，不修改历史 Run。

## 8. 核心事务和并发时序

### TX-WF-01：启动运行

事务内插入 Run / 根 NodeRun / 初始 Task / Outbox，Run 状态与初始可执行路径一致提交；请求层支持幂等键，重复调用命中原 Run。

### TX-WF-02：完成 Task 并推进节点

**不要把“Worker 回报完成”直接翻译为节点 SUCCEEDED。**

1. Asset Service 检验暂存结果并准备稳定引用。
2. `BEGIN`；锁定 Task，验证 `current_attempt_id`、`lease_epoch`、服务器时间下租约有效、Run 未取消；确认结果清单符合声明的 Task 输出。
3. 在事务中更新 Attempt/Task SUCCEEDED，绑定正式 ResultRef、必要的资产元数据，写 `TaskSucceeded` Outbox。
4. 若节点需要多个 Task，更新 NodeRun 对应的任务结果集合；只有所有必需 Task 已确认后进行 NodeRun 输出校验。
5. NodeRun 以 CAS 从 RUNNING 更新为 SUCCEEDED，写 NodeCompleted 事件/Outbox。
6. 锁定后继 NodeRun（按稳定 ID 排序），为每条实际边写唯一依赖决议；仅首个决议使投影变化。
7. 根据 Join 决议使后继 READY / SKIPPED / BLOCKED，创建唯一 Task 请求及 Outbox；可能满足运行完成判据时校验 required outputs 再终结 Run。
8. `COMMIT`；事务失败可由重放 TaskSucceeded/节点推进对账恢复。若全流程单事务体量不可控，拆成“TaskCommit 事务 + Progression 事务”，必须依靠 Outbox 和幂等状态机最终推进，不能存在无恢复路径的中间状态。

**锁次序要求**：数据库已有 TX-04 以 Task 锁为入口，而依赖推进可能先锁 NodeRun；实现必须统一同一类事务的实际锁序以防死锁。推荐 TaskCommit 与 Progression 两阶段事务解耦：前者锁 Task/Attempt，后者按 `WorkflowRun -> NodeRun ID 升序 -> Task ID 升序` 锁定；进度推进读取已确认 Task 结果，禁止反向回锁任务。以此作为后续实现默认基线。

### TX-WF-03：节点决议推进（重复事件安全）

```text
BEGIN
  lock WorkflowRun (for cancellation/terminal gate)
  lock target NodeRun (stable order)
  INSERT dependency_resolution ... ON CONFLICT DO NOTHING
  if conflict: compare existing outcome; same => no-op; different => error
  recompute join from durable resolutions and edge declarations
  CAS NodeRun PENDING -> READY/SKIPPED/BLOCKED
  when READY create unique Task(s) and corresponding outbox event(s)
  maybe recompute Run terminal condition
COMMIT
```

`UNIQUE(target_node_run_id, dependency_key)` 与 `UNIQUE(node_run_id, logical_task_key)`（若一个 NodeRun 可能多任务）是关键约束。**现有 Database v1.0 尚未定义 logical_task_key；必须同步增加，不能用仅 TaskID 去重。**

### TX-WF-04：取消

设置 Run `CANCELING` 和取消时间；原子停止激活新节点、撤销尚未运行 Task、向 RUNNING Task 发出取消命令；外部执行可能无法立即结束。到达终止条件后 Run CANCELED。Task 的租约完成权必须在取消提交点被撤销或相应的提交结果拒绝；迟到 Asset 保留为待清理孤儿。取消重试幂等。

### TX-WF-05：暂停/恢复

`pause_requested_at` 记录意图，Scheduler 在调度时读取允许状态；运行中任务根据策略运行到安全点；停止新任务后转 PAUSED。Resume 重新计算可执行 NodeRun 和 Task，不通过重写终态恢复。暂停不是完成/失败终态。

## 9. 错误与重试传播

错误分类必须保留结构化 `code`、`retryable`、`origin`、`attempt_id` 和脱敏信息。

- **尝试失败**：根据 RetryPolicy 判断重新进入 Task `RETRY_WAIT`，或 Task `FAILED`。
- **Task 最终失败**：由 NodeRun 汇总策略决定节点 `FAILED`、提供声明的降级结果、或跳过（需允许的 `on_error`）。
- **节点失败**：对必需依赖传播 IMPOSSIBLE；非必需分支可以由 Join 显式容忍。
- **运行失败**：仅在无法实现 required outputs 或命中显式 fail-fast 策略时终结；非关键分支失败不一定导致 Run FAILED。
- **Retry timer**：检查 `next_run_at <= DB server time` 后把 Task `RETRY_WAIT -> READY` 并写 Outbox；重复触发无副作用。
- **租约超时**：Task Execution 先撤销旧 Attempt 授权，再根据重试预算安排新 Attempt；不得由 Workflow Engine 自行分配 Worker。

## 10. 人工审批与外部事件

审批 NodeRun WAITING 期间必须保存 `approval_id`、允许的 actor/role、请求版本、超时截止、决议和审计信息。审批命令使用 `expected_version` CAS；同一审批重复提交相同决议返回既有结果，冲突决议返回冲突错误。

Webhook / 外部回调需认证、签名验证、事件去重和关联 ID 检查。未知或过期回调不可使终态节点复活。

等待时的 Run 可以处于 WAITING，但只要其他分支仍有可执行任务，就应保持 RUNNING；WAITING 是“整体没有可推进工作且等待合法外部信号”的聚合视图。

## 11. 局部重跑与变更影响分析

- 提供 `CreateRevisionRun(parent_run_id, changed_inputs, reuse_policy)`；新 Run 引用原运行和差异元数据，原运行不修改。
- 计算失效闭包：发生变化的节点向后遍历影响的依赖边，结合端口级输入差异和缓存策略确定实际需要重新执行的 NodeRun。
- 优先复用已确认、输入/模型配置匹配且授权范围允许的 AssetVersion。
- 复用结果应记录 `origin_run_id`、`origin_node_run_id`、`origin_output_ref`，审计可以解释哪些节点未重新计算。
- 当 Composition 引用了变化素材，即使渲染节点不需要重新生成全部场景，最终输出通常仍需重新合成。
- 不允许旧运行复用引用当前可变对象的隐式快照。

## 12. 并发安全、重启恢复与对账

**必须保证**：

1. 相同节点终态事件重复到达只解析一次；依赖决议唯一。
2. 两个来源并发完成，Join 激活仅一次。
3. 旧 Worker 迟到结果由 Task Execution 的 LeaseEpoch + Attempt 校验拒绝。
4. WorkflowRun SUCCEEDED 前确认全部必需输出且 OutputRef 可读取。
5. Scheduler/引擎重启后通过 DB 重建 Ready 投影，消息队列丢通知不丢任务。
6. Reconciler 扫描超时、卡住或事件中断的 NodeRun/Run，按确定规则修复投影；异常冲突进入死信诊断和审计，不强行覆盖。

推荐恢复任务：

| 检查 | 检测 | 操作 |
|---|---|---|
| READY NodeRun 没有 Task | 满足依赖但未创建任务 | 幂等补建唯一 Task 和 Outbox |
| NodeRun RUNNING、全部 Task 已成功 | 进度未确认 | 重放输出验证及 NodeComplete |
| PENDING 且依赖全终结 | join 尚未决议 | 重新计算并解析为 READY/SKIPPED/BLOCKED |
| Run 无活动任务且无等待条件 | 僵尸 Run | 根据 required outputs 完成或失败 |
| 待审批节点超时 | `deadline <= now()` | 按审批超时策略终结 |
| Outbox 未确认 | 超过发送延迟目标 | 重新发布，消费者幂等 |
| 暂存资产无人引用 | 超出保留时间 | 按 Asset 清理策略回收 |

引擎进度事件和任务事件应带 `event_id`、`workflow_run_id`、`node_run_id`、`aggregate_version`、`causation_id`，避免日志推断关联关系。

## 13. Go 领域与应用接口草案

```go
// 领域层不得直接依赖 SQL/Redis/HTTP。
type DefinitionCompiler interface {
    Compile(ctx context.Context, definition WorkflowVersion) (CompiledGraph, error)
}

type WorkflowCommands interface {
    StartRun(ctx context.Context, cmd StartRunCommand) (WorkflowRunID, error)
    RequestPause(ctx context.Context, cmd PauseRunCommand) error
    Resume(ctx context.Context, cmd ResumeRunCommand) error
    RequestCancel(ctx context.Context, cmd CancelRunCommand) error
    CreateRevision(ctx context.Context, cmd RevisionCommand) (WorkflowRunID, error)

type WorkflowProgression interface {
    OnTaskCommitted(ctx context.Context, event TaskCommittedEvent) error
    ResolveDependency(ctx context.Context, cmd ResolveDependencyCommand) error
    ReconcileRun(ctx context.Context, runID WorkflowRunID) error
}

// Task 提交通过 Task Application Service；Workflow Engine 只消费已确认事实。
type TaskExecutionPort interface {
    CreateReadyTasks(ctx context.Context, commands []CreateTaskCommand) error
    RequestCancellation(ctx context.Context, taskIDs []TaskID) error
    ListNodeTaskResults(ctx context.Context, nodeRunID NodeRunID) ([]TaskResult, error)

```

事务协调由 Application Service 实现；以上接口跨模块调用时需要明确同库事务上下文或事件命令边界，**不可在一事务内调用外部网络 RPC 并等待其成功**。

## 14. 必需数据库变更对照表（相对 Database v1.0）

## 17. 未决问题与决策冻结点

1. `all_done` 是否允许输出失败占位：需明确端口类型和具体输出 schema。
2. 动态分支 `any_success` 是否采用“首个有效提交获胜”：本版默认采用，若产品要求结果确定性需改为固定优先级等待规则。
3. 父/子 WorkflowRun 的取消与审批传播规则：子工作流功能开发前冻结。
4. 所有状态推进是否统一拆成 TaskCommit 和 Progression 两事务：本版推荐分拆以减少死锁和事务时长；在代码实现前验证锁序。
5. 大规模 map 展开最大数量、事务批次和运行级并发：需要容量测试设定，不在此文档虚构性能阈值。
6. 处理已发生第三方计费但无回执的外部 Job：由 Model Gateway 定义查询/重试语义，不承诺 exactly-once 外部调用。

**设计判定**：上述未决问题不得被静默解释为实现完成；适用功能编码前应形成 ADR 或更新规范。文档的状态转换是架构契约，任何例外必须通过正式变更同步 DDD、Database、API 与测试。
