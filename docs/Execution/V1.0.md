# MediaFlow 核心执行协议与一致性设计（Execution v1.0）

> 状态：**整合候选稿，待实施评审**；日期：2026-10-20  
> 依据：`DDD/V1.0.md`、`Database/V1.0.md`、`Workflow/V1.0.md`、`Scheduler/V1.0.md`、`Worker/V1.0.md`。  
> 配套：`Database/V1.1.md`；此文件优先约束**跨模块执行协议**，各业务模块文档继续约束本模块内部逻辑。  
> 范围：核心任务执行协议、状态所有权、原子操作、持久化契约、异常恢复。不是已验证的生产实现。

## 1. 整合决策摘要

| ID | 争议或遗漏 | 统一决定 | 影响 |
|---|---|---|---|
| EX-01 | `Task` 完成时是否直接推进 DAG | **分两次事务**：先 `ResultCommit` 原子确认 Task/Attempt/资产引用/资源释放/Outbox；再由 Workflow Progression 消费事件推进 NodeRun/依赖。 | Workflow §8、Scheduler §8、Worker §5 |
| EX-02 | Claim 后由谁创建 Attempt | **Scheduler 控制面的 ClaimService** 在一个事务内完成 Task Claim、Attempt、租约和资源预留；Worker 只能凭授权执行。 | Scheduler §7、Worker §5 |
| EX-03 | Task `READY` vs `QUEUED` | `READY` 为权威可调度状态；`QUEUED` 为**可选的持久化分发状态**。首个实施切片允许 `READY→RUNNING` 的原子 Claim；使用 `QUEUED` 时必须保障 `QUEUED→READY` 恢复。 | Workflow §4、Database §7 |
| EX-04 | 结果有效性的判据 | 当前 `(task_id,current_attempt_id,lease_epoch,token_hash,worker_session_id,lease_expires_at)` 在 DB 时钟下校验；结果提交必须 CAS/行锁；旧 Attempt 无提交权。 | 三模块 |
| EX-05 | DAG 依赖只有 satisfied | 使用**依赖决议**：`SATISFIED / NOT_SELECTED / IMPOSSIBLE`，每条实际边只决议一次；保留追溯来源版本。 | Workflow §5、Database §6 |
| EX-06 | 资源预留表名重复 | 统一 `resource_reservations`；废弃草案名 `scheduler_reservations`。容量账本统一 `resource_pool_counters`，支持原子槽位预留；多维资源另行扩展。 | Scheduler §2、Database §8 |
| EX-07 | 动态节点及任务去重 | `UNIQUE(workflow_run_id,node_definition_id,expansion_key)` 和 `UNIQUE(node_run_id,logical_task_key)`；`logical_task_key NOT NULL`（新建表）；展开决议持久化。 | Workflow §6、Database §7 |
| EX-08 | Worker 远程异步 Job | 外部 Job **不是** TaskAttempt 的隐式替代；保存 `external_model_jobs`，区分 `SUBMITTED/PROCESSING/UNKNOWN` 等状态；长等待不占用 CPU worker 槽。 | Worker §8 |
| EX-09 | 重复结果 | `attempt_result_submissions` 按 `(attempt_id,submission_key)` 去重，结果摘要冲突返回错误；只有第一次合法事务会确定 Task 结果。 | Worker §10 |
| EX-10 | Pause/Cancel | 请求意图持久化；暂停阻止**新 Claim**，存量 Attempt 按策略收敛；取消需要撤销授权、收敛并明确远端调用不可撤销情况。 | Workflow §4、Worker §11 |
| EX-11 | 工作流回放 | 重做产生**新 WorkflowRun/revision**，不将 SUCCEEDED/FAILED 终态复活。 | Workflow §11 |
| EX-12 | 租约回收 vs 状态转换 | Reconciler 是受控 TaskExecution 命令的调用方，不直接修改其他模块表；结束旧 Attempt 与释放 Reservation 必须幂等。 | Scheduler §8、Worker §6 |

## 2. 权责矩阵

| 动作 | 唯一业务所有者 | 调用发起方 | 可修改的权威对象 |
|---|---|---|---|
| 发布工作流 | WorkflowDefinition | 用户/API | WorkflowVersion |
| 创建运行 | WorkflowExecution | API/业务事件 | WorkflowRun、初始 NodeRun、Outbox |
| 依赖决议/创建逻辑任务 | WorkflowExecution | Progression | DependencyDecision、NodeRun、Task、Outbox |
| Task Claim/租约续期 | TaskExecution ClaimService，Scheduler 选择候选 | Scheduler/Worker | Task、TaskAttempt、Reservation、资源账本 |
| 外部执行 | Worker Runtime | Worker | 不直接修改数据库执行权威记录 |
| 产物预登记/结果提交 | TaskExecution + Asset 应用服务 | Worker | ResultSubmission、AssetVersion 引用、Task/Attempt、Reservation、Outbox |
| 失败、超时与回收 | TaskExecution | Worker/定时器/Reconciler | Task/Attempt、Reservation、Outbox |
| Workflow 最终判定 | WorkflowExecution | Progression | NodeRun、WorkflowRun、Outbox |

不允许 Worker 修改 NodeRun/WorkflowRun；不允许 Scheduler 解析 DAG；不允许 Workflow Engine 私自授予 Lease。各控制面应用服务可共享同一个受控 PostgreSQL 事务，但领域所有权不能因此模糊。

## 3. 状态转换矩阵与边界

### 3.1 WorkflowRun

- `CREATED→RUNNING|CANCELING|FAILED`（初始化失败场景）。
- `RUNNING→WAITING|PAUSED|CANCELING|SUCCEEDED|FAILED`。
- `WAITING→RUNNING|PAUSED|CANCELING|SUCCEEDED|FAILED`。
- `PAUSED→RUNNING|WAITING|CANCELING`。
- `CANCELING→CANCELED`。
- `CANCELED|SUCCEEDED|FAILED` 为终态。
- 新增 `pause_requested_at`、`cancel_requested_at`；请求不意味着状态立刻改变。暂停收敛可继续使用 `RUNNING + pause_requested_at`；进入 `PAUSED` 前必须定义现有 Attempt 的处理策略。

### 3.2 NodeRun

- `PENDING→READY|SKIPPED|BLOCKED|CANCELED`。
- `READY→RUNNING|WAITING|SUCCEEDED|FAILED|SKIPPED|CANCELED`。
- `RUNNING→WAITING|SUCCEEDED|FAILED|CANCELED`。
- `WAITING→RUNNING|SUCCEEDED|FAILED|CANCELED`。
- `SUCCEEDED|FAILED|SKIPPED|BLOCKED|CANCELED` 为终态。节点完成必须结合节点类型、Join 策略和实际输出校验。

### 3.3 Task

- `PENDING→READY|CANCELED`。
- `READY→QUEUED|RUNNING|CANCELED`（`READY→RUNNING` 仅由原子 Claim 发起）。
- `QUEUED→RUNNING|READY|CANCELED`。
- `RUNNING→SUCCEEDED|RETRY_WAIT|FAILED|CANCELED`。
- `RETRY_WAIT→READY|FAILED|CANCELED`。
- `SUCCEEDED|FAILED|CANCELED` 不回退。

### 3.4 TaskAttempt

- `CREATED→RUNNING|FAILED|TIMED_OUT|ABANDONED`。
- `RUNNING→SUCCEEDED|FAILED|TIMED_OUT|ABANDONED`。
- `SUCCEEDED|FAILED|TIMED_OUT|ABANDONED` 为终态。
- 同一 Task 最多一个 `CREATED/RUNNING` Attempt；Claim 新 Attempt 前必须先收敛旧 Attempt。

### 3.5 跨层约束

- `Task.SUCCEEDED` 与其有效 `Attempt.SUCCEEDED` 同一事务确认。
- Task 完成事件**不等同于** NodeRun 完成，且允许重复消费。
- NodeRun 只有在所有必要子 Task、审批和输出条件满足时才完成。
- WorkflowRun 的完成需要 `required outputs` 验证及必要路径终结。

## 4. 核心消息和 API 协议

版本号 `protocol_version=1`，所有请求传递 `correlation_id`；鉴权凭证和 Lease Token 不进入日志。

**TaskEnvelope（下发）：** `protocol_version,task_id,attempt_id,attempt_no,lease_epoch,lease_token,lease_expires_at,worker_session_id,task_type,capability,input_ref,input_schema_version,resource_limits,timeout_at,correlation_id`。

**Renew（请求）：** `task_id,attempt_id,lease_epoch,lease_token,worker_session_id,requested_ttl`；成功返回新的服务器时间和租约到期时间；重复请求不能缩短租约。

**ResultManifest：** `schema_version,task_id,attempt_id,lease_epoch,submission_key,artifacts[{staging_key,content_hash,size,mime_type}],output_json,external_job_ref(optional)`。

**Complete（请求）：** TaskEnvelope 授权五元组 + `submission_key` + `manifest_hash` + `manifest`。服务端成功返回 `committed_result_ref` 与 `task_status`；重复同内容返回已提交结果；不同内容冲突。

**Fail（请求）：** 授权信息 + `error_code,retryable,error_details_ref`；自动重试由控制面根据 Policy 判断，Worker 不直接变更 Task 状态。

**统一错误语义：** `UNAUTHORIZED`, `LEASE_LOST`, `ALREADY_COMMITTED`, `RESULT_CONFLICT`, `TASK_NOT_RUNNABLE`, `QUOTA_DENIED`, `RETRY_LATER`, `INVALID_OUTPUT`, `TRANSIENT_FAILURE`。客户端按错误类型决定停止执行/查询结果/回退重试。

## 5. 五个关键数据库事务

### TX-01 StartWorkflow

`BEGIN` → 验证 WorkflowVersion/输入快照/权限 → 创建 WorkflowRun、初始 NodeRun 与初始依赖记录 → Outbox(RunStarted/NodeReady) → `COMMIT`。同一外部请求使用 scope + idempotency key 防止重复创建。

### TX-02 ResolveDependency + CreateTask

`BEGIN` → 锁定目标 NodeRun（明确锁顺序） → 插入 `(target_node_run_id,dependency_key)` 唯一决议记录 → 若已存在且相同则 no-op，若存在冲突决议则报警/拒绝 → 根据 Join 策略（含不可满足判断）确定 `READY/SKIPPED/BLOCKED` → 对可执行节点创建唯一 `(node_run_id,logical_task_key)` Task → Outbox(TaskReady) → `COMMIT`。

### TX-03 ClaimAndReserve（执行权线性化点）

`BEGIN` → 按稳定顺序锁 Workspace/Run 可执行许可、Task、WorkerSession、ResourcePoolCounters、配额账户 → 校验 `READY|QUEUED`、`next_run_at`、用户暂停/取消意图、资源/配额 → 条件预留资源 → 插入 `Attempt(CREATED, lease_epoch=old+1, token_hash, expiry)` → 更新 Task `RUNNING,current_attempt_id,lease_epoch,attempt_count,lock_version` → Outbox(TaskClaimed) → `COMMIT` → 将授权返回 Worker。

锁序不能在所有事务中任意改变。所有涉及多个资源池的事务按 `pool_id` 排序；后续 SQL 实现需要有统一锁序审查。**严禁在事务中调用 AI、FFmpeg、对象存储。**

### TX-04 RenewLease

`BEGIN` → 锁 Task 及当前 Attempt → 使用 DB 时钟验证当前 `AttemptID/epoch/token_hash/session`、任务 `RUNNING`、租约尚有效、Session/取消许可 → 到期时间更新为 `GREATEST(existing_expiry, db_now + ttl)` → `COMMIT`。Lease 丢失返回 `LEASE_LOST`，Worker 必须停止结果提交尝试。

### TX-05 ResultCommit（结果接受线性化点）

前置阶段在事务外：上传暂存对象、校验文件大小/散列与可访问性、生成 ResultManifest。正式事务：锁定 Task/Attempt → 校验有效授权、结果摘要、预算与产物引用 → 幂等插入提交记录 → 登记稳定 AssetVersion/结果引用 → `Attempt.SUCCEEDED,Task.SUCCEEDED` → 释放本 Attempt ACTIVE 资源预留并更新容量账本 → Outbox(TaskSucceeded) → `COMMIT`。

**资产要点：** DB 事务无法原子提交 S3。事务前必须保证持久对象可访问，若对象键由暂存转正式存储，则先完成持久复制/验证，再开始 DB 提交；孤儿对象通过 GC 清理。不可在数据库事务提交后才以尚未完成的复制作为资产存在性前提。

### TX-06 WorkflowProgression（独立事务）

从 Inbox 去重消费 TaskSucceeded → 锁 NodeRun，检查其任务集合的逻辑完成条件 → 写 NodeRun 输出/状态和 Outbox(NodeSucceeded) → 决议下游边与创建下游 READY Task → 评估 WorkflowRun 完成条件 → `COMMIT`。可按 NodeRun 并发分批事务推进，确保事件最终可重放。

## 6. 失败与恢复

| 故障窗口 | 可恢复事实 | 恢复策略 |
|---|---|---|
| Claim DB Commit 前失败 | 无有效 Attempt | 回滚后重试 Claim |
| Claim 成功但授权响应丢失 | 当前 Attempt/Lease 已持久化 | Worker 带 request id 查询 Claim 结果；过期后回收 |
| 上传完成但 Commit 未执行 | 已暂存/持久对象，Task 未成功 | 查询 submission；合法租约内重提交，否则按策略重试与 GC |
| Commit DB 成功但 HTTP 响应丢失 | Task/Attempt 与 submission 已成功 | 相同 submission 返回原结果 |
| Outbox 发布丢失/重复 | DB Outbox 为事实 | 重发，Inbox 幂等消费 |
| Worker 崩溃 | Attempt Lease 过期 | 收敛 Attempt，释放预留，Task→RETRY_WAIT/FAILED |
| Run 取消与 Claim 并发 | Run 禁止执行标记已提交 | Claim 使用相同锁协议串行化；取消按策略撤销已有授权 |
| 旧 Worker 恢复提交 | epoch/token/current_attempt 不匹配 | 拒绝，暂存对象待 GC |
| Provider 异步 Job 状态未知 | 持久化 external_job_id | 先查询 Provider，避免盲目再次提交可能收费请求 |

Reconciler 核对 `READY/QUEUED`、活跃租约、预约账本、未消费 Outbox、待提交产物、动态展开状态；所有修复命令幂等并可审计。

## 7. 暂停、取消、局部重跑

- `pause_requested_at` 是调度禁入意图；新 Claim 检查该字段，已运行任务按规定收敛，收敛后 Run→PAUSED。
- `cancel_requested_at` 触发禁止新 Claim、撤销有效租约、传播取消。对于无法撤销的外部 API，只能标记结果不被采纳；仍需记录成本。
- `CANCELING→CANCELED` 必须有明确收敛条件，不能仅因客户端点击取消直接完成。
- 局部修改使用新修订运行，旧运行不回退；资产版本引用保持有效。

## 8. Provider 异步执行特别约定

外部提交与内部资源占用分开：持久保存 `external_model_jobs`，使用 `SUBMITTED/PROCESSING/SUCCEEDED/FAILED/CANCELED/UNKNOWN`。提交或轮询可以由短任务承担；漫长等待时释放 CPU/Worker 执行槽。外部 Job 的回调/轮询应通过唯一 Provider Job 身份去重。外部任务完成的结果需以新的有效 TaskAttempt 或明确的受控外部事件决议进入 ResultCommit，**不能使用已经到期的原 Lease 提交**。详细的 Resume/Callback 原子协议需要在 Worker/API 实现前冻结。

## 9. 编码前强制校验项

1. 字段与状态名完全对齐 `Database/V1.1.md`，不得让同概念出现两个表名。
2. `TaskClaim` 的资源预留和 Attempt 在同一数据库事务内提交。
3. `ResultCommit` 不混入外部 IO，也不在同事务内遍历整张 DAG。
4. 引擎只消费 Task 已确认事件；同一 Task 事件重复任意次数结果一致。
5. 通过同 Run 复合外键保证源/目标依赖归属一致。
6. 跨租户关联采用组合 FK 或应用服务强校验，严格测试越权。
7. 用真实 PostgreSQL 并发集成测试验证每个状态转换和锁序。
8. 草案未冻结部分（动态 Join、异步 Job 恢复策略、预算预扣方式）应写 ADR 才进入对应代码。

## 10. 最小自动化验收矩阵

| ID | 场景 | 期望 |
|---|---|---|
| EX-T01 | 2 Scheduler 并发 Claim 同 Task | 仅一个当前 Attempt/Lease |
| EX-T02 | Claim 资源不足 | Task/Attempt/Reservation 都不发生部分提交 |
| EX-T03 | Claim 响应丢失 | 查询已有授权或租约回收，无永久悬挂 |
| EX-T04 | Commit 响应丢失后重试 | 相同 manifest 返回同一有效结果 |
| EX-T05 | 相同 submission key 不同 manifest | RESULT_CONFLICT |
| EX-T06 | 旧 epoch 提交 | LEASE_LOST，旧结果不覆盖 |
| EX-T07 | Source 事件重复 | 一条 DependencyDecision，不重复建立 Task |
| EX-T08 | `NOT_SELECTED` 分支 | 下游按 Join 规则 SKIPPED/READY，无错误启动 |
| EX-T09 | 一个必要分支失败 | 后继 BLOCKED，Run 按 required output 策略终结 |
| EX-T10 | Outbox 重复投递 | Inbox 幂等处理，状态相同 |
| EX-T11 | 取消与 Claim 并发 | 取消后不产生新有效执行授权 |
| EX-T12 | DB 提交前对象校验失败 | Task 不 SUCCEEDED，不引用无效资产 |
| EX-T13 | 租约过期回收 | 资源仅释放一次，可安全生成新 Attempt |
| EX-T14 | 暂停中触发任务就绪 | 不能被 Claim，恢复后继续执行 |
| EX-T15 | Provider UNKNOWN | 查询/人工决议，不无界重复远程收费调用 |
