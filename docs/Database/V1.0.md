## 0. 本文的性质与交付界限

本文件是**领域聚合到 PostgreSQL 的逻辑/物理映射与关键事务设计**。它提供核心表的可实施 DDL 样例、约束、索引、并发 SQL、失败恢复约定以及验收矩阵。示例 SQL 是设计模板，**不是已经在项目数据库运行通过的完整 migration 包**；须拆分、排序并执行集成测试后才能作为生产迁移。

**设计假设（需要项目确认）：** 第一阶段使用单个 PostgreSQL 数据库，按模块归属表，暂不分库；Go 服务使用一个受控的 Unit of Work 协调跨模块事务；ID 使用由应用生成的 UUID（v4 或 v7 均可，须统一）；所有时间持久化为 `timestamptz`，计费精度为 `numeric`；对象内容存 S3 兼容存储，数据库仅持有稳定引用。SQL 示例使用 `gen_random_uuid()` 作为可选服务端默认生成方式。

### 0.1 设计目标

1. 维护 DDD 聚合根的所有权、版本及强一致边界。
2. 用 `PRIMARY KEY`、`FOREIGN KEY`、`UNIQUE`、`CHECK`、部分唯一索引保证可声明的不变量。
3. 用乐观锁与原子 SQL 解决并发修改；用短事务行锁处理任务领取。
4. 明确 WorkflowRun、NodeRun、Task、TaskAttempt 间的可恢复状态推进。
5. 对数据库、消息系统、对象存储及外部 AI 调用之间无法原子提交的操作设计补偿与对账。
6. 保留已发布工作流、创作修订、资产版本、交付版本的不可变历史。

### 0.2 规范化约定

- 表/列名：`snake_case`，复数表名；约束名显式命名。
- 主键：`id uuid PRIMARY KEY`；跨模块引用用显式 FK（如需拆库先制定迁移 ADR）。
- `workspace_id` 应出现在租户边界内的主要业务实体，防止错误跨租户关联。
- 聚合根的可变行包含 `lock_version bigint NOT NULL DEFAULT 0 CHECK (lock_version >= 0)`；`revision_no` 和 `version_no` 是**业务版本**，与乐观锁版本完全不同。
- 已发布版本行采用插入式版本化；应用账号应无权 `UPDATE`/`DELETE` 这些历史表，运维修复需受控审批；若需数据库层防护可添加不可变触发器并限制权限。
- `status text` 配 `CHECK` 约束，重要状态推进由应用服务/事务 SQL 检查；CHECK **不能**校验跨行状态转移。
- 高价值结果使用明确外键和唯一约束；`jsonb` 用于可版本化快照、可扩展参数，不用于替代核心关系模型。
- 删除：优先归档、软删除和独立清理；历史引用默认 `ON DELETE RESTRICT/NO ACTION`，不得滥用 `CASCADE`。
- 资金、使用量：计费币种 `char(3)`，金额 `numeric(20,8)`（示例精度，需结合币种和计费单位确认）。

## 1. 领域聚合到数据库的映射

| 限界上下文 | 聚合/实体 | 权威表 | 关键一致性策略 |
|---|---|---|---|
| Identity/Workspace | Workspace、Membership | `workspaces`、`workspace_memberships` | 所属关系唯一；权限在应用层校验 |
| Project | Project | `projects` | `workspace_id` 不可隐式迁移；乐观锁 |
| Creative | Brief/Script/Storyboard + Revisions | `creative_briefs`, `brief_revisions`, `scripts`, `script_revisions`, `storyboards`, `storyboard_revisions`, `storyboard_scenes` | 不可变修订；发布时一致的场景快照 |
| Asset | Asset、AssetVersion、Ingestion | `assets`, `asset_versions`, `asset_ingestions`, `asset_references` | 版本唯一；对象验证先于提交；引用保护 |
| Delivery | Composition/Work | `compositions`, `composition_versions`, `works`, `work_versions` | 输出资产和审核版本明确 |
| Workflow Definition | WorkflowDefinition/Version | `workflow_definitions`, `workflow_versions` | 版本不可变、 `(workflow_id, version_no)` 唯一 |
| Workflow Execution | WorkflowRun、NodeRun、Dependency | `workflow_runs`, `node_runs`, `node_dependency_satisfactions` | 节点独立更新；每个依赖只能满足一次 |
| Task Execution | Task、TaskAttempt | `tasks`, `task_attempts` | 唯一有效 Attempt、递增 lease_epoch、有效结果一次提交 |
| Worker | Worker/Session | `workers`, `worker_sessions` | 新进程新 Session，旧 Session 不具备新执行权 |
| Scheduler/Quota | Pool/Account/Reservation | `resource_pools`, `quota_accounts`, `resource_reservations` | 原子资源预留和释放 |
| Model | Provider/Model Configuration | `provider_configurations`, `model_configurations` | 凭证仅保存引用；使用确定配置快照 |
| Cost | Budget/Usage | `budgets`, `usage_ledger` | 用量不可变、来源事件去重 |
| Reliability | Outbox/Inbox/Idempotency | `outbox_events`, `inbox_receipts`, `idempotency_records` | 事务发布、重复消费保护、重复请求保护 |
| Operations | Audit | `audit_events` | 追加式审计；分级留存 |

**重要区别：** DDD 中 TaskAttempt 由 Task 执行授权规则管控，不要求物理上与 Task 同行存储；NodeRun 独立表与独立 `lock_version` 是为并行节点减少热点，而不是将领域规则下沉给任意消费者。

## 2. 核心身份和租户数据

```sql
CREATE TABLE workspaces (
  id uuid PRIMARY KEY,
  owner_user_id uuid NOT NULL,
  name text NOT NULL CHECK (length(btrim(name)) BETWEEN 1 AND 120),
  status text NOT NULL DEFAULT 'ACTIVE'
    CHECK (status IN ('ACTIVE','SUSPENDED','DELETING')),
  lock_version bigint NOT NULL DEFAULT 0 CHECK (lock_version >= 0),
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now()
);

-- users 表属于认证模块，必须先建立；此处仅示意最小业务身份。
CREATE TABLE users (
  id uuid PRIMARY KEY,
  created_at timestamptz NOT NULL DEFAULT now()
);
ALTER TABLE workspaces ADD CONSTRAINT fk_workspaces_owner
  FOREIGN KEY (owner_user_id) REFERENCES users(id);

CREATE TABLE workspace_memberships (
  workspace_id uuid NOT NULL REFERENCES workspaces(id),
  user_id uuid NOT NULL REFERENCES users(id),
  role text NOT NULL CHECK (role IN ('OWNER','ADMIN','EDITOR','REVIEWER','VIEWER','OPERATOR')),
  status text NOT NULL DEFAULT 'ACTIVE'
    CHECK (status IN ('INVITED','ACTIVE','DISABLED')),
  lock_version bigint NOT NULL DEFAULT 0,
  created_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (workspace_id,user_id)
);

CREATE TABLE projects (
  id uuid PRIMARY KEY,
  workspace_id uuid NOT NULL REFERENCES workspaces(id),
  name text NOT NULL CHECK (length(btrim(name)) BETWEEN 1 AND 200),
  description text,
  defaults jsonb NOT NULL DEFAULT '{}'::jsonb,
  status text NOT NULL DEFAULT 'ACTIVE'
    CHECK (status IN ('ACTIVE','ARCHIVED','DELETING')),
  lock_version bigint NOT NULL DEFAULT 0 CHECK (lock_version >= 0),
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (id,workspace_id)
);
CREATE INDEX ix_projects_workspace_status ON projects(workspace_id,status,created_at DESC);
```

**租户隔离注意：** 单纯 `project_id` FK 并不能证明其他表的 `workspace_id` 与 Project 一致。对同时持有这两个字段的关键表建议用复合外键：`FOREIGN KEY(project_id,workspace_id) REFERENCES projects(id,workspace_id)`；只要 `project_id` 可空，该 FK 不负责空值时的 Workspace 校验。跨空间引用由显式授权表或应用服务批准，不允许通过任意拼接 ID 绕过授权。可在后续启用 PostgreSQL Row Level Security 作为纵深防御，但不能替代服务端鉴权。

## 3. 创作修订持久化

Brief、Script、Storyboard 均采用“可变逻辑根 + 不可变修订”的映射。

```sql
CREATE TABLE creative_briefs (
  id uuid PRIMARY KEY,
  project_id uuid NOT NULL REFERENCES projects(id),
  current_revision_id uuid,
  draft jsonb NOT NULL DEFAULT '{}'::jsonb,
  lock_version bigint NOT NULL DEFAULT 0,
  created_at timestamptz NOT NULL DEFAULT now()
);
CREATE TABLE brief_revisions (
  id uuid PRIMARY KEY,
  brief_id uuid NOT NULL REFERENCES creative_briefs(id),
  revision_no integer NOT NULL CHECK (revision_no > 0),
  content jsonb NOT NULL,
  content_hash text NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (brief_id,revision_no),
  UNIQUE (brief_id,id)
);
ALTER TABLE creative_briefs ADD CONSTRAINT fk_brief_current_revision
  FOREIGN KEY(id,current_revision_id) REFERENCES brief_revisions(brief_id,id)
  DEFERRABLE INITIALLY IMMEDIATE;

CREATE TABLE scripts (
  id uuid PRIMARY KEY,
  project_id uuid NOT NULL REFERENCES projects(id),
  current_revision_id uuid,
  draft jsonb NOT NULL DEFAULT '{}'::jsonb,
  lock_version bigint NOT NULL DEFAULT 0
);
CREATE TABLE script_revisions (
  id uuid PRIMARY KEY,
  script_id uuid NOT NULL REFERENCES scripts(id),
  revision_no integer NOT NULL CHECK (revision_no > 0),
  source_brief_revision_id uuid REFERENCES brief_revisions(id),
  structured_content jsonb NOT NULL,
  schema_version integer NOT NULL CHECK (schema_version > 0),
  content_hash text NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (script_id,revision_no), UNIQUE (script_id,id)
);
ALTER TABLE scripts ADD CONSTRAINT fk_script_current_revision
 FOREIGN KEY(id,current_revision_id) REFERENCES script_revisions(script_id,id);

CREATE TABLE storyboards (
  id uuid PRIMARY KEY,
  project_id uuid NOT NULL REFERENCES projects(id),
  current_revision_id uuid,
  draft jsonb NOT NULL DEFAULT '{}'::jsonb,
  lock_version bigint NOT NULL DEFAULT 0
);
CREATE TABLE storyboard_revisions (
  id uuid PRIMARY KEY,
  storyboard_id uuid NOT NULL REFERENCES storyboards(id),
  revision_no integer NOT NULL CHECK (revision_no > 0),
  source_script_revision_id uuid REFERENCES script_revisions(id),
  content_hash text NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE(storyboard_id,revision_no), UNIQUE(storyboard_id,id)
);
ALTER TABLE storyboards ADD CONSTRAINT fk_storyboard_current_revision
 FOREIGN KEY(id,current_revision_id) REFERENCES storyboard_revisions(storyboard_id,id);

CREATE TABLE storyboard_scenes (
  storyboard_revision_id uuid NOT NULL REFERENCES storyboard_revisions(id),
  scene_id uuid NOT NULL,
  order_no integer NOT NULL CHECK (order_no >= 0),
  payload jsonb NOT NULL,
  is_locked boolean NOT NULL DEFAULT false,
  PRIMARY KEY(storyboard_revision_id,scene_id),
  UNIQUE(storyboard_revision_id,order_no)
);
```

**发布事务：** `SELECT ... FOR UPDATE` 锁定逻辑根行 → 校验草稿/资产授权与结构 → 计算下一个 `revision_no` → 插入不可变修订及 Scene 快照 → 条件更新根的 `current_revision_id, lock_version` → 插入 Outbox。相同聚合并发发布要么串行完成，要么一方明确冲突；不能用 `SELECT MAX(revision_no)+1` 在无锁并发中推断安全序号。

**不可变性落地：** 生产应用的数据库角色只获这些 Revision 表的 INSERT/SELECT 权限；若使用同一高权限连接池，则须进一步使用专门的 `BEFORE UPDATE OR DELETE` 拒绝触发器，或者数据库权限隔离。仅在文档中宣称“不可变”不充分。

## 4. 资产与交付数据

```sql
CREATE TABLE assets (
  id uuid PRIMARY KEY,
  workspace_id uuid NOT NULL REFERENCES workspaces(id),
  project_id uuid,
  asset_type text NOT NULL CHECK (asset_type IN ('IMAGE','VIDEO','AUDIO','SUBTITLE','DOCUMENT','OTHER')),
  name text NOT NULL,
  status text NOT NULL DEFAULT 'ACTIVE' CHECK(status IN ('ACTIVE','ARCHIVED','DELETING')),
  current_version_id uuid,
  lock_version bigint NOT NULL DEFAULT 0,
  created_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE(id,workspace_id),
  FOREIGN KEY(project_id,workspace_id) REFERENCES projects(id,workspace_id)
);
CREATE TABLE asset_versions (
  id uuid PRIMARY KEY,
  asset_id uuid NOT NULL REFERENCES assets(id),
  version_no integer NOT NULL CHECK(version_no > 0),
  bucket text NOT NULL,
  object_key text NOT NULL,
  content_sha256 text NOT NULL CHECK(content_sha256 ~ '^[0-9a-f]{64}$'),
  size_bytes bigint NOT NULL CHECK(size_bytes >= 0),
  mime_type text NOT NULL,
  media_metadata jsonb NOT NULL DEFAULT '{}'::jsonb,
  provenance jsonb NOT NULL DEFAULT '{}'::jsonb,
  source_attempt_id uuid,
  committed_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE(asset_id,version_no), UNIQUE(bucket,object_key), UNIQUE(asset_id,id)
);
ALTER TABLE assets ADD CONSTRAINT fk_asset_current_version
 FOREIGN KEY(id,current_version_id) REFERENCES asset_versions(asset_id,id);

CREATE TABLE asset_ingestions (
  id uuid PRIMARY KEY,
  asset_id uuid NOT NULL REFERENCES assets(id),
  attempt_id uuid,
  bucket text NOT NULL,
  staging_key text NOT NULL,
  status text NOT NULL CHECK(status IN ('UPLOADING','UPLOADED','VERIFIED','COMMITTED','ABANDONED')),
  sha256 text,
  verified_at timestamptz,
  expires_at timestamptz NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE(bucket,staging_key)
);
CREATE INDEX ix_asset_ingestions_cleanup ON asset_ingestions(expires_at)
 WHERE status IN ('UPLOADING','UPLOADED','VERIFIED','ABANDONED');

CREATE TABLE asset_references (
  id uuid PRIMARY KEY,
  asset_version_id uuid NOT NULL REFERENCES asset_versions(id) ON DELETE RESTRICT,
  owner_type text NOT NULL CHECK(owner_type IN ('SCENE','COMPOSITION_VERSION','WORK_VERSION','WORKFLOW_RUN','OTHER')),
  owner_id uuid NOT NULL,
  ref_key text NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE(owner_type,owner_id,ref_key)
);
CREATE INDEX ix_asset_references_version ON asset_references(asset_version_id);
```

`asset_references` 的多态 `owner_type/owner_id` 无法通过普通 FK 约束引用所有 Owner 表。若其承担**防止文件删除的权威职责**，须采取下列一个方案：① 按 owner 类型拆成具有真实 FK 的引用表；② 使用受控引用写入服务、事务锁与周期对账并禁止其他路径删除；③ 引入统一资源身份表并由各领域约束映射。**推荐在生产交付引用场景优先采用明确 FK 的专项表，而非只依赖通用多态引用。**

```sql
CREATE TABLE works (
  id uuid PRIMARY KEY,
  project_id uuid NOT NULL REFERENCES projects(id),
  name text NOT NULL,
  current_version_id uuid,
  lock_version bigint NOT NULL DEFAULT 0
);
CREATE TABLE compositions (
  id uuid PRIMARY KEY,
  work_id uuid NOT NULL REFERENCES works(id),
  draft jsonb NOT NULL DEFAULT '{}'::jsonb,
  current_version_id uuid,
  lock_version bigint NOT NULL DEFAULT 0
);
CREATE TABLE composition_versions (
  id uuid PRIMARY KEY,
  composition_id uuid NOT NULL REFERENCES compositions(id),
  version_no integer NOT NULL CHECK(version_no > 0),
  timeline jsonb NOT NULL,
  schema_version integer NOT NULL CHECK(schema_version > 0),
  created_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE(composition_id,version_no), UNIQUE(composition_id,id)
);
ALTER TABLE compositions ADD CONSTRAINT fk_composition_current_version
 FOREIGN KEY(id,current_version_id) REFERENCES composition_versions(composition_id,id);

CREATE TABLE work_versions (
  id uuid PRIMARY KEY,
  work_id uuid NOT NULL REFERENCES works(id),
  version_no integer NOT NULL CHECK(version_no > 0),
  composition_version_id uuid NOT NULL REFERENCES composition_versions(id),
  output_asset_version_id uuid REFERENCES asset_versions(id) ON DELETE RESTRICT,
  review_status text NOT NULL DEFAULT 'DRAFT'
    CHECK(review_status IN ('DRAFT','IN_REVIEW','APPROVED','REJECTED')),
  delivery_status text NOT NULL DEFAULT 'NOT_READY'
    CHECK(delivery_status IN ('NOT_READY','READY','DELIVERED')),
  lock_version bigint NOT NULL DEFAULT 0,
  created_at timestamptz NOT NULL DEFAULT now(),
  CHECK(delivery_status <> 'DELIVERED' OR (review_status = 'APPROVED' AND output_asset_version_id IS NOT NULL)),
  UNIQUE(work_id,version_no), UNIQUE(work_id,id)
);
ALTER TABLE works ADD CONSTRAINT fk_work_current_version
 FOREIGN KEY(id,current_version_id) REFERENCES work_versions(work_id,id);
```

**版本不可变与审核状态冲突的处理：** `work_versions` 的**内容身份字段**（`work_id`、`composition_version_id` 等）禁止修改，但审核/交付状态是版本关联的**可变流程状态**。应采用字段级写入约束或将审核与交付拆至 `work_version_reviews` / `work_version_deliveries`；不能既声明整行不可变又直接更新 `review_status`。本版示例选用“内容字段不可变、流程字段允许受控更新”，并强制 `lock_version` CAS。

## 5. 工作流定义表

```sql
CREATE TABLE workflow_definitions (
  id uuid PRIMARY KEY,
  workspace_id uuid NOT NULL REFERENCES workspaces(id),
  name text NOT NULL,
  draft_graph jsonb NOT NULL DEFAULT '{}'::jsonb,
  status text NOT NULL DEFAULT 'ACTIVE' CHECK(status IN ('ACTIVE','ARCHIVED')),
  current_version_id uuid,
  lock_version bigint NOT NULL DEFAULT 0,
  created_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE(id,workspace_id)
);
CREATE TABLE workflow_versions (
  id uuid PRIMARY KEY,
  workflow_id uuid NOT NULL REFERENCES workflow_definitions(id),
  version_no integer NOT NULL CHECK(version_no > 0),
  definition jsonb NOT NULL,
  schema_version integer NOT NULL CHECK(schema_version > 0),
  definition_hash text NOT NULL,
  published_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE(workflow_id,version_no), UNIQUE(workflow_id,id)
);
ALTER TABLE workflow_definitions ADD CONSTRAINT fk_workflow_current_version
 FOREIGN KEY(id,current_version_id) REFERENCES workflow_versions(workflow_id,id);
```

`definition` 包含发布时校验后的节点、边、输入输出 Schema、重试/超时与动态展开限制。DAG 无环、端口类型和必需输出可达性属于**跨 JSON 节点的业务校验**，不可用单列 CHECK 替代；发布必须在应用层执行编译校验并将结果快照写入版本表。

## 6. WorkflowRun、NodeRun 和依赖满足

```sql
CREATE TABLE workflow_runs (
  id uuid PRIMARY KEY,
  workspace_id uuid NOT NULL REFERENCES workspaces(id),
  project_id uuid,
  workflow_version_id uuid NOT NULL REFERENCES workflow_versions(id),
  status text NOT NULL DEFAULT 'CREATED'
    CHECK(status IN ('CREATED','RUNNING','WAITING','PAUSED','CANCELING','CANCELED','SUCCEEDED','FAILED')),
  input_snapshot jsonb NOT NULL,
  input_fingerprint text NOT NULL,
  trigger_type text NOT NULL,
  triggered_by uuid,
  failure_summary jsonb,
  started_at timestamptz,
  finished_at timestamptz,
  lock_version bigint NOT NULL DEFAULT 0,
  created_at timestamptz NOT NULL DEFAULT now(),
  FOREIGN KEY(project_id,workspace_id) REFERENCES projects(id,workspace_id),
  UNIQUE(id,workspace_id)
);
CREATE INDEX ix_runs_workspace_status ON workflow_runs(workspace_id,status,created_at DESC);

CREATE TABLE node_runs (
  id uuid PRIMARY KEY,
  workflow_run_id uuid NOT NULL REFERENCES workflow_runs(id),
  node_definition_id text NOT NULL,
  expansion_key text NOT NULL DEFAULT '',
  parent_node_run_id uuid REFERENCES node_runs(id),
  status text NOT NULL DEFAULT 'PENDING'
    CHECK(status IN ('PENDING','READY','RUNNING','WAITING','SUCCEEDED','FAILED','SKIPPED','BLOCKED','CANCELED')),
  input_snapshot jsonb,
  output_ref jsonb,
  remaining_dependencies integer NOT NULL DEFAULT 0 CHECK(remaining_dependencies >= 0),
  lock_version bigint NOT NULL DEFAULT 0,
  started_at timestamptz,
  finished_at timestamptz,
  UNIQUE(workflow_run_id,node_definition_id,expansion_key),
  UNIQUE(id,workflow_run_id)
);
CREATE INDEX ix_node_runs_run_status ON node_runs(workflow_run_id,status);

CREATE TABLE node_dependency_satisfactions (
  target_node_run_id uuid NOT NULL REFERENCES node_runs(id),
  dependency_key text NOT NULL,
  source_node_run_id uuid NOT NULL REFERENCES node_runs(id),
  source_outcome_version bigint NOT NULL CHECK(source_outcome_version >= 0),
  satisfied_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY(target_node_run_id,dependency_key)
);
```

**重要边界：** 当前 `node_dependency_satisfactions` 的两个 FK 仅保证节点存在，不保证源/目标属于相同 WorkflowRun。推进服务必须校验，若要数据库强制保障，应在表内增加 `workflow_run_id` 并采用组合 FK `(node_id,workflow_run_id)` 分别指向源和目标节点。**推荐落地迁移使用组合 FK**，下方演示 SQL 的基础版需按该约束加强。

动态展开唯一性采用非空 `expansion_key DEFAULT ''`，而非允许 NULL 的三列 UNIQUE，以规避 NULL 默认互不相等造成的重复根节点。

### 6.1 依赖推进事务

```
BEGIN;
-- 锁定目标节点，防止两个来源并发推进时同时读旧计数
SELECT id, status, remaining_dependencies FROM node_runs WHERE id = $target_id FOR UPDATE;
INSERT INTO node_dependency_satisfactions
  (target_node_run_id,dependency_key,source_node_run_id,source_outcome_version)
VALUES ($target_id,$dep_key,$source_id,$source_version)
ON CONFLICT (target_node_run_id,dependency_key) DO NOTHING
RETURNING target_node_run_id;
-- 只有 INSERT 返回行，且依赖语义已校验时才能将 remaining_dependencies - 1
-- 如果 remaining_dependencies 变为 0 且 Join/Condition 规则通过：将 NodeRun 置 READY，创建 Task，写 Outbox。
COMMIT;
```

以上为**应用层事务算法伪代码**，不能把注释当可执行 SQL：实现必须检查 `RowsAffected`，校验 source 状态/同 Run 归属、目标节点非终态以及 Join 分支语义。如果发生重复事件，绝不重复递减。

## 7. Task 与 TaskAttempt 持久化

```sql
CREATE TABLE tasks (
  id uuid PRIMARY KEY,
  workflow_run_id uuid NOT NULL REFERENCES workflow_runs(id),
  node_run_id uuid NOT NULL,
  workspace_id uuid NOT NULL REFERENCES workspaces(id),
  task_type text NOT NULL,
  capability text NOT NULL,
  status text NOT NULL DEFAULT 'PENDING'
    CHECK(status IN ('PENDING','READY','QUEUED','RUNNING','RETRY_WAIT','SUCCEEDED','FAILED','CANCELED')),
  input_ref jsonb NOT NULL DEFAULT '{}'::jsonb,
  priority integer NOT NULL DEFAULT 0,
  resource_requirements jsonb NOT NULL DEFAULT '{}'::jsonb,
  retry_policy jsonb NOT NULL DEFAULT '{}'::jsonb,
  timeout_ms bigint NOT NULL CHECK(timeout_ms > 0),
  next_run_at timestamptz,
  attempt_count integer NOT NULL DEFAULT 0 CHECK(attempt_count >= 0),
  lease_epoch bigint NOT NULL DEFAULT 0 CHECK(lease_epoch >= 0),
  current_attempt_id uuid,
  result_ref jsonb,
  lock_version bigint NOT NULL DEFAULT 0,
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now(),
  FOREIGN KEY(node_run_id,workflow_run_id) REFERENCES node_runs(id,workflow_run_id),
  FOREIGN KEY(workflow_run_id,workspace_id) REFERENCES workflow_runs(id,workspace_id),
  UNIQUE(id,workflow_run_id)
);
CREATE INDEX ix_tasks_ready ON tasks(priority DESC,created_at,id)
 WHERE status IN ('READY','QUEUED');
CREATE INDEX ix_tasks_retry ON tasks(next_run_at,id) WHERE status = 'RETRY_WAIT';
CREATE INDEX ix_tasks_running ON tasks(updated_at,id) WHERE status = 'RUNNING';
CREATE INDEX ix_tasks_node ON tasks(node_run_id);

CREATE TABLE worker_sessions (
  id uuid PRIMARY KEY,
  worker_id uuid NOT NULL,
  started_at timestamptz NOT NULL DEFAULT now(),
  heartbeat_at timestamptz NOT NULL DEFAULT now(),
  status text NOT NULL CHECK(status IN ('ACTIVE','DRAINING','EXPIRED','CLOSED')),
  capabilities jsonb NOT NULL DEFAULT '[]'::jsonb,
  resource_snapshot jsonb NOT NULL DEFAULT '{}'::jsonb
);
CREATE TABLE workers (
  id uuid PRIMARY KEY,
  name text NOT NULL,
  status text NOT NULL DEFAULT 'ACTIVE' CHECK(status IN ('ACTIVE','DISABLED')),
  lock_version bigint NOT NULL DEFAULT 0
);
ALTER TABLE worker_sessions ADD CONSTRAINT fk_worker_session_worker
 FOREIGN KEY(worker_id) REFERENCES workers(id);
CREATE INDEX ix_worker_sessions_active ON worker_sessions(worker_id,heartbeat_at DESC) WHERE status = 'ACTIVE';

CREATE TABLE task_attempts (
  id uuid PRIMARY KEY,
  task_id uuid NOT NULL REFERENCES tasks(id),
  attempt_no integer NOT NULL CHECK(attempt_no > 0),
  worker_session_id uuid NOT NULL REFERENCES worker_sessions(id),
  lease_epoch bigint NOT NULL CHECK(lease_epoch > 0),
  lease_token_hash text NOT NULL,
  lease_expires_at timestamptz NOT NULL,
  status text NOT NULL CHECK(status IN ('CREATED','RUNNING','SUCCEEDED','FAILED','TIMED_OUT','ABANDONED')),
  result_manifest jsonb,
  error_code text,
  started_at timestamptz NOT NULL DEFAULT now(),
  finished_at timestamptz,
  UNIQUE(task_id,attempt_no),
  UNIQUE(task_id,lease_epoch),
  UNIQUE(task_id,id)
);
-- 任何时刻最多一条仍被标记为活跃的 Attempt；过期恢复事务需先终结旧 Attempt。
CREATE UNIQUE INDEX ux_one_active_attempt_per_task ON task_attempts(task_id)
 WHERE status IN ('CREATED','RUNNING');
ALTER TABLE tasks ADD CONSTRAINT fk_task_current_attempt
 FOREIGN KEY(id,current_attempt_id) REFERENCES task_attempts(task_id,id);
CREATE INDEX ix_attempts_lease_expiry ON task_attempts(lease_expires_at)
 WHERE status IN ('CREATED','RUNNING');
```

**关于循环外键：** `tasks.current_attempt_id -> task_attempts` 与 `task_attempts.task_id -> tasks` 构成受控循环引用。建表顺序如上以 `ALTER TABLE` 添加后向 FK；领取事务应先插入 Attempt 再更新 Task 当前指针。不要在迁移时让新表的双向 FK 阻止合法创建流程。

**逻辑有效性 vs 物理唯一性：** 部分唯一索引阻止两条同时标记为 RUNNING 的 Attempt，但真正的**有效执行权**还由 Task 的 `current_attempt_id`、`lease_epoch`、租约时间和 WorkerSession 状态一起决定。索引不能取代结果提交时的检查。

## 9. Outbox、Inbox 与请求幂等

```sql
CREATE TABLE outbox_events (
  id uuid PRIMARY KEY,
  aggregate_type text NOT NULL,
  aggregate_id uuid NOT NULL,
  aggregate_version bigint,
  event_type text NOT NULL,
  schema_version integer NOT NULL CHECK(schema_version > 0),
  workspace_id uuid,
  correlation_id uuid,
  causation_id uuid,
  payload jsonb NOT NULL,
  occurred_at timestamptz NOT NULL DEFAULT now(),
  published_at timestamptz,
  publish_attempts integer NOT NULL DEFAULT 0 CHECK(publish_attempts >= 0),
  next_publish_at timestamptz NOT NULL DEFAULT now(),
  claimed_until timestamptz
);
CREATE INDEX ix_outbox_pending ON outbox_events(next_publish_at,occurred_at,id)
 WHERE published_at IS NULL;

CREATE TABLE inbox_receipts (
  consumer_name text NOT NULL,
  event_id uuid NOT NULL,
  processed_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY(consumer_name,event_id)
);

CREATE TABLE idempotency_records (
  id uuid PRIMARY KEY,
  scope text NOT NULL,
  actor_id uuid NOT NULL,
  operation text NOT NULL,
  idempotency_key text NOT NULL,
  request_hash text NOT NULL,
  result_kind text,
  result_id uuid,
  response_payload jsonb,
  status text NOT NULL CHECK(status IN ('PROCESSING','SUCCEEDED','FAILED')),
  expires_at timestamptz NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE(scope,actor_id,operation,idempotency_key)
);
CREATE INDEX ix_idempotency_expire ON idempotency_records(expires_at);
```

**Outbox 核心纪律：** 更新 Task/Run 与插入 `outbox_events` 发生在同一数据库事务；发布器可重复发送；消费者必须以 `(consumer_name,event_id)` 去重。发布器不能在事务提交前将业务事件发送到外部消息系统。

**Inbox 事务纪律：** 消费者必须在**同一个数据库事务**中插入 `inbox_receipts` 并完成目标状态变更。只插 Inbox 就提交，再另起事务处理事件，会导致“标记已消费但实际未推进”。

**Idempotency 纪律：** `scope` 必须包含租户/接口作用边界的稳定语义；相同 key 不同 `request_hash` 返回冲突；相同 key 且处于 PROCESSING 时返回进行中而非发起第二次运行；超过 TTL 后重新使用 key 的行为需在 API 契约中说明，关键长期去重不能只依赖有过期时间的请求记录。

## 10. 乐观锁与数据版本控制

### 10.1 聚合 CAS 更新

```sql
UPDATE projects
SET name = $2,
    lock_version = lock_version + 1,
    updated_at = now()
WHERE id = $1 AND lock_version = $3 AND status <> 'DELETING'
RETURNING lock_version;
```

0 行返回时必须进一步区分“对象不存在、无访问权限、版本冲突、当前状态不允许”。不能把所有 0 行一律当 404。对于并发用户编辑，HTTP 可映射为 409 Conflict 或明确约定的条件更新失败状态。

### 10.2 与业务修订版本的区别

- `lock_version`：内部并发控制，更新一次递增一次。
- `revision_no`：剧本/分镜等已发布修订，插入新快照时递增。
- `workflow_versions.version_no`：工作流发布版本，用于历史运行固定引用。
- `lease_epoch`：Task 执行代数，用于隔离过期执行者。

它们不能混用。尤其不能把 `lease_epoch` 当普通 UI 乐观锁，也不能把 `lock_version` 当可见业务发布版本。

### 10.3 修改多个聚合

跨聚合修改不是“给所有表加 lock_version 就自然原子”。必须有应用事务，确定锁顺序、受影响记录以及可恢复事件。例如提交 Task 结果 + 资产元数据 + Outbox 在同一事务内完成；NodeRun 的后续推进可由独立幂等消费者完成。

### 10.4 乐观锁失败处理

普通人工编辑：返回冲突并要求用户比较、刷新或合并，不自动覆盖。

内部幂等命令：允许有界重读和重试，前提是没有产生不可逆的外部副作用。

高争用调度：使用短事务行锁/条件更新，不依赖无限 CAS 自旋。

## 11. 四条核心事务详细设计

### TX-01：启动 WorkflowRun

**前提：** 已校验 Workspace 权限、WorkflowVersion 属主、输入修订、项目状态及预算策略。

**步骤：** 开始事务 → 锁定/检查请求 Idempotency Key → 写 `workflow_runs` → 初始化静态 `node_runs`（或只初始化可确定的起始节点）→ 写 `outbox_events(WorkflowRunStarted)` → 更新幂等记录为 SUCCEEDED 并保存 RunID → 提交。

**正确性标准：** 同一业务请求重发不会多创建 Run；Run 的版本和输入快照不可被外部草稿修改；提交失败不发送已完成事件。

**重要：** 预算预留如果属于同库强一致约束，应在同一事务内锁定 Budget/Quota 行；如果不能同事务，则必须定义预留失败的补偿行为。

### TX-02：并发领取任务并授予租约

```sql
BEGIN;
-- 候选任务领取：只在已授权的 Worker 能力/租户/资源策略下运行
SELECT id,attempt_count,lease_epoch,lock_version
FROM tasks
WHERE status IN ('READY','QUEUED')
ORDER BY priority DESC,created_at,id
FOR UPDATE SKIP LOCKED
LIMIT 1;
-- 无行：ROLLBACK/COMMIT 并等待；有行：
-- 1. 锁相关 quota/resource_pool 并检查资源余量
-- 2. 验证 WorkerSession ACTIVE、能力/资源匹配
-- 3. INSERT task_attempts(status='CREATED', attempt_no=old+1,
--       lease_epoch=old+1, lease_expires_at=..., lease_token_hash=...)
-- 4. UPDATE tasks SET status='RUNNING',attempt_count=attempt_count+1,
--       lease_epoch=lease_epoch+1,current_attempt_id=new_id,
--       lock_version=lock_version+1 WHERE id=... AND status IN (...)
-- 5. INSERT resource_reservations + outbox(TaskLeaseGranted)
COMMIT;
```

**关键：** 这里 `SKIP LOCKED` 用于队列式领取，返回的集合可能是不完整视图；不适合用它做“当前所有任务状态”的统计查询。资源/配额检查同样必须处于有效原子边界。优先级跨多类型任务公平分配需要调度器另外实现。

**失败：** DB 事务失败时没有有效租约；提交成功但 Worker 未收到消息，则由分发重试或租约恢复处理。

### TX-03：续租任务

```sql
UPDATE task_attempts a
SET lease_expires_at = $new_deadline
FROM tasks t, worker_sessions s
WHERE a.id = $attempt_id
  AND a.task_id = t.id
  AND a.worker_session_id = s.id
  AND t.current_attempt_id = a.id
  AND t.status = 'RUNNING'
  AND t.lease_epoch = a.lease_epoch
  AND a.lease_epoch = $lease_epoch
  AND a.lease_token_hash = $token_hash
  AND a.status IN ('CREATED','RUNNING')
  AND a.lease_expires_at > clock_timestamp()
  AND s.status = 'ACTIVE'
RETURNING a.lease_expires_at;
```

**实现补充：** 若要严格防止“续租刚检查完成、结果提交或恢复同时变更 Task”的竞争，续租必须显式锁定 Task 行（如 `SELECT ... FOR UPDATE`）再校验和更新 Attempt；上述 SQL 是条件判定示例，不能单独视为完整的并发安全协议。续租和回收的锁顺序必须保持一致。租约时间推荐由数据库服务端时间计算，以减少不同 Worker 时钟漂移影响；不可将客户端自报时间作为最终授权判断。

### TX-04：提交执行结果（最关键）

**前置外部操作：** Worker 上传对象并计算校验和；服务端验证对象内容和输出 Schema，准备稳定且长期保存的对象引用。对象存储动作不置于 PostgreSQL 事务内部等待。

**事务：**

1. `SELECT tasks WHERE id=$task_id FOR UPDATE`。
2. 检查 `status='RUNNING'`、`current_attempt_id`、`lease_epoch` 与当前有效授权。
3. 检查 Attempt 属于该 Task，尚未终结，Lease 未失效（或按明确定义的过期提交策略拒绝）。
4. 若资产尚未正式登记，INSERT `asset_versions`（以及必要 Asset 根变更），保证幂等来源键。
5. UPDATE `task_attempts` = SUCCEEDED，写 `result_manifest`。
6. UPDATE `tasks` = SUCCEEDED，写 `result_ref`，`lock_version += 1`。
7. 对预留资源执行幂等释放/结算，写 Outbox(TaskSucceeded)。
8. 提交事务。

**重复提交：** 若 Task 已 SUCCEEDED 且提交来自相同已确认 Attempt、相同结果摘要，可返回已确认结果（幂等成功）；来自不同 Attempt 或内容不一致，返回冲突，不能二次生成正式资产。

**迟到提交：** 租约已失效/代数改变/任务已取消时拒绝。临时对象留给 GC，对账保证不会误删已引用对象。

**必须补充的唯一性：** 若“一个 Attempt 只生成一个主结果资产”是契约，可对 `asset_versions.source_attempt_id` 建立部分唯一索引；若单次 Attempt 会产生多个资产，应使用 `artifact_key` 或 `(source_attempt_id, output_slot)` 唯一，不能错误地把所有产物挤成一个。

## 12. 重试、超时、取消、恢复与对账

### 12.1 恢复任务

恢复器按时间扫描 `task_attempts` 中 `lease_expires_at < clock_timestamp()` 且活跃的记录，逐任务短事务锁定 `tasks` 再锁 Attempt。若该 Attempt 已不再是 `current_attempt_id`，只执行幂等收尾；若仍为当前执行，标记 Attempt `TIMED_OUT/ABANDONED`，释放或标记资源预留，按 RetryPolicy 将 Task 转为 `RETRY_WAIT` 或 `FAILED`，写 Outbox。

**重要：** 重调度前必须先把旧 Attempt 改为非活跃状态，才能满足 `ux_one_active_attempt_per_task`；它保证可恢复流程中不会有两个数据库标记为活跃的尝试，但无法强行停止失联 Worker 的外部计算。

### 12.2 Retry timer

扫描 `tasks.status='RETRY_WAIT' AND next_run_at <= now()`，使用条件状态更新将 Task 转为 READY，写 Outbox(TaskReady)。即使重试计时器重复触发，也只允许第一次符合条件的状态变更产生事件。

### 12.3 Workflow 取消

取消请求先将 WorkflowRun 置 CANCELING + Outbox；异步传播至 NodeRun/Task，运行任务按照执行能力协作式取消或拒绝后续有效结果。直到必要子状态得到收敛后，Run 才能进入 CANCELED。不能直接把所有运行中的 Attempt 当作已经实际停止。

### 12.4 Reconciliation

定期发现并修复：

- RUNNING Task 当前 Attempt 为空或不匹配；
- Lease 已超期但没有重试/终结；
- READY Task 长期未获调度；
- Task SUCCEEDED 但 NodeRun 仍等待推进；
- NodeRun 未满足计数与实际依赖记录不一致；
- 已消费事件对应的状态没有推进；
- 孤立 AssetIngestion / Staging 对象；
- 资源 Reservation 已过期但仍标记有效；
- Outbox 长期未发布。

恢复动作本身需具备唯一事件键或条件更新，不能使对账器成为新一轮重复写入来源。

## 13. 隔离级别、锁顺序与死锁处理

**默认建议：** 大部分短事务使用 PostgreSQL 默认 `READ COMMITTED`，通过唯一索引、行锁、CAS 和条件写入保证关键不变量。跨多行、难以通过显式锁保护的复杂约束可以评估 `SERIALIZABLE`，并必须处理 `40001` serialization_failure 的整个事务重试；这不是所有操作统一设置 SERIALIZABLE 的理由。

**统一锁顺序建议：** `workflow_runs`（仅需要时）→ `node_runs` → `tasks` → `task_attempts` → `resource_pools/quota_accounts`（若高并发实际需要不同顺序，应统一重新制定）。但 **Task Claim** 先锁 Task 后锁资源，**Task Result Commit** 也从 Task 开始；对于跨多对象写入必须确定一种不会形成循环等待的实际全局顺序。不能机械照抄本表与操作步骤中冲突的顺序；落地实施前须以事务矩阵审查并固定锁序。多资源池按 ID 排序加锁。

建议设置合理的 `lock_timeout`、`statement_timeout`，并针对 SQLSTATE `40P01`（deadlock_detected）和 `40001` 在**允许安全重试的事务**中执行有限次数完整事务重试，带随机退避。

**防止长事务：** 任何 AI HTTP 调用、FFmpeg、对象存储上传、外部 Webhook 都不能在持有数据库行锁的事务中执行。

## 14. 索引与容量设计

| 查询/作业 | 核心索引 | 说明 |
|---|---|---|
| 工作空间项目列表 | `(workspace_id,status,created_at DESC)` | 分页应加稳定 ID 次序 |
| 工作流运行列表 | `(workspace_id,status,created_at DESC)` | 大表采用游标分页 |
| 某 Run 下节点 | `(workflow_run_id,status)` | 支持运行进度 |
| READY 任务分发 | 部分索引 `(priority DESC,created_at,id)` | 可按 capability 分桶优化 |
| RETRY_WAIT 唤醒 | 部分索引 `(next_run_at,id)` | 定时器扫描 |
| Attempt 超时 | 部分索引 `(lease_expires_at)` | Recovery |
| Outbox 发送 | 部分索引 `(next_publish_at,occurred_at,id)` | 批量发布 |
| 资产引用清理 | `asset_references(asset_version_id)` | 删除前核对 |
| 用量统计 | `(workspace_id,occurred_at)`（待落表） | 长期可按时间分区 |

**索引演进：** 根据 `EXPLAIN (ANALYZE, BUFFERS)` 和实际执行计划调整，避免无依据对所有列建立索引。大体量 `task_attempts`、`outbox_events`、`usage_ledger`、`audit_events` 可考虑时间分区/归档，但分区键、全局唯一性和 FK 限制需专项评估。

**租户安全：** 本阶段采用服务端必传 workspace 作用域 + 复合外键 + 授权检查，生产环境应评估 Row Level Security 和数据库角色最小权限。RLS 的启用需要完整评估连接池上下文传播与后台管理任务权限，不可只开启策略就认为隔离已完成。

## 15. 迁移设计与落地顺序

建议迁移包分组，采用单向、编号、可审计的 SQL 文件（需要支持回滚时提供经过验证的 down 迁移；避免未经评估的生产数据删除）。

```text
backend/migrations/
  000001_identity_workspace.up.sql
  000002_project.up.sql
  000003_creative_revisions.up.sql
  000004_assets.up.sql
  000005_delivery.up.sql
  000006_workflow_definition.up.sql
  000007_workflow_execution.up.sql
  000008_workers_tasks.up.sql
  000009_resources_usage.up.sql
  000010_outbox_inbox_idempotency.up.sql
```

**执行顺序审查：** 示例中 `asset_versions.source_attempt_id` 尚未加 TaskAttempt FK，以避免 assets 先于 tasks 造成循环依赖。核心表全部建立后通过单独迁移增加相关 FK（如业务要求），或以 `source_attempt_id` 做弱关联+对账。跨版本参照采取“先建双方表，再 ALTER TABLE 添加回指 FK”。

每次迁移验证：空库安装、升级已有库、约束冲突失败、并发请求兼容、回滚策略、备份与数据恢复。在线大表加索引可考虑 `CREATE INDEX CONCURRENTLY`，但该语句不能放在普通事务块里；迁移工具必须支持非事务迁移。

## 16. Go Repository/UnitOfWork 契约

```go
// 领域接口示意：不强制与数据库表一一对应。
type TaskRepository interface {
    Get(ctx context.Context, id TaskID) (Task, error)
    SaveCAS(ctx context.Context, task Task, expectedVersion int64) error
}

type UnitOfWork interface {
    WithinTx(ctx context.Context, fn func(context.Context) error) error
}

// 高争用路径使用专门的原子命令接口，而非先全量加载再 Save。
type TaskClaimStore interface {
    ClaimNext(ctx context.Context, request ClaimRequest) (ExecutionGrant, error)
    RenewLease(ctx context.Context, request RenewLeaseRequest) error
    CommitResult(ctx context.Context, request CommitResultRequest) (CommitOutcome, error)
}
```

实现重点：

- 使用 `pgx`/`database/sql` 等事务能力，在 `context.Context` 中传递受控事务上下文，禁止任意业务代码直接获得原始全局 Tx。
- `RowsAffected == 0` 的 CAS 失败必须返回可区分的 `ErrConflict`/`ErrInvalidState`/`ErrNotFound`。
- 事务内重试要重新读取数据并重新验证业务不变量。
- 业务状态变化与 Outbox 插入在一个 Tx 中完成。
- Repo 不负责调用 AI、对象存储、FFmpeg 等外部副作用。

## 18. 设计检查清单与待决事项

### 18.1 设计已确定

- 已发布 WorkflowVersion、CreativeRevision、AssetVersion 的内容不可变。
- WorkflowRun 与 NodeRun 分离持久化，NodeRun 可以独立竞争更新。
- Task 与 TaskAttempt 分表，结果确认需要 `current_attempt_id + lease_epoch + lease` 校验。
- 应用聚合通过 `lock_version` 乐观锁防止丢失更新。
- 关键跨聚合状态变更与 Outbox 同事务提交。
- PostgreSQL 保存权威状态，Redis 仅为加速和通知可选组件。
- 对象存储与 PostgreSQL 之间采用先验证产物、再数据库确认、最后对账清理的协议。

### 18.2 编码前需冻结的决策

| 决策编号 | 问题 | 当前建议 |
|---|---|---|
| DB-D01 | UUID 生成方案 | 应用生成 UUID，禁止混用无序业务 ID |
| DB-D02 | `asset_references` 如何拥有真实 FK | 交付关键引用拆分独立关系表 |
| DB-D03 | WorkVersion 审核记录是否独立表 | 如需完整历史/多轮审核，应独立 `work_version_reviews` |
| DB-D04 | ResultManifest 多产物唯一键 | `(attempt_id,output_slot)` |
| DB-D05 | Node 依赖组合 FK | 增加 `workflow_run_id` 强制同 Run 引用 |
| DB-D06 | Task 租约超时策略 | 使用 DB 时间、恢复任务前以行锁检查 |
| DB-D07 | 锁顺序 | 在 Scheduler/Worker 时序设计中统一审查并固化 |
| DB-D08 | 资源向量约束 | 初期行锁 ResourcePool + 应用校验；压测后再优化 |
| DB-D09 | 租户数据隔离 | 复合 FK + 权限，评估 RLS |
| DB-D10 | 已发布数据防修改手段 | DB 权限或拒绝 UPDATE/DELETE 触发器 |

### 18.3 实施提醒

1. 本文 DDL 给出**核心映射及足以验证设计的骨架**，部分扩展表仅列出字段要求而非完整 DDL。
2. 所有 SQL 需要放入真实 PostgreSQL 做语法、迁移顺序、锁竞争和回滚测试。
3. 不能因为某项约束已在 Go 领域层校验，就跳过数据库能合理提供的唯一性或引用约束。
4. 也不能用 CHECK/FK 替代跨表的业务状态机和权限模型。
5. 一旦详细实现偏离本文的领域不变量，应更新文档或写 ADR，不能静默改变语义。
