# 第一章 产品概述

## 1.1 产品背景

生成式人工智能正在改变数字内容的生产方式。文字、图片、音频和视频能够通过不同类型的 AI 模型生成，但完成一件具有实际交付价值的多媒体作品，仍然涉及多个相互依赖的环节。

以短视频制作为例，完整的生产过程通常涉及主题策划、内容编写、剧本生成、分镜规划、视觉素材制作、旁白配音、字幕处理、时间轴编排、视频合成、质量检查以及作品导出。

这些环节并非彼此独立。剧本的修改可能影响分镜，分镜的变化可能影响素材需求，旁白时长又可能影响视频片段长度。部分任务可以并行处理，部分任务必须等待其他任务完成，而部分失败只需要重新执行受影响的生产环节。

仅仅将多个 AI API 串联起来，无法完整解决这些问题。

真正需要解决的是：**如何将 AI 能力组织成可理解、可控制、可追踪、可恢复并能够持续迭代的内容生产流程。**

MediaFlow 因此被定义为一个完整的 AI 多媒体生产平台，而不是单一的视频生成工具。

## 1.2 产品定义

MediaFlow 是一个面向个人创作者、内容生产团队、企业以及开发者的 AI 多媒体生产与工作流编排平台。

平台通过统一的创作工作台、AI 模型接入体系、多媒体资产管理系统、工作流编排引擎和任务执行平台，将内容生产中的多个步骤组织成可配置、可观察、可复用的生产流程。

用户可以通过自然语言描述创作目标，也可以对剧本、分镜、素材和工作流进行精细控制。

系统负责执行生产流程、管理任务依赖、调度计算资源、处理生成结果、记录执行过程，并将各个生产环节的输出转化为最终可交付的多媒体作品。

## 1.3 产品愿景

**让复杂的多媒体内容生产变成一个可规划、可协作、可自动化、可持续优化的过程。**

长期愿景包括三个层面：

第一，降低多媒体生产门槛，使缺乏专业剪辑和设计经验的用户也能够完成质量可控的内容创作。

第二，提高内容生产效率，使专业创作者能够从大量重复性操作中解放出来，将更多精力投入创意、审美和内容质量。

第三，构建开放、可扩展的生产基础设施，使 AI 模型、处理工具和自动化任务能够通过统一的工作流机制协同运行。

## 1.4 产品使命

MediaFlow 的使命不是取代人的创作决策，而是让人能够更高效地组织、控制和完成复杂创作。

在 MediaFlow 中，AI 负责辅助创作和执行任务，人负责设定目标、制定约束、评估质量和决定最终结果。

## 1.5 核心价值主张

MediaFlow 为用户提供六项核心价值：

1. **端到端生产：** 从创意输入到最终交付，提供完整的内容生产链路。
2. **过程透明：** 每个生产步骤均有明确的输入、输出、状态和执行记录。
3. **局部可控：** 用户可以修改单个分镜、替换素材或重新执行局部步骤，而不必无条件重新生产整个作品。
4. **结果可复用：** 剧本、分镜、素材、模板和工作流均可积累为可复用资产。
5. **执行可靠：** 长时间运行的复杂任务能够处理失败、超时、服务限流、节点中断和部分恢复。
6. **能力可扩展：** 用户能够接入不同 AI 模型和处理工具，开发者能够通过 API 和扩展机制复用平台能力。

## 1.6 产品设计原则

### 目标优先

系统设计围绕用户希望完成的内容生产目标，而不是围绕某个具体模型、算法或技术组件展开。

### 创作过程可控

任何自动化能力都应当具有可观察的执行过程和明确的人工干预方式。

### 数据与资产可持续

用户创作的数据、生产素材、历史版本和最终作品具有长期价值，不应因为工作流执行结束而丢失。

### 失败是正常业务场景

系统设计必须默认外部模型可能限流、任务可能超时、Worker 可能退出、网络可能中断。

可靠恢复属于产品基础能力，而不是后期补丁。

### 模型与业务解耦

多媒体生产业务不应绑定单一模型供应商。

### 自动化与人工控制并存

用户既可以选择完全自动生成，也可以逐阶段确认和调整。

### 平台优先于单点功能

任何新的内容生产能力都应尽可能接入统一的资产、工作流、任务和执行体系，而不是建立无法复用的独立实现。

# 第二章 产品目标与边界

## 2.1 长期产品目标

MediaFlow 的长期目标分为四个方向。

| 目标维度 | 产品目标 |
|---|---|
| 创作体验 | 用户能够以低门槛完成高质量、多步骤的多媒体作品 |
| 生产效率 | 减少重复操作，提高素材复用率和生产流程自动化程度 |
| 生产可靠性 | 复杂任务可追踪、可恢复、可审计，不因局部故障轻易导致全部成果丢失 |
| 平台扩展性 | 支持新的模型类型、媒体类型、任务处理器、工作流和外部系统集成 |

这些目标应持续指导产品演进，不依赖某个特定发布版本。

## 2.2 产品成功的定义

MediaFlow 的成功不等于实现了多少 AI API，也不等于工作流支持多少节点。

真正的成功应体现为：

- 用户能够持续产出符合创作目标的作品。
- 用户能够准确了解作品的生产状态。
- 生成结果不理想时，用户能够以合理成本进行局部修改。
- 长时间运行的生产流程具有可预测的执行行为。
- 内容资产和生产流程能够被重复使用。
- 随着用户、项目和任务数量增加，平台能够保持稳定服务。
- 第三方模型和工具能够以一致的方式融入系统。
- 用户对生产成本、结果归属、数据处理和系统行为有足够的控制权。

## 2.3 产品范围

MediaFlow 的长期产品范围包括：

**创作层：** 内容策划、剧本、分镜、素材、配音、字幕、视频编排、预览、审核和交付。

**管理层：** 用户、团队、项目、作品、素材库、模板库、权限、版本和成本。

**平台层：** 模型接入、工作流定义、执行引擎、任务调度、资源管理、Worker、插件和开放 API。

**运营层：** 系统配置、执行监控、任务诊断、使用统计、服务配额、成本分析和安全审计。

## 2.4 产品边界

MediaFlow 的核心是组织和完成 AI 多媒体生产，不以替代所有专业制作软件为目标。

对于复杂的专业后期特效、电影级非线性编辑、三维建模或专业音频混音，产品可通过资产导入导出、外部工具集成和开放接口提供支持。

同时，MediaFlow 不以训练基础 AI 模型为主要业务目标。它可以调用、管理和编排模型推理能力，但模型训练平台不属于核心产品范畴。

# 第三章 目标用户与使用场景

## 3.1 用户角色

### 个人内容创作者

包括短视频创作者、知识分享者、教育内容创作者以及自媒体运营者。

主要需求是减少从创意到成片的操作复杂度，提高生产效率，并允许针对不满意的结果快速修改。

### 专业内容制作人员

包括视频策划、编导、设计师、剪辑人员和音频制作人员。

主要需求是对剧本、分镜、时间轴和素材具有更细致的控制能力，同时可以复用重复性流程。

### 内容生产团队

包括营销团队、品牌团队和内容工作室。

主要需求包括项目协作、任务分工、素材共享、审核流程、统一风格和批量生产。

### 企业用户

包括具有稳定内容生产需求的组织。

主要需求包括团队权限、资源配额、预算管理、审计追踪、数据安全、供应商管理和系统集成。

### 开发者与技术团队

主要需求是通过 API、SDK、自定义工作流和任务节点，将 AI 多媒体能力嵌入已有业务系统。

### 平台管理员与运维人员

主要需求是管理模型供应商、Worker、资源池、任务队列、失败恢复、安全策略和系统运行状态。

## 3.2 典型业务场景

### 场景 A：一句话生成短视频

用户输入主题、视频时长、语言、画面风格及目标受众。

系统完成剧本、分镜、画面、旁白、字幕和视频合成，并提供预览与修改能力。

### 场景 B：人工参与的精细化创作

用户先由 AI 生成剧本，经过人工修改后生成分镜，再选择性生成图片、视频和语音。

生产过程中可以锁定已确认内容，并只更新发生变化的部分。

### 场景 C：批量内容制作

用户使用一个模板，输入多个主题或数据记录，批量创建生产任务。

系统自动控制并发、成本和资源使用，汇总每件作品的状态与结果。

### 场景 D：品牌内容生产

团队建立统一的品牌风格、提示词模板、配音方案、素材库和审核流程。

新项目复用这些配置，并由指定成员审核后交付。

### 场景 E：开发者调用

开发者通过 API 创建工作流实例，提交输入参数，查询执行状态，并通过 Webhook 接收结果。

### 场景 F：故障恢复

某个分镜的图片生成失败或某台执行机器离线。

系统识别受影响任务，按照策略重试、转移或等待人工处理，不丢失已完成的其他素材。

# 第四章 产品整体架构

## 4.1 产品能力分层

MediaFlow 从产品能力角度划分为五层。

**第一层：用户与交互层**

提供项目管理、创作工作台、可视化工作流、素材管理、作品交付和系统管理入口。

**第二层：创作业务层**

负责剧本、分镜、素材生成、媒体编排、审核、作品版本和内容生产策略。

**第三层：工作流与任务层**

负责工作流定义、依赖关系、执行实例、任务状态、重试、取消、暂停、恢复和执行历史。

**第四层：能力与资源层**

负责 AI 模型能力、媒体处理能力、Worker、资源池、并发控制、配额及执行调度。

**第五层：基础设施层**

负责持久化、对象存储、消息通信、身份认证、监控、日志和运行环境。

各层通过明确的业务契约协作，避免创作业务直接依赖具体执行节点或供应商实现。

## 4.2 核心产品对象

| 领域对象 | 定义 |
|---|---|
| Workspace | 用户或组织开展工作的空间 |
| User | 平台用户 |
| Team | 协作用户集合 |
| Project | 围绕一个创作目标组织的工作集合 |
| CreativeBrief | 项目的创作目标与约束 |
| Script | 剧本及结构化内容 |
| Storyboard | 分镜集合 |
| Scene | 单个分镜或场景 |
| Asset | 可管理的多媒体资产 |
| AssetVersion | 资产的具体版本 |
| Composition | 作品的媒体编排定义 |
| Work | 一个可交付作品及其版本 |
| WorkflowDefinition | 工作流定义 |
| WorkflowVersion | 不可变的工作流定义版本 |
| WorkflowRun | 一次工作流执行实例 |
| NodeRun | 单个工作流节点在一次运行中的执行实例 |
| Task | 可独立调度的执行任务 |
| TaskAttempt | 一次具体的任务执行尝试 |
| Worker | 执行任务的运行节点 |
| Provider | 模型或外部能力供应商 |
| Model | 可供调用的模型配置 |
| ResourcePool | 提供特定执行能力的资源集合 |
| UsageRecord | 使用量和成本记录 |
| Approval | 审核决策 |
| AuditEvent | 重要业务操作的审计记录 |

这些对象共同构成产品的长期领域模型。

## 4.3 核心关系约束

一个 Workspace 可以包含多个项目。

一个项目可以包含多个作品以及它们的版本。

一个作品可以引用多个剧本版本、分镜版本和素材版本。

一个工作流可以具有多个定义版本，每次执行必须绑定其中一个确定版本。

一个工作流运行实例可以产生多个节点运行实例与执行任务。

一个任务可以因重试或执行环境故障产生多个 TaskAttempt。

一个 Worker 可以根据能力和资源限制同时承担多个任务。

执行结果通过明确的资产引用交付，不通过不受管理的本地临时文件形成长期依赖。

# 第五章 完整内容生产流程

## 5.1 端到端生产生命周期

MediaFlow 将内容生产视为具有持续状态的生命周期：

**创作需求 → 策划 → 剧本 → 分镜 → 素材生产 → 媒体编排 → 预览 → 审核 → 渲染 → 交付 → 归档与复用。**

这个生命周期不是固定的线性步骤。

用户可以跳过部分环节、从已有素材开始、重做某一环节，也可以使用自动化工作流一次性完成整个过程。

系统必须能够识别哪些产物已被确认、哪些发生变化，以及哪些后续任务因此需要更新。

## 5.2 创作需求定义

用户创建项目时，可以提供：

- 内容主题与核心观点
- 目标受众
- 创作目的
- 内容类型
- 目标时长
- 视频比例与分辨率
- 输出语言
- 视觉风格
- 旁白风格
- 品牌规范
- 参考素材
- 禁止出现的内容
- 成本预算
- 质量偏好
- 自动化级别

输入支持自然语言和结构化参数并存。

系统应将这些信息形成可编辑的 CreativeBrief，用作后续创作的统一依据。

当 Brief 被修改时，系统需要能够分析对已生成内容的影响。

## 5.3 剧本创作

剧本模块负责将创作目标转化为结构化内容。

主要能力：

- 根据 Brief 生成剧本
- 为不同内容类型提供剧本结构
- 按目标时长控制内容长度
- 支持章节和段落
- 支持旁白、画面说明及字幕内容
- 人工编辑与 AI 局部改写
- 对比历史版本
- 锁定已确认片段
- 将剧本转换为分镜输入
- 支持导入已有剧本

剧本生成结果不得仅以不可解析的自由文本存在。系统应能够识别其结构，以支持后续场景拆分、时间估计和素材生产。

## 5.4 分镜规划

分镜是剧本与多媒体生产之间的核心业务对象。

每个分镜至少包含：

| 属性 | 说明 |
|---|---|
| Scene ID | 稳定业务标识 |
| Order | 分镜顺序 |
| Duration | 目标时长 |
| Narrative | 对应叙述内容 |
| Visual Description | 画面描述 |
| Visual Prompt | 素材生成提示词 |
| Audio Script | 旁白文本 |
| Style Reference | 风格及参考资产 |
| Transition | 转场方案 |
| Asset References | 关联图片、视频、音频 |
| Review Status | 人工确认状态 |

分镜支持增加、删除、拆分、合并、重新排序和局部生成。

对于同一分镜，可以维护多个候选视觉方案，供用户比较和选择。

当分镜变化时，系统应明确提示哪些素材可能失效，而不是直接删除原有成果。

## 5.5 视觉素材生产

平台支持生成、导入和复用视觉素材。

长期能力包括图片生成、图片编辑、参考图驱动生成、图生视频、文生视频、已有视频处理以及静态素材动态化。

用户可以配置模型、风格、分辨率、画面比例、生成数量和其他模型支持的参数。

生成结果应支持预览、候选比较、收藏、替换、重试和关联分镜。

平台必须保存素材来源、生成配置、模型信息、版本及必要的使用权限信息。

## 5.6 音频生产

音频模块支持文字转语音、旁白管理、音频上传、音效和背景音乐处理。

主要能力包括：

- 选择语言与发音人
- 配置语速及供应商支持的表达参数
- 按分镜或段落生成旁白
- 支持局部重新配音
- 提供音频时长与波形信息
- 管理背景音乐和音效
- 对多个音轨进行音量及时间编排
- 保留音频来源和授权信息

不同供应商的特有参数通过能力描述进行扩展，不强制要求所有模型具有完全一致的功能。

## 5.7 字幕生产

平台提供字幕生成、导入、编辑和导出能力。

字幕可以根据旁白文本及时间信息生成，也可以从已有音频识别得到。

支持：

- 句级字幕
- 在具备可靠对齐能力时支持词级字幕
- 字幕时间轴调整
- 样式模板
- 多语言字幕轨道
- 字幕预览
- 字幕文件导出
- 视频硬字幕
- 视频软字幕（受目标格式支持情况约束）

字幕始终作为可以独立编辑和版本管理的资产，而不是只能通过重新渲染修改的固定画面。

## 5.8 视频编排与合成

视频编排模块负责将媒体资产转换为可以渲染的作品定义。

Composition 至少包含：

- 画布规格
- 帧率与输出比例
- 视频轨道
- 音频轨道
- 字幕轨道
- 素材时间位置
- 裁剪与缩放方式
- 转场定义
- 音量设置
- 输出格式
- 渲染参数

平台应允许用户在有限范围内调整时间轴和素材顺序，并预览编排结果。

合成引擎将 Composition 解析为可执行的媒体处理任务。

产品能力不应与 FFmpeg 命令本身绑定，具体渲染实现可以替换或扩展。

## 5.9 预览、审核与交付

用户可以在正式导出前查看预览结果。

预览与最终渲染可以采用不同质量配置，以减少不必要的等待和成本。

审核能力包括：

- 分镜审核
- 素材确认
- 作品整体审核
- 审核意见
- 驳回与修改
- 审核历史
- 已确认版本锁定

作品交付支持下载、导出资产包、保存历史版本和通过 API 获取交付结果。

未来可扩展发布平台集成，但发布失败不应影响作品本身的完成状态。

---

# 第六章 用户与组织管理

## 6.1 账户体系

平台提供注册、登录、身份验证、找回账号、个人资料及账户安全管理。

用户身份与项目、作品、工作流和执行记录建立关联。

## 6.2 工作空间

Workspace 是组织资源、权限和成本的边界。

一个用户可以属于多个工作空间。

工作空间包含：

- 成员
- 项目
- 共享素材
- 工作流模板
- 模型配置
- 资源配额
- 预算
- 审计记录

## 6.3 权限管理

系统采用基于角色的权限管理，并保留未来进行资源级授权的扩展能力。

典型角色包括：

| 角色 | 主要权限 |
|---|---|
| Owner | 工作空间与所有资源管理 |
| Admin | 成员、配置和资源管理 |
| Editor | 创建、修改和执行内容生产任务 |
| Reviewer | 查看内容并执行审核 |
| Viewer | 查看授权资源 |
| Operator | 管理任务执行和运行状态 |

权限必须在服务端执行校验，前端隐藏操作入口不构成权限控制。

## 6.4 协作要求

支持项目成员分工、评论、审核指派和变更记录。

对于多人编辑同一资源的情况，系统必须提供冲突处理机制，避免静默覆盖。

实时多人协同编辑可以作为进一步增强的交互方式，但多人操作的数据一致性从产品模型建立时就必须考虑。

---

# 第七章 项目与作品管理

## 7.1 项目管理

项目是围绕某一创作目标组织内容和操作的业务容器。

主要功能：

- 创建项目
- 编辑项目基本信息
- 项目归档
- 复制项目
- 关联模板
- 配置默认创作参数
- 管理成员
- 查看执行历史
- 查看资产和作品
- 查看项目使用量及成本

项目状态用于表达业务进展，任务状态用于表达系统执行情况，两者应当区分。

## 7.2 作品管理

一个项目可以包含多个独立作品。

例如，一个品牌宣传项目可以同时生成横屏版、竖屏版和多语言版本。

作品应当支持：

- 独立命名
- 版本管理
- 预览
- 比较
- 审核
- 下载
- 归档
- 恢复历史版本

## 7.3 版本管理

版本管理贯穿剧本、分镜、素材、工作流和作品。

系统至少需要区分：

**草稿版本：** 用户持续修改的内容。

**已确认版本：** 可作为后续生产依据的内容。

**执行快照：** 某次生成任务实际使用的输入和配置。

**交付版本：** 已完成并可下载的作品成果。

当用户编辑当前版本时，既有运行实例不应被隐式改变。

用户可以基于旧版本创建新的生产分支，而不破坏历史结果。

---

# 第八章 素材与文件管理

## 8.1 统一资产模型

所有可复用的媒体文件都作为 Asset 管理，包括图片、视频、音频、字幕、文档及衍生文件。

资产不仅保存文件地址，还应保存元数据和业务关系。

## 8.2 资产元数据

至少包含：

- 资产标识
- 所属工作空间
- 所属项目
- 资产类型
- 文件格式
- 文件大小
- 内容校验值
- 存储位置
- 创建来源
- 生成模型及参数
- 创建时间
- 分辨率、时长等媒体属性
- 关联分镜及作品
- 版本
- 使用授权或来源声明
- 生命周期状态

## 8.3 文件操作

支持分片或可恢复上传、大文件下载、预览、校验、导入、复制、归档和删除。

文件处理采用对象存储抽象，具体服务提供商不应成为业务逻辑的一部分。

## 8.4 资产生命周期

资产需要区分：

- 临时资产
- 已保存资产
- 被作品引用的资产
- 已归档资产
- 待删除资产

任何仍然被有效版本或正在运行的任务引用的资产，都不能仅因某个项目页面操作而直接物理删除。

系统应具备引用关系检查、保留策略和延迟清理机制。

## 8.5 素材复用

用户可以跨项目复用已授权素材。

素材检索支持名称、类型、标签、项目、生成时间及其他元数据。

长期可提供内容语义检索和相似素材发现，但需要明确其数据与隐私边界。

---

# 第九章 AI 模型管理

## 9.1 模型管理目标

构建统一的模型能力入口，使创作流程与供应商 API 解耦。

平台应允许同时接入云端模型、自建推理服务和其他符合接口约定的模型服务。

## 9.2 Provider 管理

管理供应商信息、接口地址、认证方式、服务状态、速率限制和能力配置。

API 凭证必须加密存储并限制访问。

普通用户不应获得其他用户或组织的凭证。

## 9.3 模型能力管理

模型按能力描述，而非仅凭名称分类。

能力类型包括：

- 文本生成
- 结构化文本生成
- 图片生成
- 图片编辑
- 视频生成
- 语音合成
- 语音识别
- 多模态理解
- 文本向量化
- 其他自定义能力

一个模型可以具有多个能力。

## 9.4 统一调用契约

业务层根据能力类型提交请求。

模型适配器将统一请求转换为供应商特定格式，并将返回结果映射为标准化输出。

无法标准化的特殊功能通过扩展参数声明。

平台必须保留供应商原始错误信息，供诊断使用，但不能直接将敏感信息暴露给普通用户。

## 9.5 模型选择策略

用户可以显式指定模型，也可以使用平台策略选择。

策略可考虑：

- 任务能力要求
- 输入输出格式
- 用户偏好
- 成本限制
- 服务可用性
- 质量配置
- 区域与合规要求

不得假设所有模型之间能够无损替换。

对于依赖特定模型行为的工作流，切换模型时需要提示可能的兼容性影响。

## 9.6 模型失败与降级

平台可以配置失败重试、延迟执行或备用模型策略。

涉及模型切换时，需要考虑结果差异和成本影响。

在可能显著改变内容质量、风格或预算的情况下，应由用户明确授权降级策略。

---

# 第十章 工作流管理

## 10.1 工作流定义

Workflow 是对一个生产过程的结构化定义。

工作流描述：

- 节点
- 输入与输出
- 依赖关系
- 执行条件
- 参数
- 超时策略
- 重试策略
- 错误处理策略
- 人工审核步骤
- 最终输出

工作流采用有向无环图（DAG）表示执行依赖。

## 10.2 工作流节点类型

| 节点类型 | 用途 |
|---|---|
| Input | 接收输入 |
| AI Generation | AI 模型生成 |
| Transform | 数据结构转换 |
| Media Processing | 多媒体处理 |
| Condition | 条件分支 |
| Parallel | 并行执行组织 |
| Join | 依赖汇合 |
| Human Approval | 人工审核 |
| External Request | 外部系统调用 |
| Output | 结果输出 |
| Subworkflow | 调用子工作流 |

节点拥有明确的输入和输出契约。

节点连接必须经过类型和依赖校验。

## 10.3 工作流可视化编辑

提供可视化 DAG 编辑器，允许用户：

- 添加和删除节点
- 建立依赖关系
- 配置节点参数
- 选择模型
- 设置条件
- 配置错误处理
- 保存模板
- 校验工作流
- 执行测试
- 查看运行状态
- 查看节点输入与输出

编辑器的可视化布局与工作流语义定义应当区分。

## 10.4 工作流合法性校验

保存或发布工作流前，应检查：

- 是否存在非法环路
- 节点类型是否有效
- 必填输入是否满足
- 输入输出类型是否兼容
- 依赖引用是否存在
- 资源或模型能力是否可用
- 是否包含无法到达的必要节点
- 输出定义是否完整

校验结果需要指出具体节点、问题原因和建议处理方式。

## 10.5 工作流版本

工作流支持草稿、发布和版本管理。

已发布的工作流版本不可被原地修改。

工作流执行时绑定确定的版本和输入快照。

修改模板不会影响正在运行或已经完成的实例。

## 10.6 动态工作流

对于分镜数量等只能在运行时确定的情况，平台应支持受控的动态节点展开。

例如剧本生成后得到 12 个分镜，系统可以根据工作流中定义的映射规则创建 12 个素材任务。

动态展开必须具有：

- 明确的展开来源
- 规模限制
- 稳定的节点关联
- 可追踪的依赖关系
- 可重复恢复的执行语义

不允许任务执行器未经授权任意修改运行图结构。

## 10.7 人工审核节点

人工审核属于工作流的一种正常执行状态，而不是任务失败。

工作流可以等待用户确认后继续执行。

审核等待应支持通知、超时策略、授权检查及后续恢复。

---

# 第十一章 工作流运行与任务系统

## 11.1 运行实例

一次 WorkflowRun 表示对某个工作流版本及确定输入的一次执行。

包含：

- 执行标识
- 工作流版本
- 所属用户及项目
- 输入快照
- 当前状态
- 已完成节点
- 待执行节点
- 执行时间
- 成本及资源消耗
- 最终输出
- 错误和执行历史

## 11.2 工作流状态

建议业务语义包含：

CREATED、RUNNING、WAITING、PAUSED、CANCELING、CANCELED、SUCCEEDED、FAILED。

其中 WAITING 用于表示等待人工确认或外部事件。

运行中的状态变化必须受到明确规则约束。

## 11.3 任务生命周期

Task 表示可被独立执行和调度的工作单元。

任务可能经历：

PENDING → READY → QUEUED → RUNNING → SUCCEEDED。

对于失败、取消和超时情况，可以进入 FAILED、RETRY_WAIT、CANCELED 或其他明确定义的状态。

依赖未满足的任务不得提前执行。

存在无法满足的必要依赖时，任务应被标记为 BLOCKED，或通过明确的失败传播规则结束。

## 11.4 执行尝试

TaskAttempt 记录每次真实执行行为。

一个任务可能产生多个尝试，但必须有明确的有效结果认定规则。

每次尝试记录：

- Worker
- 开始和结束时间
- 尝试序号
- 租约或执行令牌
- 执行日志
- 错误分类
- 输出资产
- 资源消耗

## 11.5 重试

重试策略至少支持：

- 最大尝试次数
- 固定或指数退避
- 随机抖动
- 按错误类型判断是否重试
- 最大重试时间窗口
- 用户手动重试
- 耗尽重试次数后的处理方式

重试必须避免形成无限执行循环。

## 11.6 局部重新生成

用户可针对一个节点、分镜或素材触发局部重新生成。

系统应根据依赖关系计算可能受影响的后继结果。

对于已经确认或锁定的节点，不能未经用户确认就覆盖。

局部重新执行应产生新的执行记录，并保持原始版本可追溯。

## 11.7 取消与暂停

取消需要支持协作式终止。

已开始的外部服务调用不一定能够被立即取消，因此系统需区分取消请求、实际执行终止与费用是否已经产生。

暂停工作流不应默认中断所有正在进行的任务。

平台应根据节点能力和运行策略选择安全的暂停边界。

## 11.8 任务幂等和结果一致性

分布式环境中不能假设任务恰好执行一次。

系统应以至少一次执行的可能性进行设计，通过执行标识、任务租约、原子状态变更和结果提交约束，避免重复执行造成逻辑上的重复交付。

对于 AI 推理这类可能产生不可逆成本的外部操作，幂等机制能够控制内部结果提交，但无法保证第三方不会重复计费。

产品必须能够记录和呈现这类情况。

---

# 第十二章 分布式调度与 Worker 管理

## 12.1 调度目标

任务调度系统需要同时满足：

- 正确执行任务依赖
- 高效利用计算资源
- 控制外部供应商限制
- 避免单用户独占资源
- 支持任务优先级
- 支持高负载下的稳定运行
- 允许执行节点动态扩缩容
- 处理机器和服务故障

## 12.2 职责边界

工作流引擎负责判断哪些任务满足执行条件。

调度器负责决定何时分配可执行任务以及由哪类资源执行。

Worker 负责具体执行。

这种边界使 DAG 业务逻辑与资源调度策略保持相对独立。

## 12.3 任务分类

系统支持不同任务类型，包括：

- 外部 AI API 调用
- CPU 密集型媒体处理
- GPU 推理任务
- IO 密集型文件操作
- 网络传输任务
- 普通数据处理任务

每个任务应声明执行能力需求、资源要求及超时策略。

## 12.4 资源管理

平台统一管理：

- CPU
- 内存
- GPU 或显存
- 并发执行槽位
- 外部 API 请求配额
- 模型 Token 配额
- 带宽及其他受限资源

资源调度必须同时考虑任务声明和实际可用资源。

## 12.5 调度策略

支持按业务需要配置：

- FIFO
- 优先级调度
- 不同用户或工作空间之间的公平分配
- 按能力匹配
- 按资源要求匹配
- 供应商级限流
- 工作空间级并发限制
- 系统级资源限制

长期可以引入加权公平调度和任务配额预留。

调度策略应当可以调整而不改变工作流业务定义。

## 12.6 Worker 生命周期

Worker 应具备：

- 注册
- 能力上报
- 资源上报
- 任务领取
- 执行
- 进度报告
- 任务完成报告
- 心跳
- 租约续期
- 优雅退出
- 故障恢复

Worker 应具有唯一身份和可追踪的运行实例标识。

## 12.7 任务租约

执行任务需要获得有时效的执行权。

系统通过任务租约判断当前哪次执行拥有有效结果提交资格。

当租约失效时，系统可以重新分配任务。

迟到的旧执行结果不得覆盖已经被更新执行版本确认的结果。

## 12.8 Worker 故障恢复

当 Worker 离线或任务租约过期时，系统应判断任务是否可以重新调度。

对于支持安全重试的任务，可以生成新的执行尝试。

对于可能存在不可逆副作用的任务，应优先进行执行结果核对，再决定是否重试。

## 12.9 系统恢复

调度器、工作流引擎或消息基础设施重启后，应能够根据持久化状态恢复未完成任务。

持久化任务状态必须能够与消息传递状态进行核对。

不能仅依靠内存队列作为任务唯一事实来源。

---

# 第十三章 资源、成本与配额

## 13.1 资源可见性

用户和管理员应能够查看任务消耗的资源类型、执行时间以及相关成本。

## 13.2 成本计算

平台应记录：

- 模型调用次数
- Token 使用量（适用时）
- 图片和视频生成次数
- 音频生成用量
- 媒体处理资源消耗
- 存储及传输使用量
- 供应商返回的计费信息

成本应区分估算值与最终确认值。

## 13.3 项目预算

用户可以配置预算上限和提醒阈值。

在启动可能超过预算的任务前，系统应给出预估并按照策略要求确认或拒绝执行。

## 13.4 配额管理

支持：

- 用户配额
- 工作空间配额
- 项目预算
- 模型调用配额
- 并发配额
- 存储配额
- Worker 资源限制

## 13.5 成本优化

系统可以提供素材复用、避免不必要的重复运行、低成本预览和模型选择建议。

任何可能明显降低质量的自动成本优化行为都需要受策略约束。

---

# 第十四章 用户界面与交互体验

## 14.1 产品导航

建议采用以用户任务为中心的导航体系：

**工作空间、项目、创作工作台、素材库、作品、工作流、执行中心、模型与资源、系统设置。**

普通创作者主要使用项目、工作台、素材和作品。

高级用户可进入工作流和执行中心。

管理员根据权限进入模型、资源和系统管理页面。

## 14.2 创作工作台

创作工作台是产品最重要的交互入口。

建议包含：

**左侧：** 项目结构、剧本、分镜、资产、作品和历史版本。

**中央：** 当前编辑对象、分镜画布、素材预览或时间轴。

**右侧：** AI 生成参数、模型、风格、操作和属性配置。

**底部或独立面板：** 执行进度、生成日志和相关任务状态。

具体布局需经过交互验证，不强制要求所有页面同时显示全部功能。

## 14.3 创作模式

提供两个主要模式。

**引导模式：** 用户通过主题和简单参数完成创作，系统提供默认流程和必要确认步骤。

**专业模式：** 用户能够详细控制分镜、模型参数、工作流和执行策略。

两种模式操作同一套业务对象，避免形成两套互不兼容的数据模型。

## 14.4 执行反馈

长时间运行的任务必须持续提供反馈。

用户至少应当知道：

- 当前进行到哪个生产阶段
- 哪些任务已经完成
- 哪些任务正在等待
- 哪些任务发生错误
- 是否需要人工操作
- 可以执行哪些恢复操作

当无法可靠预测剩余时间时，不应显示没有事实依据的倒计时。

## 14.5 错误体验

普通用户应看到可理解的错误描述及解决方式。

技术用户可以进一步查看任务尝试、日志、外部错误代码和追踪信息。

错误不能只显示“生成失败”。

## 14.6 操作安全

删除、覆盖、取消和批量重跑等可能产生较大影响的操作必须提供适当的保护。

系统应明确区分撤销、恢复、重新生成以及永久删除。

# 第十五章 开放平台与扩展能力

## 15.1 开放 API

平台提供稳定、具有版本管理的 API，覆盖：

- 项目管理
- 资产管理
- 工作流定义
- 工作流执行
- 任务查询
- 作品交付
- 模型和能力查询
- 使用量查询

## 15.2 Webhook

支持在工作流完成、失败、取消、进入人工审核等事件发生时通知外部系统。

Webhook 应具备签名校验、失败重试、事件标识和重复消息处理建议。

## 15.3 自定义节点

允许开发者按照标准契约扩展节点执行能力。

节点声明输入、输出、配置、资源需求、错误语义及执行方式。

需要对第三方代码的网络、文件系统、权限和资源消耗进行隔离与限制。

## 15.4 工作流模板

工作流模板可由平台提供，也可由用户创建和共享。

模板应包含版本、输入说明、依赖能力和适用场景。

## 15.5 外部集成

长期支持对接素材库、企业业务系统、消息通知系统、云存储和内容发布平台。

集成以标准化连接能力为基础，不应侵入工作流引擎的核心语义。

# 第十六章 可观测性与运营管理

## 16.1 执行中心

统一提供工作流、任务、执行尝试和 Worker 的运行视图。

支持按照项目、用户、工作空间、状态、任务类型、模型和时间范围筛选。

## 16.2 日志管理

记录：

- 任务创建与状态变化
- Worker 执行事件
- 外部服务调用结果
- 错误与重试
- 工作流依赖变化
- 文件处理结果
- 重要人工操作

日志应根据用户权限展示，并避免泄露密钥及敏感原始内容。

## 16.3 指标系统

关注：

- 工作流完成率
- 任务成功率
- 排队等待时间
- 任务执行时间
- 工作流端到端耗时
- 重试次数及比例
- Worker 使用率
- 资源池容量
- 供应商错误率
- 用户生产成本

## 16.4 分布式追踪

一个工作流运行应具有可关联的追踪上下文。

系统能够关联工作流、节点、任务、执行尝试、模型调用和素材输出，以支持复杂故障排查。

## 16.5 告警管理

管理员能够针对异常失败率、长时间排队、Worker 离线、供应商限流和资源不足等情况配置告警。

# 第十七章 安全、隐私与治理

## 17.1 身份认证与授权

所有涉及用户数据、模型凭证、工作流执行和资产访问的操作都需要身份及权限验证。

## 17.2 凭证管理

供应商 API Key 等敏感凭证必须进行安全存储、访问控制、轮换及操作审计。

凭证不能明文出现在常规日志、前端响应和可下载执行记录中。

## 17.3 数据隔离

不同用户及工作空间之间的数据和资源访问必须遵守隔离规则。

Worker 在执行任务时只能访问该任务被授权使用的输入和资源。

## 17.4 用户数据治理

平台应明确：

- 数据保存周期
- 用户删除行为
- 工作流日志保存范围
- 向外部模型传输的数据
- 资产共享权限
- 作品导出能力
- 数据备份与恢复策略

## 17.5 内容与版权

平台应允许用户记录参考素材来源、使用授权和作品相关声明。

应明确向用户说明第三方模型输出、上传素材和配乐可能涉及的使用限制。

不能因为内容由 AI 生成，就默认所有输出在所有场景下具有不受限制的商业使用权。

## 17.6 内容安全

根据使用场景，平台可提供输入内容检查、生成结果审核、违规风险提示和人工复核机制。

内容治理不应只依赖单个外部模型服务商。

## 17.7 审计能力

成员权限变化、密钥修改、预算变更、资产删除和重要系统配置修改，应具有可查询的审计记录。

# 第十八章 非功能需求

## 18.1 性能

平台应支持多个工作流并发运行，并能够随资源容量增加扩展任务处理能力。

性能目标必须依据具体任务类别、外部供应商配额和部署资源进行验证。

不能将“同时提交 100 个视频项目”等同于“同时执行所有 2000 个子任务”。

## 18.2 可用性

关键业务状态必须持久化。

服务进程或 Worker 重启不应导致已确认的工作流和资产数据丢失。

部署环境需要具备健康检查、重启恢复、备份和监控机制。

## 18.3 可靠性

应重点保证：

- 任务不会因为消息丢失而永久消失
- 非法状态转移受到阻止
- 重复执行不会覆盖有效结果
- 失败能够明确归因
- 恢复流程具有可测试性
- 工作流能够识别永久失败的依赖
- 长时间等待不会被误判为正常执行完成

## 18.4 可扩展性

业务能力、工作流节点和执行资源应能够独立演进。

允许通过增加 Worker 或外部资源池提高吞吐能力。

## 18.5 可维护性

核心领域必须具有清晰的模块边界。

工作流定义、执行状态和调度逻辑不应混在同一业务对象内。

系统应支持自动化测试、配置管理、数据库迁移和向后兼容策略。

## 18.6 数据一致性

工作流和任务的关键状态变化必须满足明确的一致性规则。

对于跨数据库、队列、对象存储和外部 API 的操作，不假设存在统一的分布式事务。

应通过可靠消息发布、状态核对、幂等处理以及必要的补偿机制实现可恢复的一致性。

## 18.7 易用性与无障碍

关键操作需要清晰的文字提示、状态反馈和键盘可访问能力。

平台应考虑不同屏幕尺寸，但复杂工作流编辑和视频编排的主要工作环境以桌面端为优先。

# 第十九章 产品核心指标体系

## 19.1 北极星指标

建议使用：

**每周成功交付并被用户实际采纳的作品数量。**

“成功交付”不等于系统自动生成了一个文件。

需要综合考虑用户是否完成确认、下载、发布或其他能够体现成果被接受的行为。

这可以避免单纯追求生成次数而忽略质量。

## 19.2 创作效率指标

- 从创建项目到首次可预览作品的时间
- 从创建项目到最终交付的时间
- 单作品人工操作次数
- 素材复用率
- 模板复用率
- 局部重新生成占全部重新生成的比例

## 19.3 质量指标

- 用户首次生成结果接受率
- 分镜确认率
- 作品审核通过率
- 单作品平均修改轮次
- 交付后重新修改比例

## 19.4 平台可靠性指标

- Workflow 成功率
- Task 成功率
- 不可恢复失败率
- 任务平均排队时间
- 故障后恢复时间
- 状态一致性异常次数
- 任务重复有效提交次数

## 19.5 商业与成本指标

- 单个成功作品的平均生成成本
- 每用户或工作空间资源消耗
- 预算超限事件
- 各模型供应商成本分布
- 无效生成成本比例

## 19.6 指标解释原则

所有指标必须有统一统计口径。

例如工作流失败率，需要明确用户取消、人工审核等待、外部供应商故障和真实系统故障是否被纳入。

没有统一分母和时间窗口的指标，不应直接用于产品质量判断。

# 第二十章 关键业务规则

## 20.1 资产不因任务重试被覆盖

新的生成尝试创建新的结果记录，只有通过有效结果提交机制才能成为当前选用版本。

## 20.2 工作流运行采用确定配置

一次运行绑定工作流版本、输入快照和相关配置快照。

## 20.3 人工确认内容优先

已确认的剧本、分镜及素材不得被自动工作流静默覆盖。

## 20.4 依赖满足后才能执行

节点是否 Ready 由工作流执行规则决定，不由 Worker 自行判断。

## 20.5 失败处理必须显式

遇到错误时，系统依据节点策略执行重试、跳过、等待人工处理或终止。

不得默默忽略关键节点失败。

## 20.6 成本行为必须可解释

对于可能产生额外费用的重试、模型切换和批量重新生成，系统必须有明确的预算及执行策略。

## 20.7 删除行为遵循引用关系

被有效作品、版本或运行实例依赖的资产，应按照保留策略处理。

## 20.8 执行和业务状态分离

一个任务执行成功，不代表作品已经通过审核或完成交付。

## 20.9 外部系统不作为唯一事实来源

对于平台能够控制的工作流和任务状态，应保有自己的持久化记录与恢复机制。

## 20.10 所有重要执行行为可追踪

用户可以从作品定位到素材，再定位到生成工作流、具体任务、执行尝试和相关模型配置。

# 第二十一章 核心业务验收场景

下列场景属于长期产品必须具备的端到端业务能力，不等同于要求在第一次发布时全部完成。

## 场景一：完整自动生产

用户创建创作需求，启动预设工作流。

系统生成剧本、分镜、视觉素材、配音、字幕及最终视频。

最终作品可以预览、下载和归档。

**验收重点：** 内容链路完整，输入输出可追踪，最终产物有效。

## 场景二：人工精细修改

用户修改第三个分镜并重新生成图片。

系统保留其他分镜的确认状态和可复用资产，对受影响结果进行必要更新。

**验收重点：** 局部修改正确、依赖影响可解释、历史资产未丢失。

## 场景三：批量生产

用户基于模板批量创建多个视频生成实例。

系统根据配额、资源和供应商限制执行任务。

**验收重点：** 不因瞬时提交大量任务而失控，用户能够分别查看每个作品的结果。

## 场景四：Worker 异常退出

某个执行图片或视频处理任务的 Worker 意外退出。

系统检测任务租约失效，并依据任务类型恢复执行。

**验收重点：** 无永久丢失任务、旧执行结果不覆盖新结果。

## 场景五：外部模型限流

模型供应商返回可识别的限流响应。

系统根据限流策略暂停、延迟或重新安排受影响任务。

**验收重点：** 不进行无限重试，不影响无关资源池的正常处理。

## 场景六：工作流运行中修改模板

用户编辑并发布了新的工作流版本。

原有运行继续遵循其绑定的版本，新运行使用新版本。

**验收重点：** 运行确定性与历史可重现性。

## 场景七：管理员恢复系统

调度服务重启后，系统核对未完成任务及执行租约。

**验收重点：** 工作流正确恢复，无不可解释的重复提交或状态丢失。

## 场景八：跨项目素材复用

用户在新项目中引用原项目已有素材。

**验收重点：** 权限正确、资产引用稳定、删除行为安全。

## 场景九：团队审核

编辑人员提交作品审核，审核人员驳回某个分镜。

系统保留审核意见，并允许修改后重新提交。

**验收重点：** 审核历史完整、版本关系明确、权限有效。

## 场景十：开放 API

外部应用通过 API 启动工作流，接收完成事件并获取输出资产。

**验收重点：** 认证、重复请求处理、事件通知和执行状态一致。

# 第二十二章 长期产品演进策略

## 22.1 能力建设原则

MediaFlow 的演进以长期完整产品为目标，采取逐步交付、持续验证的方式。

每次交付都应形成可使用、可维护并能继续扩展的产品能力。

短期实现可以简化，但不得随意改变长期领域模型的核心语义。

## 22.2 第一阶段：建立完整的创作业务闭环

建设项目、剧本、分镜、素材、基本生成流程和视频交付能力。

重点验证用户真实的创作行为，以及多媒体生产中哪些环节最需要控制和复用。

## 22.3 第二阶段：建立可靠工作流能力

完善 DAG、工作流版本、任务状态、失败恢复、局部重跑和执行可视化。

重点解决复杂生产过程的可控性与可靠性。

## 22.4 第三阶段：提升生产规模和资源效率

完善分布式 Worker、资源调度、公平性、供应商限流、使用量统计和预算控制。

重点验证平台在高任务量和复杂故障环境中的运行能力。

## 22.5 第四阶段：建设专业生产与协作能力

强化时间轴、内容审核、资产复用、团队协作、品牌模板和内容生产管理。

重点提升专业用户的效率和生产质量。

## 22.6 第五阶段：开放平台生态

完善 API、Webhook、节点扩展、外部集成、工作流模板共享和更广泛的自动化能力。

推动 MediaFlow 从完整的多媒体生产工具演进为开放的 AI 生产平台。

## 22.7 阶段验收原则

阶段结束的判断依据不是功能开发数量，而是：

- 用户目标是否可以被完整实现
- 关键业务流程是否可用
- 数据模型是否具备持续演进能力
- 系统是否满足当前实际使用规模的可靠性要求
- 后续能力能否在已有体系上自然扩展

# 第二十三章 产品风险与决策事项

## 23.1 模型质量不稳定

不同供应商、模型版本和参数可能导致生成结果差异。

应通过结果版本化、候选比较、人工确认和模型配置快照降低影响。

## 23.2 AI 生成成本不可预测

视频生成、重复推理和失败重试可能产生较高费用。

应建立用量记录、成本预估、预算限制和重试策略。

## 23.3 长时间任务的可靠性风险

网络中断、进程退出、消息重复和状态竞争都可能影响结果。

必须建立持久化状态、执行租约、幂等提交和恢复机制。

## 23.4 产品复杂度过高

同时面向普通创作者和高级开发者，容易造成界面复杂。

应采用分层体验，在保持同一业务模型的前提下提供不同程度的控制入口。

## 23.5 第三方供应商依赖

外部模型的接口、价格、配额和可用性可能变化。

需要统一适配层、能力声明、版本管理和兼容性策略。

## 23.6 素材与知识产权风险

生成素材、参考图片、音乐和语音可能涉及使用授权及权利归属。

需要素材来源记录、用户声明、供应商条款提示和适用的合规流程。

## 23.7 技术平台建设偏离用户价值

工作流、调度器和 Worker 等底层系统具有工程复杂度，但不能仅为了技术展示而无限扩展。

每项基础设施建设都应能够映射到明确的用户收益，例如更高成功率、更低等待时间、更可控的成本或更方便的修改能力。

# 第二十四章 产品最终形态

MediaFlow 长期应形成四个相互支撑的核心产品体系。

## 24.1 MediaFlow Studio

面向创作者的多媒体创作环境。

包含创作需求、剧本、分镜、素材、时间轴、预览、审核及交付。

其目标是提供完整、流畅且专业程度可逐步提升的创作体验。

## 24.2 MediaFlow Workflow

面向内容生产流程的定义与管理平台。

包含可视化 DAG、工作流模板、版本管理、人工审核、运行追踪及局部重跑。

其目标是让复杂生产过程具备可配置性、可理解性和可复用性。

## 24.3 MediaFlow Runtime

面向复杂任务的执行基础设施。

包含任务状态、调度、Worker、资源池、限流、失败恢复、幂等执行及可观测性。

其目标是让多步骤生产流程能够在复杂环境下持续可靠运行。

## 24.4 MediaFlow Platform

面向开发者、团队和组织的开放能力平台。

包含模型管理、API、Webhook、权限、预算、节点扩展和第三方集成。

其目标是让 MediaFlow 能够融入更广泛的内容生产与 AI 自动化生态。

这四个体系不一定需要分别部署为独立服务，但在产品概念、模块责任和接口设计上应当保持明确边界。

# 第二十五章 总结与产品决策基线

MediaFlow 的长期竞争价值不应该建立在某一个模型的生成效果或某一项视频制作功能之上。

模型可能迭代，供应商可能变化，新的内容形态也会不断出现。

MediaFlow 真正需要长期积累的是三类能力：

**第一，理解和组织内容生产。** 将用户的创作目标转化为结构化、可修改、可复用的生产对象。

**第二，控制复杂生产过程。** 将不同模型和处理工具组织成具有依赖关系、明确状态和可恢复语义的执行流程。

**第三，持续交付可信赖的结果。** 让用户能够明确知道系统做了什么、使用了哪些资源、生成了哪些资产，以及结果如何修改和复现。

基于这些原则，MediaFlow 应被建设成一个真正能够长期使用和持续演进的 AI 多媒体生产产品。

**最终产品定位：**

MediaFlow 是一个以创作目标为中心，以结构化内容和多媒体资产为基础，以工作流编排和可靠执行为核心能力，面向个人、团队和开发者的开放式 AI 多媒体生产平台。

**最终判断标准：**

MediaFlow 不仅要能够生成作品，还应当让用户有能力管理作品的整个生产生命周期，并让复杂的自动化生产过程变得可靠、透明、可控和可扩展。
