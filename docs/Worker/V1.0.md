## 0. 本文边界与冻结决策

本文只规定 Worker 如何安全地接受、运行、上报和结束一个已经满足工作流依赖的 Task；不重述 PRD 创作需求、DAG 编译算法或 Scheduler 公平算法。

**冻结约束：**

1. Workflow Engine 决定节点何时 READY；Scheduler/Task Execution 授予执行权；Worker 只执行已获授权的 Task。
2. **Worker 永远不能直接写** `workflow_runs`、`node_runs`、`tasks`、`task_attempts`、`resource_reservations`；写入统一经过控制面授权命令和事务。
3. 有效结果提交的线性化点是控制面的 **ResultCommit 数据库事务**，不是 Handler 返回，也不是对象上传完成。
4. 每次执行绑定 `(task_id, attempt_id, lease_epoch, lease_token, worker_session_id)`；租约过期后的旧结果不得夺回执行权。
5. 外部调用和对象上传不进入数据库长事务；数据库记录“授权与确认”，不假设第三方 API、对象存储和 PostgreSQL 之间存在原子事务。
6. **至少一次派发/可能重复执行**，**最多一个有效结果提交**；外部副作用和第三方计费不保证恰好一次。
7. Worker Session 心跳与 Task Lease 是两条独立的生命线；前者不代表后者仍有效。
8. 默认 Worker 主动拉取工作：Worker 向控制面请求 Claim，控制面在数据库事务中完成资源预留/Attempt 创建/Lease 授权；Queue 通知**不是执行授权**。
9. 对于未获新租约、会话 DRAINING/失效、取消已生效的任务，Worker 不应继续启动新的不可逆操作。
10. 结果与进度通信、资源计量、敏感信息处理必须可观测、可限流并支持多租户隔离。

**与 Scheduler v1.0 对齐：** 采用 `READY` 直接 Claim 的默认模式；`QUEUED` 仅在引入外部分发阶段时使用；RateLimit 的真实外部请求许可在 Provider API 调用前获取，不能用单纯 Claim 冒充 RPM/TPM 许可。

## 1. 术语与组件职责

| 术语 | 定义 | 状态所有者 |
|---|---|---|
| Worker | 具备一个或多个 Capability 的可执行进程或隔离单元 | Worker Management |
| WorkerSession | 一次进程启动的会话；重启产生新 SessionID | Worker Management |
| Handler | 单一任务类型的实际执行实现 | Worker Runtime |
| Task | 可调度的业务工作单元 | Task Execution |
| TaskAttempt | 一次具体执行与提交的记录 | Task Execution |
| Lease | 具有期限的执行授权；需续租 | Task Execution/Worker Management |
| Fencing Token | 服务端对当前执行代数的校验材料 | Task Execution |
| TaskEnvelope | 授予 Worker 的不可随意扩权的任务快照 | Control Plane |
| ResultManifest | 结果产物、校验、元数据、用量的声明 | Worker 提议；控制面验证 |
| ResourceReservation | Claim 时预留、结束时释放的执行资源 | Scheduler |
| Reconciler | 对账、恢复遗失通知、过期执行权和残留产物 | Control Plane |

```text
                   Workflow Engine (DAG)
                          │ Task READY
                          ▼
                Scheduler / Task Execution
                 │  Claim + Lease + Reservation (PG txn)
                 ▼
         Worker Runtime (WorkerSession)
          │       │       │        │
        LLM    Image     TTS     FFmpeg
          │       │       │        │
          └──────────┬─────────────┘
                     ▼
              Temporary Artifacts (S3)
                     │ ResultManifest
                     ▼
             ResultCommit Service (PG txn)
                     │ TaskCommitted Outbox
                     ▼
            Workflow Progression Consumer
```

**控制面 API 调用与数据库操作关系：** Worker → Worker API → Application Service → Repository；Handler 不感知调度数据库。

## 2. Worker 身份、注册与会话状态机

### 2.1 Worker 身份

- `worker_id`：逻辑工作节点身份，可通过配置或注册获得；不可作为安全凭据。
- `worker_session_id`：每次启动生成的唯一 ID（建议 UUID）；同一 Worker 重启不得重用旧 Session。
- `worker_auth`：独立的短期服务身份（mTLS 或可轮换服务令牌）；必须绑定 Worker 和允许的资源池。
- `capabilities`：例如 `ai.text.generate/v1`、`ai.image.generate/v1`、`media.ffmpeg.render/v1`；包含契约版本。
- `execution_environment`：平台、架构、容器镜像摘要、FFmpeg 版本、特性与资源上限。

### 2.2 WorkerSession 状态

| 当前状态 | 事件 | 下一状态 | 允许操作 |
|---|---|---|---|
| REGISTERING | 注册且授权成功 | ACTIVE | Claim、Heartbeat、Renew、Report |
| ACTIVE | 管理员 Drain / SIGTERM | DRAINING | 旧任务继续执行或取消；**禁止新 Claim** |
| ACTIVE | 心跳超时 / 认证撤销 | LOST | 不授予新 Claim；现有 Task Lease 按自身规则裁决 |
| DRAINING | 已无执行中 Attempt | CLOSED | 终止进程 |
| ACTIVE/DRAINING | 主动正常退出 | CLOSED | 关闭会话 |
| LOST | 旧会话恢复网络 | LOST | 不恢复旧会话的 Claim 资格；重新注册为新 Session |

`LOST` 不自动意味着所有关联 Attempt 已立即失效。只有 TaskLease 过期或被显式撤销后，才可重新分配；需避免瞬时误判导致重复计算。

### 2.3 注册握手

`RegisterWorker` 提交：`worker_id`、`session_id`、`software_version`、`protocol_versions`、`capabilities`、`resource_limits`、`runtime_info`。服务端校验身份/Pool 权限/协议版本，返回：`accepted_protocol_version`、`heartbeat_interval`、`max_parallelism`、`server_time`、`session_token` 或等价授权信息。**这些配置均需边界校验**。

建议状态心跳间隔 10 秒、Session 失联阈值 35 秒作为本地测试默认值；必须由服务端配置并允许调整，不是固定 SLO。服务端按数据库时钟判定租约，不能信任 Worker 本地墙上时钟。

## 3. 能力注册、资源声明与调度匹配

Worker 注册的 Capability 描述应含 `name`、`version`、`supported_input_schema_versions`、`output_schema_version`、`concurrency_limit`、`required_tools`。资源声明可以包含 CPU millicores、内存 bytes、GPU/VRAM、工作目录可用空间、已分配槽位。

- 静态资源上限决定准入，CPU 使用率、内存占用等动态观测**不能替代硬限制**。
- Worker 只公布已启用的 Handler；缺少所需二进制或依赖时拒绝对应 Capability 注册。
- Capability 升级须兼容发布版本；不能静默将 `media.ffmpeg.render/v1` 换成语义不兼容的执行器。
- Worker 的内部本地并发信号量只是第二道保护；**资源权威预留**发生在 Scheduler Claim 事务内。
- 最终本地资源限制依赖容器/cgroup/进程限制等机制；Go 并发池不是隔离机制。

## 4. TaskEnvelope 与协议版本

### 4.1 授权响应最小结构

```json
{
  "protocol_version": "1.0",
  "task_id": "uuid-task",
  "attempt_id": "uuid-attempt",
  "lease_epoch": 5,
  "lease_token": "opaque-secret-token",
  "worker_session_id": "uuid-session",
  "lease_expires_at": "2026-10-20T13:01:00Z",
  "task_type": "media.ffmpeg.render",
  "capability_version": "v1",
  "input_schema_version": 1,
  "input": {"composition_version_id": "uuid-comp"},
  "input_references": [{"asset_version_id": "uuid-asset"}],
  "limits": {"timeout_seconds": 1800, "max_output_bytes": 1073741824},
  "result_policy": {"result_manifest_version": 1},
  "correlation": {"workflow_run_id": "uuid-run", "node_run_id": "uuid-node"}
}
```

此示例使用占位标识符，不是可提交生产请求。真实协议使用经过校验的 UUID/令牌并通过安全传输保护租约凭据。`input` 不应包含明文 Provider Key；使用受限能力凭证或由控制面代发必要调用凭据。

### 4.2 版本与兼容性

- 控制面协商 `protocol_version`；未知主版本拒绝 Claim。
- 每个 TaskType 有独立输入/输出 Schema 版本。
- Worker 接受任务前再次验证 Capability、Schema、运行限制和受信输入引用。
- 需要读取长期资产时由控制面签发短期、最小权限的 URL 或通过受控下载代理；对外部 URL 限制目标网络与重定向。

### 4.3 重要幂等键

| 操作 | 识别方式 | 服务端行为 |
|---|---|---|
| Claim | `claim_request_id` + Session | 幂等返回同一授权或明确冲突，不重复创建 Attempt |
| Renew | `attempt_id,lease_epoch,lease_token` | 有效令牌续租；重复请求不能缩短租约 |
| Progress | `attempt_id,sequence` | 最多接受每个序号一次；允许丢弃过时进度 |
| Complete | `attempt_id,submission_id` | 相同清单哈希重复提交返回同一结果；内容不同返回冲突 |
| Fail | `attempt_id,failure_report_id` | 重复报告不再增加重试次数 |
| Session Heartbeat | `session_id,sequence` | 旧序号无状态回退 |

## 5. 完整执行协议与时序

```text
Worker       Control/Claim       PostgreSQL       Handler       S3          ResultCommit
  │ Register      │                │                │           │               │
  ├──────────────►│                │                │           │               │
  │ Session token │                │                │           │               │
  ◄───────────────┤                │                │           │               │
  │ Claim         │                │                │           │               │
  ├──────────────►├─ TX: Task+Attempt+Reserve ───►│           │               │
  ◄── Envelope ───┤                │                │           │               │
  ├────────────────────────────────► Execute Handler│           │               │
  │ Renew/Progress│                │                │           │               │
  ├──────────────►├─ CAS Renew ────►│                │           │               │
  │                │                │                ├─ upload ─►│               │
  │ Complete(Manifest)────────────────────────────────────────────────────────►│
  │                │                ◄───────── TX verify+commit+release ──────┤
  ◄────────────────────────────────────────── Committed/Rejected ─────────────┤
  │                │                │                │           │               │
```

### 5.1 Claim

1. Worker 以会话凭据发送 Claim 请求（包含能力及可用槽位提示）。
2. Claim Service 选择候选 Task，验证 WorkflowRun、Session、配额、资源池等资格。
3. 在一个 PostgreSQL 事务内锁定 Task、资源账户和必要的 Session Counter，增加 `lease_epoch`，创建 TaskAttempt 与资源 Reservation，将 Task 改为 RUNNING，并记录事件。
4. 数据库提交成功后返回不可伪造的 TaskEnvelope。
5. 响应丢失时，Worker 以原 `claim_request_id` 查询/重试，**禁止盲目再创建 Attempt**。

### 5.2 执行前验证

Worker 校验本地并发、协议版本、Handler 支持、输入大小限制、受限路径及取消状态；配置错误应报告 `NON_RETRYABLE_CONFIG_ERROR` 而不是重复执行。执行开始前先准备独立工作目录，不能跨 Task 共享可写临时文件。

### 5.3 Progress

进度是最佳努力观测，不能作为任务成功事实。`progress_sequence` 单调递增，支持阶段标识（`DOWNLOAD`,`GENERATE`,`UPLOAD`,`VERIFY`）；缺少可计算分母时报告阶段而非虚构百分比。进度写入应节流、合并，不为每个 FFmpeg 输出行建立 DB 事务。

### 5.4 Renew

Task Lease 续租**与 Session Heartbeat 分别上报**。建议服务端返回 `renew_after` 提示，Worker 在租期过半前续租，使用有界退避和抖动；实际间隔需考虑网络延迟与长期暂停。服务端用数据库时间判断有效性。

Renew 至少校验：`Task RUNNING`、当前 Attempt、`lease_epoch`、令牌哈希、匹配 Session、租约尚有效、取消/撤销策略许可。仅在满足条件时延长到 `max(existing_expiry, db_now + ttl)` 并使用 CAS 或行锁保证并发更新；拒绝后 Worker 应触发取消并且不再提交有效结果。

### 5.5 Complete

Handler 返回的文件仍处于**待提交**状态。Worker 上传临时产物并验证文件摘要，构造 ResultManifest，然后调用 `CompleteAttempt`。控制面先按资产、配额和业务策略验证结果，再执行有效 ResultCommit 事务。Worker 不应直接调用 WorkflowProgression；它由已确认事件驱动。

### 5.6 Fail

Worker 报告分类型错误，附诊断引用而非大量原始敏感内容。控制面决定终态或 RETRY_WAIT，不允许 Worker 自行指定 Task 为 SUCCEEDED/FAILED。重复 Fail 不增加 Attempt 或 Retry 计数。

## 6. Lease、Fencing 与丢失响应

**安全不变量：** 对同一个 Task，能够改变最终业务状态的提交只能来自当前有效 Attempt 和 LeaseEpoch。旧进程仍可能执行外部计算，但其结果不得被接受。

- LeaseToken 应是不可猜测的高熵随机值；数据库只保存安全的验证材料（例如哈希），日志中绝不输出完整令牌。
- `lease_epoch` 在每次新的执行授权下增加，不能由客户端提供；64 位整数溢出应视为不可恢复数据异常。
- `worker_session_id` 绑定 Attempt，不能跨重启会话沿用。
- 续租 HTTP 超时不能立刻视为续租失败；应查询授权状态或重试，但在未知状态下避免启动新的不可逆操作。
- 租约失效后的后台 Handler/子进程需要尽快终止；若无法终止，应隔离其产物并拒绝提交。
- **数据库提交已成功但 Worker 没收到响应**：`GetAttemptCommitStatus(submission_id)` 必须可以返回原有效提交结果。

### 6.1 最小数据库谓词（示意，不是完整迁移）

```sql
-- 核心校验须在统一事务中执行，令牌以安全哈希验证；
-- 这里省略 join 与资源释放细节，仅表达线性化条件。
SELECT t.id, t.current_attempt_id, t.lease_epoch, a.worker_session_id
FROM tasks AS t
JOIN task_attempts AS a ON a.id = t.current_attempt_id
WHERE t.id = $1 AND t.status = 'RUNNING'
FOR UPDATE OF t, a;
-- 应用层/数据库比较当前 attempt、epoch、token_hash、session、expires_at 与取消策略；
-- 仅确认通过后，才执行提交、Reservation ACTIVE→RELEASED 和 Outbox。
```

## 7. Handler 插件生命周期与 Go 契约

### 7.1 生命周期

`Validate → Prepare → Execute → Collect → Cleanup`。`Validate` 必须无副作用；`Prepare` 创建任务局部目录、获取输入；`Execute` 执行 AI/媒体操作；`Collect` 生成清单；`Cleanup` 最佳努力删除临时文件，不能删除已确认资产。

### 7.2 建议 Go 接口

```go
package runtime

import "context"

type Handler interface {
    Capability() CapabilityDescriptor
    Validate(ctx context.Context, input TaskInput) error
    Execute(ctx context.Context, env ExecutionEnvironment, input TaskInput,
        reporter ProgressReporter) (ExecutionResult, error)
}

type ProgressReporter interface {
    Report(ctx context.Context, progress Progress) error
}

type LeaseClient interface {
    Renew(ctx context.Context, request RenewRequest) (RenewResponse, error)
    GetStatus(ctx context.Context, attemptID string) (AttemptStatus, error)
}

type ResultClient interface {
    Complete(ctx context.Context, request CompleteRequest) (CommitResponse, error)
    Fail(ctx context.Context, request FailRequest) (FailResponse, error)
}
```

上面是**概念契约**，`CapabilityDescriptor` 等 DTO 在 Worker 协议包定义，编译前需补齐。不要让 Handler 接口包含 Repository、事务或 WorkflowRun 对象。`Cleanup` 可由 Runtime 通过 defer 统一执行；必须保证进程退出后还可依靠孤儿文件清理器兜底。

### 7.3 错误分类

| ErrorCode | 可重试默认值 | 说明 |
|---|---|---|
| `INVALID_INPUT` | 否 | 输入 Schema、必填字段缺失 |
| `UNSUPPORTED_CAPABILITY` | 否 | Worker 不具备实际执行能力 |
| `AUTH_FAILED` | 否/人工介入 | 凭证无效，不可无边界循环 |
| `RATE_LIMITED` | 是，延迟 | 结合 Retry-After/Provider 窗口 |
| `PROVIDER_UNAVAILABLE` | 是 | 服务商临时故障 |
| `PROVIDER_TIMEOUT_UNKNOWN` | 需核对 | 远端可能已接受请求 |
| `LOCAL_RESOURCE_EXHAUSTED` | 是，资源策略 | OOM、磁盘不足；避免同池反复失败 |
| `PROCESS_FAILED` | 视错误 | FFmpeg 退出、无法解码等 |
| `CANCELED` | 不重试 | 控制面授权取消 |
| `LEASE_LOST` | 不由旧 Worker 重试 | 旧 Attempt 停止，由调度层恢复 |
| `OUTPUT_VALIDATION_FAILED` | 按策略 | 文件不完整、媒体信息错误 |

错误可重试与否是控制面策略决策，表中的默认值不代替最终 RetryPolicy。

## 8. AI Provider Handler：同步、异步及限流

### 8.1 同步调用

1. 校验输入与供应商能力。
2. **实际 API 调用前**通过 RateLimit Service 获得 RPM/TPM 准入，并记录请求关联键；无法获得时以 `RATE_LIMIT_WAIT` 安全退出当前 Attempt 或等待短时许可（由阈值决定）。
3. 使用受限凭证调用 Provider。
4. 规范化输出/错误并记录用量；只将必要数据写入 ResultManifest。
5. 结果由服务端确认，不由 Provider 响应直接修改 Task。

若 Provider 并发槽位已在 Claim 预留，等待长时限流时应及时释放 Worker 与 Provider 并发资源；实际释放通过控制面状态事务执行，Worker 不直接删 Reservation。

### 8.2 长时间异步任务

异步 Provider 可能返回 `external_job_id`。必须持久化 `provider_submission_id`、供应商名称、外部任务 ID（若返回）、幂等键、状态和已用费用线索。

**关键选择：不能仅把 Provider 异步任务的整个等待阶段绑定在短 Worker Lease 上。** 建议分为：

- `SubmitExternalJob`：Worker 短任务发起/核对提交；保存外部 Job 记录。
- `WaitExternalJob`：由持久化轮询/回调事件触发新的短任务或外部等待节点；Worker 无需长时间占据稀缺并发槽。
- `CollectExternalJob`：完成后收集并校验产物。

这一分段模型与 Workflow v1.0 的 WAITING/外部事件语义一致，但实际 Task 类型与节点映射须在 Workflow 详细契约中冻结。若供应商原生调用必须保留长连接，则另设明确超时、心跳和配额策略。

### 8.3 未知提交结果

请求超时但远端可能已经受理时，优先用 `external_job_id` 或供应商支持的幂等键查询，不能立即盲目重新发起高成本操作；无法核对时转人工/策略决议，记录“重复计费风险”。

## 9. FFmpeg / Media Handler

### 9.1 命令安全

- 从受信的 `CompositionVersion` 编译媒体参数；不接收用户任意 shell 命令。
- Go 使用 `exec.CommandContext` + **参数数组**（不通过 shell 解析）。
- 严格限制允许的输入格式、输出路径和解码/编码选项；禁用不必要的网络协议和外部资源访问。
- FFmpeg 过滤图也要基于受限结构构造，不得直接拼接未过滤的用户文本形成任意指令。
- 为每个 TaskAttempt 创建私有工作目录（例如 `/work/{attempt_id}/`）；目录属主、权限和磁盘配额受控。

### 9.2 资源隔离

建议 FFmpeg 在独立容器或 cgroup 限额进程中执行，配置 CPU、RAM、临时磁盘及运行时间上限。子进程树取消要有明确策略；仅取消 Go Context 不保证所有子进程立即退出。针对容器或操作系统环境选择进程组终止和 kill-graceful/kill-force 阶段。

### 9.3 进度与输出校验

推荐使用 FFmpeg 可解析的进度接口而不是依赖非结构化 stderr；将时长、帧数等映射为可解释进度，若时长未知仅报告阶段。完成后使用媒体探测检查输出是否可播放、轨道存在、分辨率/时长/编码符合指定条件，输出 checksum 和字节数。

### 9.4 清理策略

失败或 LeaseLost 时终止进程并隔离临时输出；完成后仅在 ResultCommit 已确认且数据可稳定访问时清理 Worker 临时文件。存储 GC 由 Asset 模块处理，不允许 Worker 删除业务资产引用。

## 10. ResultManifest、资产上传与提交

### 10.1 Manifest v1 建议结构

```json
{
  "manifest_version": 1,
  "submission_id": "uuid-submission",
  "task_id": "uuid-task",
  "attempt_id": "uuid-attempt",
  "lease_epoch": 5,
  "outputs": [
    {
      "name": "video",
      "temporary_object_key": "staging/attempt-id/output.mp4",
      "sha256": "hex-sha256",
      "size_bytes": 1000000,
      "mime_type": "video/mp4",
      "metadata": {"duration_ms": 60200, "width": 1080, "height": 1920}
    }
  ],
  "usage": [{"kind": "render_cpu_seconds", "estimated": false, "value": 42.1}],
  "result_schema_version": 1
}
```

Manifest 必须有大小、条目数量、允许 MIME、对象所属前缀和可读性限制。`sha256` 必须按真实内容计算；上述字符串只是格式示例。

### 10.2 资产提交状态

建议将输出分为：`UPLOADING → STAGED → VERIFIED → COMMITTED`。这些阶段可以表现为独立产物表，不应直接把尚未验证的文件登记为正式 `AssetVersion`。

**安全提交顺序：**

1. Worker 获得仅限本次 Attempt 的临时上传权限。
2. 上传到 Attempt 专属 `staging` 前缀。
3. 服务端以可信对象存储元数据/读取校验验证存在性、体积、摘要和安全边界。
4. 通过统一 `ResultCommit` 事务确认 Task 当前执行权；生成最终引用与业务结果，释放 Reservation，写 Outbox。
5. 正式结果引用的对象须处于可稳定读取的位置；若需要从临时对象复制/提升，**应先完成提升并校验，再执行指向最终对象的 DB 提交**，以避免数据库确认成功但对象不存在。
6. 老 Attempt 的 Staging 文件进入 GC，不能因为过期 Attempt 存在文件就接受其结果。

对象存储的 staging 与 final 并不参与 PostgreSQL ACID；复制已成功但 DB 事务失败将形成可回收孤儿对象，这是可接受的补偿场景。需保护正在提交中的对象免受 GC 竞态清理。

### 10.3 结果提交谓词

`CompleteAttempt` 必须同时验证：

- `task.status == RUNNING`；
- `task.current_attempt_id == attempt_id`；
- `task.lease_epoch == lease_epoch`；
- Attempt Session 与已授权 Session 一致；
- LeaseToken 校验成功、有效期尚未过去；
- Task 未被控制面取消或吊销；
- Manifest、输出 Schema、归属、版本和对象摘要有效；
- 结果提交的业务幂等键匹配。

相同 `submission_id` 且相同 Manifest 哈希重复调用必须返回既有提交结果；相同键不同哈希返回 Conflict。**提交验证失败不应通过隐式新建 Attempt 修复。**

## 11. 超时、取消与优雅退出

### 11.1 超时分层

必须分别配置：`queue_wait_timeout`（可选）、`task_execution_timeout`、`provider_request_timeout`、`subprocess_timeout`、`lease_ttl`、`worker_shutdown_grace`。LeaseTTL 不等于 TaskTimeout。

### 11.2 取消协议

用户取消 WorkflowRun → 控制面设置 `CANCELING` 并传播取消意图 → Task Execution 吊销待执行任务和有效租约（按照统一事务）→ Worker 下次 Renew/Cancel Poll 获知 → 取消 context/子进程/供应商可取消 Job → Cleanup → 控制面推进最终 `CANCELED`。

对于不支持远端取消的 Provider，应记录取消未能中止远端计费的事实；本地任务可拒绝迟到产物，但不承诺第三方停止执行。

### 11.3 Drain

Worker 收到 SIGTERM：

1. 原子切换本地 `DRAINING`，请求服务端登记。
2. 停止新的 Claim。
3. 在 `shutdown_grace` 内继续续租已在执行的 Task，尽可能完成或协作式取消。
4. 超期后终止本地子进程并退出；剩余执行权由 Lease + Reconciler 回收。

不得在没有执行状态提交/租约释放的情况下将任务直接标记为成功或失败。

## 12. 安全、多租户与秘密处理

- Worker Session 凭证与工作空间授权分开管理，任务数据访问应按 `workspace_id`/Task 范围授权。
- 禁止将供应商 API Key 放入普通 TaskEnvelope、结构化日志、错误堆栈或 Trace Attribute。
- 受限上传 URL 必须限制对象前缀、大小、内容类型、有效期；结果提交不能仅凭 URL 自行声明归属。
- 下载/请求外部媒体 URL 时防范 SSRF、内网地址访问、重定向绕过、恶意媒体文件和解压炸弹。
- FFmpeg 子进程运行于最小权限、尽可能非 root 的环境；工作目录禁止跨租户共享可写路径。
- 用户提供的音视频数据可能含敏感信息；日志中只记录脱敏路径、任务 ID 和受控错误摘要。

## 13. Worker 端本地并发与背压

Worker 维护受控执行槽位，而不是对每个 Claim 无界启动 Goroutine。建议 `WorkerRuntime` 包含：`claimLoop`、`activeAttemptRegistry`、`leaseSupervisor`、`progressAggregator`、`handlerPool`、`shutdownController`。

- 满槽时停止 Claim；本地槽位释放仅代表本地执行已结束，不代表资源预留已被权威释放。
- 对下载/上传设置全局并发与流量限制，避免 IO 任务挤占 FFmpeg 工作集。
- 若磁盘低于安全水位或关键依赖不可用，暂停新 Claim 并上报降级状态。
- 本地协程 panic 必须被顶层执行包装器捕获并作为受控失败报告（进程级致命错误另行处理）。
- 处理器实现需要在 `context.Context` 被取消时及时退出；不得偷偷重启已失效 Attempt。

## 14. 控制面 API 草案

建议采用内部 gRPC 或鉴权 HTTP，传输形式不影响命令语义。接口应在 `docs/API` 冻结详细 OpenAPI/Proto。

| Command / Query | 参数要点 | 返回及安全语义 |
|---|---|---|
| `RegisterWorker` | identity, session, capabilities, limits | session authorization、策略与心跳配置 |
| `HeartbeatSession` | session, sequence, observed usage | ACTIVE/DRAINING/REVOKED；**不续租 Task** |
| `ClaimTask` | session, request_id, capability, free_slots | Envelope 或 NoTask；Claim 原子化 |
| `RenewTaskLease` | task, attempt, epoch, token | NewExpiry / LeaseLost / Canceled |
| `ReportProgress` | attempt, sequence, stage | 幂等/节流，不改变最终状态 |
| `GetAttemptStatus` | task, attempt, submission_id? | 当前有效性/提交状态，用于未知结果核对 |
| `CompleteAttempt` | grant, submission_id, manifest_hash, manifest | Committed / AlreadyCommitted / Conflict / LeaseLost |
| `FailAttempt` | grant, failure_id, classified error | Accepted / AlreadyReported / LeaseLost |
| `BeginDrain` | session | 不再允许新 Claim |

**错误码约定：** `UNAUTHENTICATED`、`PERMISSION_DENIED`、`INVALID_ARGUMENT`、`SCHEMA_UNSUPPORTED`、`NO_CAPACITY`、`NO_TASK`、`LEASE_LOST`、`TASK_CANCELED`、`CONFLICT`、`TRANSIENT_UNAVAILABLE`、`INTERNAL`。调用端必须区分可重试、不可重试、需查询状态三类响应。

### 14.1 Worker HTTP/gRPC 超时策略

- `Claim` 超时后使用相同 `claim_request_id` 重试或查询，不使用新键盲目再 Claim。
- `Renew` 超时后优先继续确认当前授权，但不得假设服务端已续租。
- `Complete` 超时后必须通过相同 `submission_id` 查询/重试，直到得到权威状态或进入受控未知状态。
- `Fail` 超时后按同一 `failure_report_id` 重试；不因网络超时自增 AttemptNumber。

## 16. 并发与故障注入测试矩阵

| 编号 | 场景 | 核心期望 |
|---|---|---|
| W-01 | Worker 注册后重启使用旧 Session | 旧 Session 不能 Claim |
| W-02 | 同 Worker 重复注册同一 Session | 幂等或显式冲突，无双身份 |
| W-03 | 多 Worker 并发 Claim | 同 Task 仅一个当前有效 Attempt |
| W-04 | Claim 事务成功、响应丢失 | 原 request_id 可恢复原授权，不新增 Attempt |
| W-05 | Session Heartbeat 成功但 Task 未续租 | Task Lease 正常过期，不能被心跳代替 |
| W-06 | 旧 Worker 失联、新 Worker 重试，旧结果晚到 | 旧结果提交被拒绝 |
| W-07 | Renew 与取消并发 | 事务串行化，取消后不再延长有效授权 |
| W-08 | Complete 与 Lease 回收竞争 | 仅有一个最终状态，资源只释放一次 |
| W-09 | Complete 数据库成功、响应丢失 | 相同 submission_id 返回原提交结果 |
| W-10 | 相同 submission_id 使用不同 Manifest | Conflict，无覆盖 |
| W-11 | Upload 完成、DB 提交失败 | 对象可安全 GC，不产生已确认无文件资产 |
| W-12 | DB 结果已确认、通知丢失 | Outbox/Reconciler 最终推进 NodeRun |
| W-13 | 异步模型请求超时但远端已接受 | 优先查询，不盲目重复发起 |
| W-14 | Provider 返回 429 | 尊重限流策略，释放长等待资源 |
| W-15 | FFmpeg 超时 / OOM | 进程树退出，记录分类错误，临时输出不交付 |
| W-16 | SIGTERM Drain，活跃任务未结束 | 无新 Claim；旧任务续租直到完成或超时退出 |
| W-17 | Worker 磁盘临界 | 拒绝新任务，反馈容量状态 |
| W-18 | 同租户和跨租户对象 URL 越权 | 拒绝访问与提交 |
| W-19 | 重复/乱序 Progress | 不影响最终状态、不回退进度序号 |
| W-20 | Handler panic | 受控错误、槽位释放、诊断可定位 |
| W-21 | 已失效 Token 请求 Complete | LEASE_LOST，不能恢复执行权 |
| W-22 | 多资源池预留后 Handler 失败 | Reservation 只释放一次，无负库存 |
| W-23 | Task 已取消而 Provider 返回结果 | 不接受结果为成功，明确实际成本 |
| W-24 | 100 个工作流、2000 个 Task 压测 | 队列可恢复、有限并发、无丢失；性能值须测得 |
| W-25 | 队列消息重复/丢失 | 权威任务状态与 Reconciler 保证最终发现 |
| W-26 | 跨版本 Capability 不兼容 | 拒绝 Claim 或选择兼容 Worker |

自动化测试分层：Handler 单测（Mock IO）、协议契约测试、PostgreSQL 事务集成测试、S3/MinIO 协调测试、故障注入、FFmpeg 沙箱端到端测试。**必须使用真实 PostgreSQL 检验 Claim/Renew/Commit 的事务竞争**，不能只使用内存 Fake 得出一致性结论。

## 17. 推荐 Go 实现结构与开发切片

```text
backend/internal/worker/
  domain/                # WorkerSession / Capability / ExecutionGrant 值对象
  application/           # 注册、会话心跳、Drain、执行协调
  protocol/              # 请求/响应、版本、错误码
  runtime/               # Claim Loop / Lease Supervisor / Local Slots
  handlers/
    mock/
    llm/
    image/
    tts/
    ffmpeg/
  infrastructure/        # Worker API Client / S3 / Telemetry / Local Process
```

**切片 A：Mock 执行闭环。** 注册→Claim→Renew→Mock Handler→Complete→Outbox，含幂等结果提交及旧令牌拒绝。  
**切片 B：可靠运行。** Drain、Cancel、Lease 过期、Reconciler、断线重连、重复消息测试。  
**切片 C：资产协议。** 临时对象上传、校验、正式资产登记、孤儿对象 GC。  
**切片 D：真实媒体。** FFmpeg 进程隔离、输入验证、输出探测、取消/超时。  
**切片 E：Provider。** 同步 AI、RateLimit 协作、外部异步 Job 状态和用量账本。  
**切片 F：负载与运维。** 多 Worker、故障注入、SLO 基线、日志/指标/Trace。

每个切片的完成判据包括：对应协议字段冻结、端到端用例通过、异常路径有测试、数据库迁移可重复执行、日志无凭证泄露、升级和回滚说明完善。

## 18. 架构 ADR 建议与待决事项

### 18.1 应记录的 ADR

- `ADR-WKR-001` Worker Pull + 控制面原子 Claim，而非队列消息直接授权。
- `ADR-WKR-002` WorkerSession 与 TaskLease 解耦。
- `ADR-WKR-003` Attempt LeaseEpoch + Fencing + 幂等 ResultCommit。
- `ADR-WKR-004` 长异步 Provider Job 从 Worker 长租约中解耦。
- `ADR-WKR-005` 对象先稳定化后事务确认，允许可回收孤儿对象。
- `ADR-WKR-006` FFmpeg 在进程/容器边界受限执行。

### 18.2 编码前需要冻结的决定

1. Worker ↔ Control Plane 采用 gRPC 还是 HTTP+JSON，如何进行双向身份认证？
2. 任务 Claim 是否使用客户端幂等请求键与授权查询端点，授权响应保留多久？
3. `lease_ttl`、续租间隔、Session 心跳间隔、最大任务运行时间的默认值及配置来源。
4. 结果对象采用一次上传直接稳定对象键，还是 staging → promote；GC 如何识别正在提交对象？
5. 对外部异步模型 Job 的持久化结构、轮询/回调所有者与未知结果策略。
6. CPU/内存/临时磁盘实际隔离方式；首个部署环境是否具备 cgroup/容器限制能力？
7. TaskAttempt 的 `COMMITTED` 与 `SUCCEEDED` 术语如何映射至既有 Workflow/Database 状态，避免一处叫成功另一处叫提交。
8. Task 取消与 Complete 竞争时的事务锁顺序与优先规则。

未冻结项应以 ADR 和可复现实验判定，**不得由 Handler 自行形成不同的临时约定**。

## 19. 交付完成标准与文档状态

满足以下条件才可认为 Worker Runtime 可进入生产候选状态：

- 正常执行链路贯通并能生成正式 AssetVersion；
- WorkerSession、TaskAttempt、TaskLease 和 Reservation 状态相互一致；
- 旧 Attempt 无法覆盖新结果，结果提交可安全重试；
- Worker 失联、Scheduler 重启和事件丢失后能恢复；
- FFmpeg 进程或 Provider API 异常不会导致不受控资源泄露；
- 同步和长异步 AI 任务使用不同的等待语义；
- 敏感凭证、租户资产和不可信媒体输入有明确保护；
- 多 Worker 并发/故障测试通过，并获得真实的队列与资源性能数据；
- 数据库及 API 的最终迁移/契约已经与本文件一致。
