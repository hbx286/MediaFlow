# 第一章 设计目标与原则

## 1.1 文档目标

本文档将 MediaFlow 的产品需求转化为可实现、可验证、可演进的软件架构。

文档应成为以下工作的共同依据：

- 领域对象和业务规则实现
- Go 后端模块划分
- 数据库设计
- 工作流引擎设计
- 分布式任务调度
- Worker 执行协议
- 多媒体生产集成
- API 和事件契约
- 自动化测试
- 系统部署与运行维护

本次设计不以某个开发周期为约束，而以长期产品形态为目标。但架构的复杂程度应与实际需求相适应，避免过早构建不必要的分布式组件。

## 1.2 核心架构目标

### 业务正确性

系统需要正确表示用户、项目、剧本、分镜、素材、作品、工作流和执行任务之间的关系。

业务规则必须由领域模型或应用服务明确执行，不应只依赖前端校验。

### 执行可靠性

复杂工作流在并发、故障、超时、重试和服务重启情况下仍应具备可解释且可恢复的执行状态。

### 模块独立性

创作领域、工作流编排、任务调度和执行器之间具有清晰的职责边界。

### 数据可追溯性

每个交付作品都能够追溯到生成它所使用的输入、素材、工作流版本、模型配置和执行记录。

### 资源可管理性

不同类型的任务能够根据执行能力、资源要求和系统配额安排执行。

### 可持续演进

未来增加新的媒体类型、模型供应商、节点类型和业务工作流时，不需要重写核心领域模型。

## 1.3 架构原则

**原则 A：领域模型优先于数据库表。**

首先确定业务概念、关系和约束，再设计持久化结构。

**原则 B：业务状态与执行状态分离。**

用户确认了一个分镜，不代表素材生成任务已经完成。任务执行成功，也不代表作品已经通过审核。

**原则 C：定义与实例分离。**

WorkflowDefinition 是可复用的工作流定义；WorkflowRun 是一次确定的运行实例。

**原则 D：编排与调度分离。**

Workflow Engine 负责依赖、节点执行语义和工作流状态；Scheduler 负责计算资源及执行机会分配。

**原则 E：执行与结果提交分离。**

Worker 完成计算不等于任务结果已被系统接受。

**原则 F：持久化状态优先。**

消息队列用于传递工作，不是任务状态的唯一事实来源。

**原则 G：允许重复执行，约束重复影响。**

分布式执行以可能发生重复为前提，重点保证有效结果提交和业务状态的一致性。

**原则 H：资产与生产过程解耦。**

同一个素材可以被多个分镜、作品和工作流引用。

**原则 I：通过契约扩展能力。**

业务模块通过接口和明确的数据格式集成 AI 模型及媒体处理器。

# 第二章 系统上下文与总体架构

## 2.1 系统边界

MediaFlow 的内部系统主要包含：

1. 用户和工作空间管理
2. 创作与项目管理
3. 多媒体资产管理
4. 作品编排与交付
5. AI 模型接入
6. 工作流定义与运行
7. 任务调度
8. Worker 管理
9. 资源和成本管理
10. 运行监控和审计

外部依赖主要包括：

- AI 模型供应商
- 自建推理服务
- 对象存储服务
- 消息与通知服务
- 身份认证服务
- 外部业务集成系统

## 2.2 推荐架构形态

采用：

**模块化单体控制面 + 独立 Worker 执行面 + 可替换基础设施适配器。**

控制面可以由一个 Go 应用承载多个业务模块。Worker 作为独立进程运行，可以根据任务类型采用不同部署形态。

此处的模块划分不等于必须部署同等数量的服务。

### 控制面

承担：

- API 请求处理
- 身份和权限验证
- 领域业务操作
- 工作流定义管理
- 工作流状态推进
- 任务调度决策
- 任务执行权管理
- 资源配额管理
- 执行结果确认

### 执行面

承担：

- 领取任务
- 获取执行输入
- 调用 AI 模型
- 处理多媒体文件
- 上报执行进度
- 提交结果
- 续租任务执行权
- 安全退出

### 数据面

承担：

- 关系型业务数据持久化
- 任务及工作流运行状态持久化
- 文件和媒体资产持久化
- 消息传递
- 运行指标与日志保存

## 2.3 架构组件

| 组件 | 主要职责 | 建议实现 |
|---|---|---|
| Web Application | 创作、管理、运行状态展示 | React / Next.js |
| API Server | 对外 API、鉴权、业务入口 | Go |
| Application Services | 用例编排、事务协调 | Go |
| Workflow Engine | DAG、节点状态、依赖推进 | Go |
| Scheduler | 就绪任务调度、资源与配额控制 | Go |
| Worker Manager | Worker 注册、任务租约、心跳 | Go |
| Model Gateway | AI 能力抽象、供应商适配 | Go |
| Media Runtime | 音视频处理 | Go + FFmpeg |
| Asset Service | 资产元数据和存储协调 | Go |
| PostgreSQL | 关系数据和权威执行状态 | PostgreSQL |
| Redis | 缓存、队列通知或调度辅助 | Redis，可选 |
| Object Storage | 多媒体文件与执行产物 | S3 兼容存储 |
| Observability | 日志、指标、追踪 | OpenTelemetry 等 |

## 2.4 依赖方向

模块依赖遵循：

Presentation → Application → Domain

Infrastructure 通过实现 Domain 或 Application 定义的接口接入系统。

核心业务规则不得直接依赖 HTTP 框架、Redis 客户端、ORM 或某个具体 AI SDK。

允许应用服务协调多个领域模块，但禁止通过直接修改其他模块拥有的数据库表来绕过其业务规则。

# 第三章 领域划分

## 3.1 限界上下文

MediaFlow 划分为以下限界上下文。

| 限界上下文 | 核心职责 | 主要对象 |
|---|---|---|
| Identity & Workspace | 用户、团队、权限、工作空间 | User、Workspace、Membership |
| Creative Production | 创作需求、剧本、分镜 | CreativeBrief、Script、Storyboard、Scene |
| Project Management | 项目生命周期 | Project |
| Asset Management | 素材及版本管理 | Asset、AssetVersion |
| Composition & Delivery | 媒体编排、作品和交付 | Composition、Work、RenderOutput |
| Workflow Definition | 流程模板、节点和版本 | WorkflowDefinition、WorkflowVersion |
| Workflow Execution | 流程运行、节点状态与依赖 | WorkflowRun、NodeRun |
| Task Execution | 任务生命周期、执行尝试 | Task、TaskAttempt |
| Scheduling & Resources | 任务分配、资源和配额 | ResourcePool、ResourceReservation |
| Worker Management | Worker 身份、能力和运行状态 | Worker、WorkerSession |
| Model Integration | 模型和供应商接入 | Provider、ModelConfiguration |
| Usage & Cost | 用量、预算、成本 | UsageRecord、Budget |
| Observability & Audit | 运行追踪、审计 | ExecutionEvent、AuditEvent |

这些上下文在代码中可以体现为模块，但部分模块在部署初期可以共享进程和数据库实例。

## 3.2 核心上下文关系

Creative Production 使用 Project Management 管理的项目身份和所属范围。

Creative Production 通过 Asset Management 引用媒体资产。

Workflow Definition 定义生产过程。

Workflow Execution 解释已发布工作流版本，并生成或激活可执行任务。

Task Execution 管理任务的执行状态和执行尝试。

Scheduling & Resources 决定任务是否可以获得执行资源。

Worker Management 管理实际执行端。

Model Integration 为 AI 类型任务提供模型能力。

Composition & Delivery 将资产和编排定义转换为作品交付结果。

## 3.3 跨领域通信原则

同一业务事务内的强一致性操作，应尽可能由明确的应用服务在同一个数据库事务中完成。

不要求实时强一致性的跨领域变化，可使用领域事件和可靠事件发布机制。

例如：

- ScriptApproved
- StoryboardPublished
- AssetVersionCreated
- WorkflowRunStarted
- NodeRunCompleted
- TaskReady
- TaskSucceeded
- TaskFailed
- WorkerLeaseExpired
- WorkDelivered

事件名称表达已经发生的事实，不承担未定义的跨模块隐式调用语义。

# 第四章 创作领域模型

## 4.1 Workspace

Workspace 是用户或组织持有资源的业务边界。

主要属性：

- WorkspaceID
- Name
- OwnerID
- Status
- CreatedAt
- UpdatedAt

业务约束：

- Workspace 必须具有明确的所有权。
- 项目、资产、模型配置及工作流必须可追溯所属 Workspace。
- 用户访问 Workspace 资源必须经过授权校验。

## 4.2 Project

Project 是围绕一个创作目标组织活动和资源的聚合根。

主要属性：

- ProjectID
- WorkspaceID
- Name
- Description
- Status
- DefaultConfiguration
- CreatedBy
- CreatedAt
- UpdatedAt

建议状态：

ACTIVE、ARCHIVED、DELETING。

项目不直接保存所有分镜、素材和任务实体。

这些对象通过 ID 关联项目，分别由对应领域管理。

主要业务规则：

- 只有具有权限的用户可以修改项目。
- 项目归档不等于删除已有成果。
- 项目删除必须考虑正在运行的工作流和仍被引用的资产。
- 项目状态不得直接代替作品状态或工作流状态。

## 4.3 CreativeBrief

CreativeBrief 描述创作目标。

主要属性：

- BriefID
- ProjectID
- Version
- Topic
- TargetAudience
- Objective
- DurationTarget
- Language
- AspectRatio
- VisualStyle
- AudioStyle
- Constraints
- References
- Status

CreativeBrief 采用版本化设计。

当用户修改创作目标时，应生成新的版本或草稿修订，而不是覆盖已被运行实例引用的历史版本。

## 4.4 Script

Script 为剧本聚合根。

主要属性：

- ScriptID
- ProjectID
- CurrentVersionID
- Status

ScriptVersion 包含：

- ScriptVersionID
- ScriptID
- VersionNumber
- StructuredContent
- SourceBriefVersionID
- CreatedBy
- CreatedAt

重要规则：

- AI 生成结果必须能够转换为结构化剧本。
- 已确认版本不可直接覆盖。
- 剧本修改不会自动销毁基于旧版本生成的分镜。
- 创建新分镜时必须记录来源剧本版本。

## 4.5 Storyboard

Storyboard 为分镜集合聚合根。

主要属性：

- StoryboardID
- ProjectID
- CurrentVersionID
- Status

StoryboardVersion 包含有序 Scene 定义。

Scene 至少包含：

- SceneID
- Order
- Duration
- Narrative
- VisualDescription
- VisualPrompt
- AudioScript
- StyleReference
- AssetReferences

SceneID 表示稳定的业务身份。

对于 Scene 的不同修订，使用 SceneRevisionID 或 StoryboardVersion 中的确定版本内容表示。

## 4.6 分镜一致性规则

同一分镜版本中，不允许出现重复排序位置。

同一 StoryboardVersion 中的场景关系必须可确定。

删除分镜不应直接物理删除其历史素材。

修改分镜的生成提示词，只会使依赖该提示词的结果进入需要重新评估的状态。

分镜关联的资产版本必须具有明确的权限和存在性校验。

# 第五章 资产与作品领域模型

## 5.1 Asset

Asset 是逻辑素材聚合根。

主要属性：

- AssetID
- WorkspaceID
- ProjectID
- Name
- AssetType
- CurrentVersionID
- Status
- CreatedAt

AssetVersion 表示不可变的具体媒体内容。

主要属性：

- AssetVersionID
- AssetID
- VersionNumber
- StorageKey
- ContentHash
- MimeType
- FileSize
- MediaMetadata
- SourceType
- GenerationRecordID
- CreatedAt

## 5.2 资产不变量

同一个 AssetVersion 对应的文件内容一旦提交，不允许原地修改。

替换素材创建新的版本。

已被有效作品引用的资产版本，不得在不满足删除策略的情况下被清理。

资产的物理文件可进行存储迁移，但对业务引用暴露的身份必须稳定。

## 5.3 资产生成记录

生成型素材应记录：

- 来源 TaskAttempt
- 来源模型或执行器
- 参数快照
- 输入资产
- 生成时间
- 成本与用量
- 内容校验信息

这使用户能够从一件作品追溯到具体的生成来源。

## 5.4 Composition

Composition 表示可执行的媒体编排定义。

建议采用不可变的 CompositionVersion。

包含：

- 画布配置
- 轨道定义
- 素材版本引用
- 时间安排
- 转场配置
- 字幕配置
- 音频混合参数
- 输出目标

CompositionVersion 是媒体渲染的确定性输入之一。

## 5.5 Work

Work 是面向用户的作品聚合根。

WorkVersion 包含：

- WorkVersionID
- WorkID
- CompositionVersionID
- OutputAssetVersionID
- ReviewStatus
- DeliveryStatus
- CreatedAt

作品版本与生成任务分离。

Render Task 成功只能说明渲染产物已生成。

是否通过审核、是否交付，仍由作品领域负责。

# 第六章 Workflow Definition 领域模型

## 6.1 设计目标

工作流定义用于描述可复用的生产过程。

必须支持：

- DAG
- 节点参数
- 节点输入输出
- 条件执行
- 并行与汇合
- 动态任务展开
- 人工审批
- 重试与超时策略
- 工作流版本

## 6.2 WorkflowDefinition

属性：

- WorkflowID
- WorkspaceID
- Name
- Description
- Status
- CurrentVersionID
- CreatedBy

WorkflowDefinition 表示一个逻辑工作流的长期身份。

## 6.3 WorkflowVersion

属性：

- WorkflowVersionID
- WorkflowID
- VersionNumber
- Nodes
- Edges
- InputSchema
- OutputSchema
- PublishedAt
- DefinitionHash

一旦发布，WorkflowVersion 不可变。

所有 WorkflowRun 必须引用明确的 WorkflowVersion。

## 6.4 NodeDefinition

节点定义包括：

- NodeID
- NodeType
- Name
- InputSchema
- OutputSchema
- Configuration
- RetryPolicy
- TimeoutPolicy
- ResourceRequirements
- ErrorPolicy

NodeID 在同一 WorkflowVersion 内必须唯一。

## 6.5 EdgeDefinition

边定义包括：

- FromNodeID
- FromOutput
- ToNodeID
- ToInput
- Condition

工作流发布前必须进行 DAG 校验。

## 6.6 节点输入与输出

节点之间不应通过未声明的共享内存或任意数据库查询传递业务输出。

节点输出采用明确的数据契约。

对于较小的结构化结果，可保存 JSON 或其引用。

对于图片、视频、音频等大型结果，应传递 AssetVersionID 或受控的 Artifact 引用。

节点的输入在正式执行时必须解析为确定的输入快照。

## 6.7 动态节点展开

对于分镜等动态集合，采用受控的 Map/ForEach 语义。

例如：

Storyboard 输出 12 个 Scene。

Map 节点根据集合生成 12 个子节点运行实例或任务。

系统应记录：

- 展开来源
- 展开版本
- 子项稳定标识
- 展开规则
- 最大展开数量
- 结果汇合条件

同一运行实例的展开结果需要持久化，恢复时不得因重新计算而产生不可控的重复子节点。

## 6.8 条件分支和汇合

条件分支未被选择的节点可以进入 SKIPPED。

Join 节点需要明确判断规则：

- 等待所有必要分支
- 等待指定分支集合
- 允许部分结果的容错汇合

不应将“任意一个前置节点结束”作为所有 Join 的通用语义。

# 第七章 WorkflowRun 与 NodeRun 模型

## 7.1 WorkflowRun

WorkflowRun 是工作流执行聚合根。

核心字段：

- WorkflowRunID
- WorkflowVersionID
- WorkspaceID
- ProjectID
- TriggerType
- TriggeredBy
- InputSnapshot
- Status
- StartedAt
- FinishedAt
- Version

建议状态：

CREATED、RUNNING、WAITING、PAUSED、CANCELING、CANCELED、SUCCEEDED、FAILED。

## 7.2 NodeRun

NodeRun 表示一次工作流运行中的节点实例。

属性：

- NodeRunID
- WorkflowRunID
- NodeDefinitionID
- ParentNodeRunID
- ExpansionKey
- Status
- InputSnapshot
- OutputReference
- RemainingDependencies
- Version

建议状态：

PENDING、READY、RUNNING、WAITING、SUCCEEDED、FAILED、SKIPPED、BLOCKED、CANCELED。

这里的 WAITING 通常用于人工审批或等待外部事件。

## 7.3 状态职责边界

WorkflowRun.Status 表示整条工作流的业务执行状态。

NodeRun.Status 表示单个节点在执行图中的状态。

Task.Status 表示具体可调度任务的执行生命周期。

三者不能通过简单复制相互代替。

例如：

TaskSucceeded → NodeRunSucceeded → WorkflowRunSucceeded

并不是一个无条件的直接状态变更。

Task 成功后需要先校验结果，确认该节点的全部执行要求已经满足，再推进其后继节点。

只有工作流成功条件全部满足时，WorkflowRun 才进入 SUCCEEDED。

## 7.4 依赖推进机制

对于静态 DAG，可以维护节点剩余未满足依赖数量。

当一个前置节点成功完成时：

1. 识别对应后继节点。
2. 判断该依赖边是否满足。
3. 记录该依赖已被满足。
4. 更新后继节点的依赖状态。
5. 对所有必要条件已满足的节点转为 READY。
6. 生成对应的执行调度请求。

这里必须保证同一依赖完成事件不会被重复计数。

建议为每条实际依赖维护满足状态，或使用具有唯一约束的依赖完成记录。

仅通过无条件递减整数来处理重复事件是不安全的。

## 7.5 工作流完成判定

工作流成功必须满足：

- 必要输出节点已完成。
- 所有必要执行路径达到允许的终态。
- 没有未处理的阻断性失败。
- 必要输出能够被有效读取。

工作流失败需要根据节点 ErrorPolicy 与工作流整体规则判断。

人工审核等待、外部事件等待和用户暂停均不应被误判为失败。

## 7.6 局部重新运行

原有 WorkflowRun 不应被任意回退到历史状态。

当用户修改创作输入并请求局部重新生成时，推荐创建新的修订执行上下文，引用原有运行和可复用产物。

系统根据依赖关系和输入指纹判断哪些节点需要重新执行。

能够复用的节点结果应满足：

- 输入没有变化
- 节点实现和关键配置兼容
- 引用资产仍然有效
- 节点具有可复用语义
- 用户权限允许复用

对于随机生成、外部环境依赖或有副作用的节点，不应仅凭输入哈希相同就默认复用。

# 第八章 Task 与 TaskAttempt 模型

## 8.1 Task 的定位

Task 是执行系统管理的最小可调度工作单元。

一个 NodeRun 可以产生一个或多个 Task。

也允许某些纯逻辑节点不产生异步 Task，而由 Workflow Engine 完成状态推进。

## 8.2 Task 字段

建议包含：

- TaskID
- WorkflowRunID
- NodeRunID
- WorkspaceID
- TaskType
- Capability
- InputReference
- Status
- Priority
- ResourceRequirements
- RetryPolicy
- Timeout
- NextRunAt
- AttemptCount
- CurrentAttemptID
- CreatedAt
- UpdatedAt
- Version

## 8.3 Task 状态

建议使用：

PENDING、READY、QUEUED、RUNNING、RETRY_WAIT、SUCCEEDED、FAILED、CANCELED。

其中：

PENDING：任务已创建，但执行条件尚未完全满足。

READY：执行条件满足，可以参与调度。

QUEUED：已进入分发或等待领取阶段。

RUNNING：存在有效执行尝试。

RETRY_WAIT：等待下一次重试时间。

SUCCEEDED：有效执行结果已确认。

FAILED：任务不可再自动恢复。

CANCELED：任务按照取消规则终止。

## 8.4 TaskAttempt

TaskAttempt 表示一次实际执行。

字段：

- AttemptID
- TaskID
- AttemptNumber
- WorkerSessionID
- LeaseToken
- LeaseExpiresAt
- Status
- StartedAt
- FinishedAt
- ErrorCode
- ErrorDetailReference
- ResultManifestReference

TaskAttempt 使用独立状态：

CREATED、RUNNING、SUCCEEDED、FAILED、TIMED_OUT、ABANDONED。

这里的 Attempt 成功应当指执行尝试结果通过有效提交协议确认，而不只是 Worker 自行声明完成。

## 8.5 Task 核心不变量

- 一个 Task 同一时刻最多只有一个被系统认可的有效执行租约。
- TaskAttempt 的序号不能重复。
- 已进入终态的 Task 不接受未经定义的状态回退。
- 只有有效执行令牌可以提交当前 Task 的结果。
- Task 最终只能确认一个有效结果。
- 旧 Attempt 的迟到响应不能覆盖新结果。
- 不得无限自动重试。
- 重试不改变原 Task 的业务身份。

## 8.6 执行幂等

应区分三个概念：

**任务身份：** 表示业务上需要完成什么工作。

**执行尝试身份：** 表示某一次真实运行。

**结果提交身份：** 表示哪次运行被允许改变最终业务状态。

这三个身份不能合并为一个简单的 TaskID。

# 第九章 事务边界与一致性设计

## 9.1 一致性基本策略

MediaFlow 采用：

**聚合内部强一致 + 核心执行状态事务一致 + 跨基础设施最终一致。**

关键业务状态以 PostgreSQL 为权威来源。

Redis、消息队列、Worker 本地状态和对象存储不能独立决定工作流的最终执行状态。

## 9.2 必须保证原子性的操作

| 操作 | 原子性要求 |
|---|---|
| 发布工作流版本 | 版本与完整定义一致 |
| 创建 WorkflowRun | 运行实例、初始节点状态及必要事件协调一致 |
| 激活后继节点 | 依赖满足记录与 Ready 状态一致 |
| 分配任务 | Task 状态、Attempt、租约与必要资源预留一致 |
| 任务完成 | 有效租约校验、任务结果、节点推进和事件记录一致 |
| 确认作品版本 | 作品版本与输出资产引用一致 |
| 取消工作流 | 工作流取消意图与后续处理事件一致 |

这些操作不一定需要单个大型事务，但必须具有明确的线性化点和失败恢复策略。

## 9.3 任务领取的并发控制

推荐采用数据库事务和条件状态更新保障任务领取。

在使用 PostgreSQL 任务队列表时，可以考虑 FOR UPDATE SKIP LOCKED 等机制。

实现必须同时处理：

- 多实例并发领取
- 任务版本条件
- 资源配额
- 领取后进程崩溃
- 事务回滚
- 执行租约失效

SKIP LOCKED 只用于减少队列式行领取的竞争，不自动解决资源配额和跨系统分发一致性。

## 9.4 Transactional Outbox

对于需要在数据库事务提交后通知其他组件的状态变化，推荐 Transactional Outbox。

例如任务进入 READY：

在同一个事务内：

1. 更新 Task 状态。
2. 插入 OutboxEvent。
3. 提交事务。

后台发布器读取 OutboxEvent 并投递任务通知。

只有消息成功发布且达到约定确认条件后，才更新 OutboxEvent 发布状态。

消费者必须能够处理重复消息。

## 9.5 Inbox 与事件去重

对于跨进程的事件消费，可通过 EventID 记录消费状态。

消费者在事务中检查事件是否已处理，再进行状态变更。

对任务状态推进等关键事件，重复消费必须不改变已经确认的业务结果。

## 9.6 对象存储的一致性

对象存储上传和数据库事务无法天然构成一个原子操作。

建议采用分阶段产物提交：

1. Worker 上传到临时命名空间。
2. Worker 获得文件校验信息。
3. Worker 提交结果清单。
4. 服务端校验有效执行租约。
5. 数据库事务内登记资产版本及任务结果。
6. 异步清理未被正式引用的临时文件。

正式登记后的资产不能依赖随时可能被清理的短期临时文件。

实际实现可以采用稳定对象键、原子元数据确认和引用状态管理，避免数据库提交后仍缺少最终文件。

## 9.7 重复 AI 调用

对于可能已经被第三方接受但回执丢失的 AI 请求，系统应优先查询供应商任务状态。

如果供应商支持客户端幂等键，适配器应按其契约使用。

如果供应商不支持查询或幂等，则无法从平台侧严格保证不重复计费。

此时应根据业务策略决定是否重试，并记录可能发生的重复成本。

## 9.8 数据恢复与对账

需要周期性或事件驱动的 Reconciler，检查：

- 长期处于 RUNNING 但租约已失效的任务
- 处于 READY 但缺少可用调度通知的任务
- 任务已成功但节点未推进的异常记录
- Outbox 未发布事件
- 临时资产残留
- 资源预留未释放
- 工作流处于非终态但无法继续推进的情况

Reconciler 的操作必须幂等，并保留诊断记录。

# 第十章 Scheduler 架构

## 10.1 调度器职责

Scheduler 接收满足执行条件的 Task，并根据资源、配额和策略决定能否执行。

Scheduler 不负责理解分镜、剧本或具体视频业务。

## 10.2 调度输入

调度决策至少依赖：

- TaskType
- RequiredCapability
- ResourceRequirements
- Priority
- WorkspaceID
- QueueTime
- Deadline
- ProviderQuota
- WorkerAvailability

## 10.3 调度输出

调度器最终产生执行授权，关联：

- TaskID
- AttemptID
- WorkerSessionID
- LeaseToken
- LeaseExpiresAt
- ResourceReservation

执行授权需要具备可验证的有效性。

## 10.4 资源模型

统一资源需求描述应支持：

- CPU
- Memory
- GPU
- VRAM
- ConcurrencySlot
- ProviderRequestQuota
- ProviderTokenQuota

不同资源不是同一计量单位。

不能将 API 请求限流和 CPU 使用率简单转换为一个通用数值相加比较。

## 10.5 调度策略

调度系统分层执行规则：

第一层：任务是否已经 READY。

第二层：用户和工作空间是否具有执行配额。

第三层：模型供应商是否允许当前调用。

第四层：是否存在满足能力和资源条件的 Worker。

第五层：根据优先级、公平性及等待时间选择任务。

## 10.6 防止资源饥饿

只使用静态优先级可能导致低优先级任务长期无法执行。

长期可增加：

- 等待时间权重
- 工作空间公平份额
- 任务年龄提升
- 队列容量预留
- 任务类型资源分池

调度算法必须能够解释某个任务为什么持续等待。

## 10.7 配额的原子协调

如果多个 Scheduler 实例同时分配资源，配额校验与资源预留必须具备并发安全性。

建议将关键资源预留记录纳入权威状态管理。

对于高吞吐场景，可以逐步引入专门的配额协调器，但必须定义配额状态如何与持久化任务状态核对。

## 10.8 队列设计

推荐先将 PostgreSQL 作为权威任务状态来源。

Redis 可以用于：

- Ready Task 唤醒通知
- 优先级候选缓存
- 调度协调辅助
- 热点状态缓存

如果使用 Redis Streams，需要明确消费者组、消息确认和待处理消息恢复机制。

不能把 Redis 消息是否存在直接等同于 Task 是否存在。

# 第十一章 Worker Runtime 架构

## 11.1 Worker 定义

Worker 是能够执行一种或多种 Task Capability 的独立运行单元。

Worker 不应包含工作流编排逻辑。

## 11.2 Worker 生命周期

Worker 运行流程：

1. 启动并加载配置。
2. 向控制面注册。
3. 上报能力和可用资源。
4. 获取任务执行授权。
5. 下载或解析输入。
6. 执行任务。
7. 上报心跳和进度。
8. 上传输出产物。
9. 请求确认结果。
10. 释放本地资源。
11. 继续领取任务。

## 11.3 WorkerSession

需要区分 Worker 的稳定身份和单次启动会话。

WorkerSession 至少包含：

- SessionID
- WorkerID
- StartedAt
- LastHeartbeatAt
- Capabilities
- TotalResources
- AvailableResources
- Status

这样 Worker 重启后，旧 Session 的执行权不会被错误地继承。

## 11.4 Lease 机制

租约是限时执行授权。

Worker 在执行过程中必须按照协议续租。

租约有效性由权威协调状态决定。

如果 Worker 已经失去租约，则不得继续提交有效结果。

租约并不意味着失联 Worker 的外部副作用已经停止，因此重试逻辑还必须考虑实际执行器的语义。

## 11.5 Fencing Token

为降低过期 Worker 覆盖新执行结果的风险，采用单调递增的执行代数或具有等价校验能力的令牌。

结果提交时需同时匹配 Task 当前执行代数与有效 Attempt。

仅使用 WorkerID 或过期时间进行判断并不充分。

## 11.6 任务处理器接口

Worker Runtime 通过 Handler Registry 将 TaskType 映射到执行器。

典型 Handler：

- LLMHandler
- ImageGenerationHandler
- VideoGenerationHandler
- TTSHandler
- TranscriptionHandler
- FFmpegHandler
- FileTransferHandler

每个 Handler 应具有明确的输入、输出、超时和错误分类契约。

## 11.7 取消与超时

Worker 使用执行上下文传播取消信号。

对于 FFmpeg 等子进程，需要支持进程终止、退出等待和临时文件清理。

对于第三方异步 AI 任务，如果供应商不支持取消，则平台只能停止等待、拒绝迟到结果或执行供应商支持的取消操作，不能保证远端计算立即停止。

## 11.8 资源隔离

普通 Go Goroutine 并不构成 CPU、内存或操作系统级隔离。

CPU/内存密集任务需要依靠进程、容器、系统资源限制等机制实现隔离。

不可信第三方执行器应采用更严格的隔离环境。

# 第十二章 Model Gateway 架构

## 12.1 设计目标

使业务系统依据 AI 能力调用模型，而非直接依赖供应商 SDK。

## 12.2 核心职责

- Provider 管理
- 模型能力声明
- 请求适配
- 返回结果标准化
- 错误映射
- 超时处理
- 限流协作
- 用量记录
- 模型执行任务状态查询

## 12.3 能力接口

建议根据任务语义划分接口：

- TextGeneration
- ImageGeneration
- ImageEditing
- VideoGeneration
- SpeechSynthesis
- SpeechRecognition
- MultimodalUnderstanding

不要建立参数无限膨胀的单一 Generate 接口来覆盖所有能力。

## 12.4 同步与异步调用

部分模型接口会同步返回结果。

部分模型接口仅返回外部 JobID，需要持续轮询或等待回调。

统一模型执行协议必须支持：

SUBMITTED、PROCESSING、SUCCEEDED、FAILED、CANCELED、UNKNOWN。

模型外部任务状态与 MediaFlow Task 状态是两套不同概念。

Worker 或 Provider Adapter 负责将外部生命周期映射到内部执行结果。

## 12.5 模型配置快照

工作流运行应记录实际使用的：

- Provider
- Model Identifier
- Model Configuration Version
- 调用参数
- 适配器版本
- 关键输出格式约束

模型供应商更新后，历史记录仍然需要能够解释当时执行使用的配置。

## 12.6 供应商错误分类

至少区分：

- AUTHENTICATION_ERROR
- RATE_LIMITED
- QUOTA_EXCEEDED
- INVALID_INPUT
- CONTENT_REJECTED
- PROVIDER_UNAVAILABLE
- PROVIDER_TIMEOUT
- INTERNAL_ERROR
- UNKNOWN_RESULT

错误分类决定是否可以自动重试。

并非所有 HTTP 4xx 都应立即失败，也并非所有 HTTP 5xx 都适合无条件重试。

# 第十三章 Media Runtime 架构

## 13.1 职责

Media Runtime 负责执行实际的多媒体转换和渲染操作。

主要支持：

- 媒体信息探测
- 图片预处理
- 音频处理
- 字幕生成和处理
- 视频片段拼接
- 音视频合成
- 转码
- 输出文件校验

## 13.2 Media Job

媒体处理任务输入应是明确的 MediaJobSpec。

包括：

- 输入 AssetVersion 列表
- CompositionVersion
- 输出规格
- 编码参数
- 资源要求
- 超时约束

不能将前端随意传入的 FFmpeg 命令直接交由 Worker 执行。

## 13.3 Composition 编译

将业务层 CompositionVersion 转换为具体媒体渲染计划。

该转换应具备独立验证能力。

包括：

- 素材是否存在
- 时间轴是否有效
- 轨道参数是否兼容
- 输出配置是否合法
- 所需编解码能力是否可用

## 13.4 渲染质量层级

支持预览渲染和正式渲染。

二者使用同一业务编排定义，但可以采用不同分辨率、码率和输出质量参数。

## 13.5 结果校验

FFmpeg 进程退出码为零并不必然证明最终作品满足业务要求。

还应根据实际场景检查：

- 文件存在
- 文件可读取
- 媒体流有效
- 时长在允许范围内
- 输出分辨率正确
- 必需音视频轨道存在
- 校验值和对象存储信息有效

# 第十五章 API 与事件契约

## 15.1 API 设计原则

- 资源导向
- 明确的版本策略
- 统一身份认证
- 统一错误响应
- 支持请求幂等
- 长时间任务采用异步响应
- 使用稳定的业务标识
- 不暴露内部数据库实现细节

## 15.2 API 资源范围

需要覆盖：

/workspaces

/projects

/briefs

/scripts

/storyboards

/assets

/works

/workflows

/workflow-runs

/tasks

/models

/providers

/workers

/usage

## 15.3 异步执行模式

用户启动工作流时，API 返回 WorkflowRunID，而不是保持 HTTP 连接直至视频生成完成。

前端可以通过查询接口、服务端事件或其他受支持的实时机制获得进度。

最终交付结果由作品及资产 API 提供。

## 15.4 请求幂等

对于创建运行实例、发起收费模型调用、创建作品交付等关键写操作，建议支持 Idempotency-Key。

相同授权主体、作用范围、键和相同请求语义，在规定有效期内应返回相同逻辑操作结果。

相同键对应不同请求内容应返回冲突错误。

## 15.5 事件结构

核心事件至少包含：

- EventID
- EventType
- AggregateID
- AggregateVersion
- WorkspaceID
- OccurredAt
- CorrelationID
- CausationID
- PayloadVersion
- Payload

所有事件必须定义拥有者、消费者、重复处理方式和版本兼容规则。

# 第十六章 安全与租户隔离

## 16.1 租户边界

Workspace 是主要的数据访问边界。

所有业务查询必须明确作用范围。

## 16.2 Worker 授权

Worker 不应持有跨租户通用访问权限来任意读取对象存储内容。

可以使用短期访问凭证或受控数据获取接口，仅允许访问当前任务需要的输入与输出位置。

## 16.3 密钥管理

模型 API Key 加密存储。

凭证轮换不能破坏历史运行记录，但历史记录也不应包含原始密钥。

## 16.4 资源安全

执行任务时应限制：

- 文件系统访问范围
- 网络访问范围
- CPU 和内存
- 运行时间
- 可调用的工具类型

需要防范 SSRF、路径穿越、恶意媒体文件和未经授权的跨租户数据访问。

## 16.5 审计

重要业务操作记录操作人、操作时间、资源、动作和必要的变更摘要。

审计记录与普通调试日志分开管理。

# 第十七章 可观测性设计

## 17.1 追踪模型

一次用户创建的生产行为需要能够贯穿：

API Request → WorkflowRun → NodeRun → Task → TaskAttempt → Provider/FFmpeg → Asset。

建议统一关联：

- request_id
- trace_id
- workflow_run_id
- node_run_id
- task_id
- attempt_id
- worker_session_id

## 17.2 日志

使用结构化日志，避免完全依靠自由文本解析故障。

重要状态转移应保存业务事件或明确的审计记录。

## 17.3 指标

重点指标包括：

- workflow_duration
- workflow_success_rate
- task_queue_wait
- task_execution_duration
- task_retry_total
- worker_active
- lease_expired_total
- resource_utilization
- provider_latency
- provider_error_total
- asset_upload_failure_total

## 17.4 诊断链路

管理员应该能够从一个失败的 WorkflowRun 定位：

失败节点 → 对应 Task → TaskAttempt → Worker → 错误详情 → 模型调用或媒体处理步骤。

## 17.5 告警

重点关注：

- 任务长期未调度
- Worker 大量失联
- 租约频繁过期
- 工作流成功率下降
- Provider 大量限流
- Outbox 积压
- 对账异常
- 存储资源不足

# 第十八章 完整视频生产架构验证

## 18.1 业务输入

用户创建一个视频项目。

输入主题、时长、风格、配音语言和输出规格。

系统创建 Project，并保存 CreativeBriefVersion。

## 18.2 工作流实例创建

用户选择视频生产工作流版本并启动。

系统：

1. 校验权限和预算。
2. 固定工作流版本。
3. 固定创作输入快照。
4. 创建 WorkflowRun。
5. 初始化必要 NodeRun。
6. 激活起始节点。

## 18.3 剧本生成

GenerateScript 节点产生 Task。

Worker 调用 Model Gateway。

生成结果经过结构校验后登记为 ScriptVersion。

Task 完成并推进 NodeRun。

## 18.4 分镜生成

GenerateStoryboard 节点根据 ScriptVersion 生成分镜。

结果形成 StoryboardVersion。

如果需要人工确认，则进入 WAITING。

## 18.5 分镜并行生产

确认后的 StoryboardVersion 包含 N 个 Scene。

工作流引擎展开场景级生产任务。

图片、配音及其他素材任务依据实际依赖关系并行执行。

Scheduler 根据模型配额和 Worker 能力安排执行。

## 18.6 素材确认

每个生成结果登记为 AssetVersion。

同一 Scene 可以拥有多个候选结果。

被选中的素材版本写入后续 Composition 输入。

## 18.7 视频编排

系统生成 CompositionVersion。

Composition 引用确定的 AssetVersion。

媒体编排不依赖临时未确认的 Task 输出文件。

## 18.8 渲染与交付

Media Worker 根据 CompositionVersion 执行渲染。

结果通过校验并登记为 AssetVersion。

作品模块创建 WorkVersion。

用户预览和审核后，作品进入可交付状态。

## 18.9 局部修改

用户修改 Scene 3。

系统建立新的 StoryboardVersion 或 SceneRevision。

根据依赖规则判断需要更新 Scene 3 的视觉素材及相关后继内容。

其他无影响的素材继续复用。

原作品和工作流历史不被覆盖。

## 18.10 故障验证

假设 Scene 7 的图片生成 Worker 在上传结束后失联。

系统：

1. 检测执行租约失效。
2. 检查是否存在已确认的有效结果。
3. 若结果已提交，则不重复修改任务。
4. 若结果未提交，按照策略创建新的尝试。
5. 旧 Attempt 的迟到提交被拒绝。
6. 新结果被确认后推进对应 NodeRun。
7. 其他已完成 Scene 不受影响。

该场景是任务执行模型正确性的核心验收案例。

# 第十九章 性能与容量规划

## 19.1 工作负载模型

系统容量需要根据任务类型分别计算。

例如：

100 个工作流，每个包含 20 个任务，总计约 2000 个 Task。

其中可能包含：

- 短时间数据库操作
- 外部 LLM 请求
- 图片生成
- 长时间视频生成
- CPU 密集型 FFmpeg 任务

总任务数量不等于同时运行数量。

## 19.2 容量评估指标

需要测量：

- 每秒创建任务数
- 每秒调度任务数
- 每秒状态转移次数
- 平均队列等待时间
- 任务执行时间分布
- Worker 实际资源利用率
- PostgreSQL 事务延迟
- Redis 消息积压
- 对象存储吞吐量
- 外部 Provider 限额使用情况

## 19.3 性能目标设定

架构阶段不应编造固定吞吐承诺。

正式性能 SLO 需要基于任务类别、资源规格和压测结果制定。

## 19.4 扩容策略

优先考虑：

1. 增加相应能力的 Worker。
2. 优化外部模型并发和配额使用。
3. 优化数据库索引和任务领取批次。
4. 降低热点状态更新。
5. 将高负载调度组件独立部署。
6. 在有明确瓶颈证据时调整消息和存储架构。

不建议仅依据任务总数就提前引入复杂微服务或分布式数据库。

# 第二十一章 架构决策记录

## ADR-001：采用模块化单体控制面

**决策：** 初始采用模块化单体，不直接拆分所有业务服务。

**原因：** 核心领域仍需要持续验证，多个模块间存在强一致性操作。

**影响：** 需要严格维护模块边界，防止演变为耦合的单体系统。

## ADR-002：PostgreSQL 作为权威状态来源

**决策：** 核心工作流和任务状态保存于 PostgreSQL。

**原因：** 需要事务、持久化、条件更新和可靠恢复能力。

**影响：** 高并发调度需要关注锁竞争和数据库容量。

## ADR-003：定义与执行实例分离

**决策：** WorkflowVersion、WorkflowRun、NodeRun、Task、TaskAttempt 分别建模。

**原因：** 支持版本固定、执行重试、追踪和局部恢复。

## ADR-004：采用至少一次执行的容错模型

**决策：** 不假设跨网络、数据库、Worker 和外部 API 的恰好一次执行。

**原因：** 分布式故障下重复执行可能不可避免。

**措施：** 租约、Fencing Token、幂等提交和结果对账。

## ADR-005：执行结果采用版本化资产

**决策：** 生成结果作为不可变 AssetVersion 管理。

**原因：** 支持修改、回滚、重用和执行追溯。

## ADR-006：工作流引擎不直接执行多媒体任务

**决策：** Workflow Engine 负责状态与依赖，Worker 负责执行。

**原因：** 避免复杂任务阻塞编排核心，并允许多资源池扩展。

## ADR-007：采用 Outbox 处理可靠事件发布

**决策：** 数据库状态变更与待发布事件在同一事务内记录。

**原因：** 减少数据库提交成功但消息未发送导致的状态不一致。

## ADR-008：模型接入基于能力契约

**决策：** 业务层依赖生成能力而非具体供应商 SDK。

**原因：** 支持长期模型替换、供应商适配与能力演进。

# 第二十三章 架构验收标准

本架构是否成功，不以使用了多少技术组件作为判断依据。

应以以下能力作为验收基线。

### 领域正确性

系统能够准确表达项目、作品、资产、工作流和任务之间的关系。

### 执行正确性

DAG 依赖能够正确解析，动态任务能够追踪，条件分支能够按规则完成。

### 故障可恢复性

Worker、Scheduler 或外部 Provider 异常时，平台能够识别异常并执行受控恢复。

### 结果一致性

重复事件、重试任务和迟到执行结果不会破坏已确认的业务结果。

### 资产可靠性

用户已确认的作品和素材在重新生成、重试和系统恢复期间保持可追踪、可引用。

### 资源可管理性

不同任务能按照资源需求、配额和执行策略合理分配。

### 扩展性

新增模型供应商、新任务类型和新媒体处理能力，不需要修改所有业务模块。

### 可维护性

关键领域规则、架构边界和技术决策具有测试与文档支持。

# 第二十四章 结论

MediaFlow 的技术基础应当由三个核心体系构成。

**第一，内容生产领域体系。**

负责理解用户要制作什么、已有内容是什么、哪些素材可以复用以及最终作品如何形成。

**第二，工作流执行体系。**

负责理解生产流程如何定义、节点之间如何依赖、状态如何推进以及失败如何恢复。

**第三，资源与计算执行体系。**

负责理解什么任务可以执行、需要什么资源、由谁执行以及如何可靠确认结果。

三个体系需要通过稳定的领域对象、接口契约和持久化状态协同工作。

长期架构应坚持：

- 产品业务对象独立于任务执行实现。
- 工作流定义独立于工作流运行。
- 工作流运行独立于 Worker 生命周期。
- 任务执行独立于结果正式提交。
- AI 模型供应商独立于内容生产业务。
- 多媒体资产独立于具体工作流实例。
- 逻辑模块边界独立于物理部署边界。

最终，MediaFlow 应成为一个既能支撑完整 AI 多媒体创作，又能可靠组织复杂计算任务，并能够持续扩展到其他 AI 生产工作流的产品平台。

**本文件作为后续数据库、Workflow Engine、Scheduler、Worker Runtime 和 API 详细设计的架构基线。**
